文档解析实战：Apache PDFBox + Apache POI 抽取 PDF/Word/Markdown 纯文本与表格

总预估时长：约 55 分钟（依赖与环境 10min / PDF 抽取 15min / Word 抽取 15min / 统一入口与表格 10min / 验收自测 5min）· 主线 Java（Spring AI 视角），Python 仅辅助

一、为什么文档解析是 RAG 的第一道关口（10min）

RAG 的 garbage in, garbage out 从第一行代码就开始了：抽取阶段丢失的表格行列、被打乱的阅读顺序、乱码，后续切分与检索全部无法挽回。企业语料的真实构成决定了你必须至少覆盖三类格式：PDF（技术方案/产品手册）、Word（内部规范/合同）、Markdown（Wiki/代码仓库文档）。

决策要点：Spring AI 生态里通用解析可交给 Apache Tika（一个入口吃掉几十种格式），但对 PDF/Word 的精细控制（保留表格结构、按页抽取）建议直接用 PDFBox 与 POI，Tika 本质上也是封装它们。路线图推荐项目 rag-knowledge-system 正是采用 Tika 做多格式解析、rag-study-helper 做多格式文档解析入库的工程范例。

二、PDF 抽取：Apache PDFBox（15min）

PDFBox 的核心 API 是 PDFTextStripper：它按文章流（article）逐块处理页面字符，能保持大致阅读顺序。先加依赖：

<dependency>
    <groupId>org.apache.pdfbox</groupId>
    <artifactId>pdfbox</artifactId>
    <version>3.0.8</version>
</dependency>

3.x 版本 API 变为 Loader.loadPDF(...)，比 2.x 的 PDDocument.load(...) 更安全（自动处理临时文件释放）。最小可用示例：

import org.apache.pdfbox.Loader;
import org.apache.pdfbox.pdmodel.PDDocument;
import org.apache.pdfbox.text.PDFTextStripper;

public String extractPdf(byte[] pdfBytes) throws IOException {
    try (PDDocument doc = Loader.loadPDF(pdfBytes)) {
        PDFTextStripper stripper = new PDFTextStripper();
        stripper.setSortByPosition(true);   // 按坐标排序，双栏 PDF 必开
        stripper.setStartPage(1);
        stripper.setEndPage(doc.getNumberOfPages());
        return stripper.getText(doc);
    }
}

三个实战陷阱：

  • 双栏/表格 PDF 阅读顺序错乱：默认按内部流顺序输出，setSortByPosition(true) 按坐标重排后才接近人眼阅读顺序。
  • 扫描件无文字层：PDFBox 抽出空串，说明是图片型 PDF，必须先走 OCR（如 Tesseract），这是企业语料里最常见的暗坑。
  • 编码乱码：多为字体未内嵌 ToUnicode 映射，PDFBox 层面无解，只能标注该文档质量差并降权。

三、Word 抽取：Apache POI（15min）

POI 按 Word 版本分两套 API：老 .doc（Word 97-2003）用 scratchpad 的 HWPFDocument/WordExtractor；新 .docx 用 XWPFDocument。企业环境建议明确只收 .docx，把 .doc 的历史包袱挡在验收标准外。

<dependency>
    <groupId>org.apache.poi</groupId>
    <artifactId>poi-ooxml</artifactId>
    <version>5.3.0</version>
</dependency>

快速全文用 XWPFWordExtractor（段落+表格+页眉页脚一把梭）；要保留表格行列结构就必须遍历 IBodyElement，按类型分别处理段落与表格：

import org.apache.poi.xwpf.usermodel.*;

public String extractDocx(InputStream in) throws IOException {
    StringBuilder sb = new StringBuilder();
    try (XWPFDocument doc = new XWPFDocument(in)) {
        for (IBodyElement el : doc.getBodyElements()) {
            if (el.getElementType() == BodyElementType.PARAGRAPH) {
                XWPFParagraph p = (XWPFParagraph) el;
                if (!p.getText().isBlank()) {
                    sb.append(p.getText()).append("\n\n");
                }
            } else if (el.getElementType() == BodyElementType.TABLE) {
                sb.append(tableToMarkdown((XWPFTable) el)).append("\n\n");
            }
        }
    }
    return sb.toString();
}

private String tableToMarkdown(XWPFTable table) {
    StringBuilder sb = new StringBuilder();
    List<XWPFTableRow> rows = table.getRows();
    for (int r = 0; r < rows.size(); r++) {
        sb.append("| ");
        for (XWPFTableCell cell : rows.get(r).getTableCells()) {
            sb.append(cell.getText().replace("\n", " ").replace("|", "\\|")).append(" | ");
        }
        sb.append("|\n");
        if (r == 0) {
            sb.append("|").append("---|".repeat(rows.get(r).getTableCells().size())).append("\n");
        }
    }
    return sb.toString();
}
表格转 Markdown 的意义：行列结构对检索和 LLM 都是最友好的形态——单元格文本完整、语义紧凑，比线性化成一串句子召回质量高得多。这一步直接服务于后面的智能切分任务。

四、Markdown 与统一解析入口（10min）

Markdown 是结构最完整的语料（标题层级天然是切分锚点），解析时只需处理 front-matter 和代码块保护，正则足够，无需重型依赖。最后把三者收敛成一个按扩展名路由的统一工具类，这是验收标准要求的样子：

public class DocumentParser {

    public ParsedDocument parse(Path file) throws IOException {
        String name = file.getFileName().toString().toLowerCase();
        String text = switch (name.substring(name.lastIndexOf('.') + 1)) {
            case "pdf"  -> extractPdf(Files.readAllBytes(file));
            case "docx" -> extractDocx(Files.newInputStream(file));
            case "md"   -> Files.readString(file);
            default -> throw new IllegalArgumentException("不支持的格式: " + name);
        };
        return new ParsedDocument(name, text);
    }
}

public record ParsedDocument(String source, String text) {}

Spring AI 侧的对接点：TikaDocumentReader / TextReader 产出统一的 Document 流，随后交给 TokenTextSplitter（下一任务的主角）。解析层的产出契约就一句话：干净文本 + 保留结构标记。

五、验收自测（5min）

  • 准备 3 份真实文档：一份简历 PDF、一份含表格的技术方案 docx、一份 Markdown 手册。
  • 断言：每份文档抽取结果非空；docx 表格输出为合法 Markdown 表格（含 |---| 分隔行）；中文无乱码。
  • 记录每份文档的字符数与耗时，写进决策日志——这是后续评测报告（RAG 评测任务）的基线数据。
面试串联：文档解析是「RAG 完整链路 + Chunking」第一梯队题的起点——面试官问"你的 RAG 怎么处理表格"时，答案就藏在本教程第三节：表格线性化 vs 结构化保留的取舍，以及它对检索召回的影响。
