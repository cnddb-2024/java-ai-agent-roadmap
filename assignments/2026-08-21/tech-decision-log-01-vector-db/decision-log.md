# 技术决策日志 #01：RAG 项目向量库选型

## 作业信息

- **日期**: 2026-08-21
- **Phase**: Phase 1（第 24/168 天）
- **对应飞书任务**: 技术决策日志 #01：RAG 项目向量库选型 pgvector vs Qdrant vs Milvus
- **决策结论**: pgvector（当前阶段）→ Qdrant/Milvus（规模达标后迁移）

---

## 一、选型背景

RAG 项目需要向量数据库存储 Embedding 向量并支持相似度检索。候选方案：

| 方案 | 类型 | 优势 | 劣势 |
|------|------|------|------|
| pgvector | PostgreSQL 扩展 | 事务一致性、运维复用、零额外组件 | 单机扩展受限、大索引性能差 |
| Qdrant | 专用向量库 | 轻量、过滤性能好、API 友好 | 需独立运维、无事务 |
| Milvus | 分布式向量库 | 能力最强、可扩展性最好 | 重、运维复杂、资源消耗大 |

---

## 二、核心术语（6 个）

以下术语在 RAG 向量库选型中经常出现，逐个说明：

### 1. SLA（Service Level Agreement，服务等级协议）

你和数据库服务商签的"达标承诺"，比如"可用性 99.9%"表示一年里故障时间不超过约 8.8 小时。帮你判断自建（如 pgvector 跑在自己机器上，没有 SLA）和托管服务（Qdrant/Milvus 云版有 SLA）的风险差异。

### 2. P99（99 百分位，P99 latency）

把一次请求的耗时从快到慢排序，排在第 99% 位置的那个值，代表"绝大多数用户感受到的最差延迟"。之所以不用平均值，是因为平均会被偶尔的慢请求掩盖，而 P99 更能反映真实体验。

### 3. 元数据与向量的最终一致窗口（metadata and vector eventual consistency window）

当元数据（如文档权限、标签）和向量分别存储、分开更新时，两者短暂不同步的时间段。窗口期内可能出现"向量能搜到但元数据还没更新"或反过来，导致查到了过期/不该查到的结果；选型时看它是否会引入这种不一致。

### 4. 向量+元数据过滤的计划器陷阱（vector + metadata filter planner trap）

数据库执行"先做向量检索，再按元数据筛选"时，优化器（planner）可能选错执行顺序的坑——比如先按元数据筛选再算距离，可能白算一堆；或先按向量召回 top-K 再过滤，可能因过滤后数量不足而漏掉真正该返回的结果。

### 5. HNSW 内存开销（HNSW memory overhead）

HNSW 是目前主流的向量检索索引，它额外存储"多层邻居关系"，会让内存占用明显翻倍（通常比向量本身数据大数倍）。数据量大时这会成为内存成本的决定因素，pgvector 自建要自己扛，托管库则要按内存计费。

### 6. 百万级以上 ANN 索引差距（ANN index gap above one million）

数据量在百万条以上时，不同引擎在高维向量近似检索（ANN）上的性能/召回率差距才真正拉开——pgvector 受单机扩展限制明显落后，Qdrant/Milvus 这类专用引擎靠分片、分布式和更优索引结构拉开差距。小数据量时它们差别不大，数据量大了才见真章。

## 三、选型决策

**一句话总结**：pgvector 便宜省事但无 SLA、扩展差、大索引吃亏；Qdrant 轻量但需管理；Milvus 能力最强但重、贵。具体选哪个取决于数据量、延迟要求（P99）和运维投入。

### 当前阶段选择：pgvector

**选择理由**：
- 向量规模 < 300 万，pgvector 性能足够
- P99 延迟 < 200ms 可接受
- 可接受元数据与向量的最终一致窗口
- 已有 PostgreSQL 运维能力，迁移和运维成本很低
- Spring AI 和 LangChain4j 切换向量库只需换一个 starter 依赖和建表，这是框架层级的解耦红利
- 选型决策可逆——达到一定规模再替换

### 迁移触发条件

当以下任一条件持续满足时，启动选型复核：

| 触发条件 | 阈值 | 目标方案 |
|----------|------|----------|
| 向量数量 | > 300 万 | Qdrant（轻量优先） |
| P99 延迟 | > 200ms 持续一周 | Qdrant 或 Milvus |
| 内存压力 | HNSW 索引内存 > 可用内存 70% | Qdrant（内存效率优） |
| 可用性要求 | 需要正式 SLA | 托管服务（Qdrant Cloud / Zilliz） |

## 四、面试话术（10min）

对应第一梯队「RAG 评测三层指标」与「混合检索 + Rerank」的选型追问。

### Q: 为什么不用专门的向量数据库？

> 用 pgvector 主要考虑几点：向量规模、P99 延迟、事务一致性即向量和元数据的最终一致窗口、运维复用等。如果向量规模小于 300 万、P99 延迟 < 200ms、并且可接受最终一致窗口、并且已有 PostgreSQL 迁移和运维成本很低，可以选择 pgvector。并且两个框架 Spring AI 和 LangChain4j 换这种库也只是需要换一个 starter 依赖和建表，这是框架层级的解耦红利。等达到一定规模可以再替换，这个是选型决策可逆性。

### Q: pgvector 有什么坑？

> 主要三个坑：
>
> 1. **计划器陷阱**：pgvector 执行检索时，计划器（planner）执行顺序可能造成不好的效果——计划器可能先执行元数据过滤再执行向量检索、或先向量检索再元数据过滤，就可能导致白白计算相似度而后又被过滤、先过滤后再执行 top-K 时数据不足而错过真正更准确的答案。
>
> 2. **HNSW 内存开销**：HNSW 是主流的向量检索索引，存储多层邻居关系，当数据量大时，这个索引本身会占用极大的内存，通常比向量还大数倍。如果是自建则自己扛，如果是托管库则需要考虑内存开销成本。
>
> 3. **百万级以上 ANN 索引差距**：百万级向量数据时的检索性能和召回率等指标才真正拉开距离，pgvector 的单机限制会落后，而 Qdrant 和 Milvus 的分布式、索引优化等才会真正领先。

### Q: 什么时候换？

> 触发一定条件指标才考虑替换选型，比如向量已经超过 300 万、P99 延迟超过 200ms 持续一周等。决策有边界才可信。
