01

问题背景：为什么需要增量更新

RAG（Retrieval-Augmented Generation）系统的知识库并非一次构建、永久不变。文档会更新、删除、新增，而向量数据库（Vector Database）中已入库的 Embedding 向量却不会自动同步。这种"数据已变、向量未变"的脱节会导致 RAG 检索到过时、矛盾甚至已删除的内容——这就是 幽灵知识问题（Ghost Knowledge Problem）。

类比理解：这和 MySQL 中"主库数据已更新但从库缓存还是旧值"的问题本质相同——只不过这里的"缓存"是向量索引，而"过期数据"是旧版本的 Embedding 向量。在 RAG 场景下，幽灵知识比普通缓存过期更危险：检索器会把旧向量当作"高度相关"返回给 LLM，而 LLM 会用这些过时信息生成回答，用户完全无法察觉。

幽灵知识的五种类型

👻

Stale（过期）

文档已更新，但向量库里还是旧版本的 Embedding。用户问到这个文档时，RAG 会检索到旧内容并生成过时回答。

🏚️

Orphan（孤儿）

文档已从知识库删除，但向量库里对应的 Embedding 仍然存在。RAG 会检索到"不该存在"的内容。

👯

Duplicate（重复）

同一文档被多次入库，向量库中存在多个相同或近似 Embedding。检索时同一信息出现多次，浪费 context window。

📉

Drift（漂移）

Embedding 模型升级了，但旧 Embedding 没有重新生成。新旧模型产生的向量空间不一致，检索质量下降。

⚔️

Contradictory（矛盾）

旧版和新版文档的 Embedding 同时存在于向量库。RAG 检索到两个矛盾版本，LLM 生成的回答前后冲突。

这五种幽灵知识的核心根因只有一个： 向量数据库中的 Embedding 与源文档之间缺乏一致性保障机制。本教程的增量更新管道正是为了消灭幽灵知识而设计的。

02

变更检测方案：内容哈希 + 时间戳粗筛

增量更新的第一步是回答一个问题： "这个文档到底变没变？" 答案不能靠文件名或路径——同名文件内容可能完全不同。正确做法是计算文档内容的哈希值。

2.1 content hash（内容哈希）

content hash（内容哈希）：对文档全文计算 SHA-256 摘要，得到一个 64 位十六进制字符串。类比 Git 的 commit hash——对文件内容生成唯一"指纹"，内容哪怕只改了一个字符，哈希值也完全不同。

单纯比较哈希的代价是：每次检测都需要读取全文并计算 SHA-256，对于万级文档库来说逐个哈希太慢。因此引入 两阶段粗筛 + 精筛策略：

阶段 检测维度 复杂度 说明
粗筛 lastModified 时间戳 O(1) 磁盘 stat 时间戳没变 → 直接跳过，无需读文件内容
精筛 content hash (SHA-256) O(n) 读取全文 时间戳变了才计算哈希，哈希相同 → 内容未变（可能是 touch）

2.2 内容哈希工具实现

⚠️ 框架无内置实现，以下为业界通用手写方案
Spring AI 不提供内容哈希计算工具。以下使用 JDK 标准库 MessageDigest 实现，是业界通用做法。
Java ContentHashUtil.java — SHA-256 内容指纹 
public class ContentHashUtil {

    /**
     * 计算文档内容的 SHA-256 哈希值（content hash）
     * 类似 Git commit hash：对内容生成唯一指纹
     *
     * @param content 文档全文
     * @return 64 位十六进制字符串
     */
    public static String sha256(String content) {
        try {
            MessageDigest digest = MessageDigest.getInstance("SHA-256");
            byte[] hash = digest.digest(content.getBytes(StandardCharsets.UTF_8));
            return HexFormat.of().formatHex(hash);
        } catch (NoSuchAlgorithmException e) {
            throw new RuntimeException("SHA-256 not available", e);
        }
    }
}

2.3 变更检测器实现

⚠️ 框架无内置实现，以下为业界通用手写方案
Spring AI 不提供文档变更检测器。以下通过元数据库比对实现，是 RAG 系统标准组件。
Java DocumentChangeDetector.java — 两阶段变更检测 
@Service
public class DocumentChangeDetector {

    private final DocumentMetadataRepository metadataRepo;

    public DocumentChangeDetector(DocumentMetadataRepository metadataRepo) {
        this.metadataRepo = metadataRepo;
    }

    /**
     * 变更检测：先粗筛（时间戳），再精筛（内容哈希）
     */
    public ChangeResult detect(String docId, String content, long lastModified) {
        String newHash = ContentHashUtil.sha256(content);

        Optional<DocumentMetadata> existing = metadataRepo.findById(docId);

        // 新文档 → CREATE
        if (existing.isEmpty()) {
            return ChangeResult.created(docId, newHash);
        }

        DocumentMetadata meta = existing.get();

        // 粗筛：时间戳 + 哈希均未变 → 跳过
        if (meta.getLastModified() == lastModified
                && meta.getContentHash().equals(newHash)) {
            return ChangeResult.unchanged(docId);
        }

        // 精筛：哈希不同 → 内容已变
        if (!meta.getContentHash().equals(newHash)) {
            return ChangeResult.updated(docId, newHash, meta.getContentHash());
        }

        // 时间戳变但哈希相同 → 可能是 touch，内容未变
        return ChangeResult.unchanged(docId);
    }
}

ChangeResult 是一个密封类（sealed class），封装三种状态： CREATED、UPDATED、UNCHANGED，管道下游根据状态决定执行路径。

03

Spring AI VectorStore API（开箱实现）

框架版本：Spring AI 2.0 — 提供开箱即用的 VectorStore 接口，支持 add / delete / similaritySearch 三大核心操作。底层自动调用 EmbeddingModel 将文本转为向量，开发者无需手动调用 Embedding API。

Spring AI 2.0 的 VectorStore 接口是增量更新的核心抽象。它提供了三个与增量更新直接相关的方法：

方法签名 用途 增量更新角色
add(List<Document>) 批量入库文档（自动生成 Embedding） "后增"步骤——插入新版本向量
delete(List<String>) 按 chunk ID 批量删除 "先删"步骤——清除旧版本向量
delete(Filter) 按元数据条件删除（Spring AI 2.0 新增） 按 doc_id 一键删除某文档所有 chunk
Java KnowledgeBaseService.java — Spring AI 2.0 开箱 API 
import org.springframework.ai.document.Document;
import org.springframework.ai.vectorstore.VectorStore;
import org.springframework.ai.vectorstore.filter.Filter;

// Spring AI 2.0 开箱即用的 VectorStore 接口
@Service
public class KnowledgeBaseService {

    private final VectorStore vectorStore;  // Spring AI 自动注入

    public KnowledgeBaseService(VectorStore vectorStore) {
        this.vectorStore = vectorStore;
    }

    // 添加文档向量（自动调用 EmbeddingModel 生成 embedding）
    public void addDocuments(List<Document> documents) {
        vectorStore.add(documents);
    }

    // 按 chunk ID 批量删除（先删后增策略的"先删"步骤）
    public void deleteByChunkIds(List<String> chunkIds) {
        vectorStore.delete(chunkIds);
    }

    // 按 Filter 条件删除（Spring AI 2.0 新增）
    // 一键删除某 doc_id 下的所有 chunk
    public void deleteByDocId(String docId) {
        Filter filter = Filter.builder()
                .equals("doc_id", docId)
                .build();
        vectorStore.delete(filter);
    }
}
关键设计：add() 方法在内部自动完成"文本 → Embedding → 向量数据库写入"全链路，开发者不需要手动调用 EmbeddingModel.embed()。这意味着增量更新管道只需要关注"哪些文档变了"，而不需要关心向量化细节。
04

完整增量更新管道实现

将变更检测、先删后增、分块、向量化、元数据落盘串联起来，就构成了完整的增量更新管道。核心设计原则：

  • 先删后增（delete-then-add）：文档级别先删除旧版本所有 chunk，再插入新版本。保证同一 doc_id 在向量库中只有最新版本，避免 Contradictory 幽灵。
  • 确定性 chunk ID：doc_id + "_chunk_" + index，保证重复入库不会产生 Duplicate 幽灵。
  • 元数据全量记录：doc_id、content_hash、version_id、chunk_strategy、embedding_model、ingested_at 全部落盘，作为 source of truth。
框架版本：Spring AI 2.0 — 管道使用 VectorStore（add/delete）、DocumentSplitter（分块）等 Spring AI 开箱组件，编排逻辑为手写。
Java IncrementalUpdatePipeline.java — 完整管道 
@Service
public class IncrementalUpdatePipeline {

    private final VectorStore vectorStore;
    private final DocumentChangeDetector changeDetector;
    private final DocumentMetadataRepository metadataRepo;
    private final DocumentSplitter splitter;

    public IncrementalUpdatePipeline(VectorStore vectorStore,
            DocumentChangeDetector changeDetector,
            DocumentMetadataRepository metadataRepo,
            DocumentSplitter splitter) {
        this.vectorStore = vectorStore;
        this.changeDetector = changeDetector;
        this.metadataRepo = metadataRepo;
        this.splitter = splitter;
    }

    /**
     * 增量更新管道：检测 → 先删 → 分块 → 向量化 → 入库 → 元数据落盘
     */
    @Transactional
    public UpdateResult process(DocumentInput input) {
        // 1. 变更检测
        ChangeResult change = changeDetector.detect(
                input.getDocId(), input.getContent(), input.getLastModified());
        if (change.isUnchanged()) {
            return UpdateResult.skipped(input.getDocId());
        }

        // 2. 先删旧向量（文档级"先删后增"策略）
        //    使用 Filter 按 doc_id 一次性清除所有旧 chunk
        Filter deleteFilter = Filter.builder()
                .equals("doc_id", input.getDocId())
                .build();
        vectorStore.delete(deleteFilter);

        // 3. 分块 + 构建元数据
        Map<String, Object> meta = buildMetadata(input, change);
        List<Document> rawChunks = splitter.split(
                new Document(input.getContent(), meta));

        // 4. 设置确定性 chunk ID（doc_id + "_chunk_" + index）
        List<Document> chunks = new ArrayList<>();
        for (int i = 0; i < rawChunks.size(); i++) {
            String chunkId = input.getDocId() + "_chunk_" + i;
            chunks.add(new Document(chunkId,
                    rawChunks.get(i).getText(), meta));
        }

        // 5. 向量化 + 入库（Spring AI 自动调用 EmbeddingModel）
        vectorStore.add(chunks);

        // 6. 元数据落盘（source of truth）
        metadataRepo.save(buildMetadataEntity(input, change));

        return UpdateResult.success(input.getDocId(), change.getNewHash());
    }

    /**
     * 构建向量库元数据：doc_id, content_hash, version_id,
     * chunk_strategy, embedding_model, ingested_at
     */
    private Map<String, Object> buildMetadata(DocumentInput input, ChangeResult change) {
        Map<String, Object> meta = new HashMap<>();
        meta.put("doc_id", input.getDocId());
        meta.put("content_hash", change.getNewHash());
        meta.put("version_id", change.getVersionId());
        meta.put("chunk_strategy", "token-500-overlap-50");
        meta.put("embedding_model", "text-embedding-3-small");
        meta.put("ingested_at", Instant.now().toString());
        return meta;
    }
}
幂等机制核心：由于 chunk ID 是确定性的（doc_id + chunk_index），重复执行 process() 不会产生 Duplicate 幽灵——同样的输入永远生成同样的 chunk ID，向量库中不会出现重复记录。配合元数据库中的 doc_id + content_hash 唯一约束，实现了真正的幂等入库。
05

pgvector 增量策略：确定性 ID + diff + upsert

Spring AI 的 VectorStore 抽象适合快速接入，但在生产环境中，直接操作 pgvector 可以获得更细粒度的增量控制—— 逐块 diff + upsert，只重新 embedding 内容变化的 chunk，而非整篇文档"先删后增"。

5.1 表结构与元数据设计

pgvector 是 PostgreSQL 的向量检索扩展，类比 MySQL 的全文索引插件——但专为高维向量的近似最近邻搜索（ANN）设计。HNSW（Hierarchical Navigable Small World）是 pgvector 支持的一种索引算法，类比 MySQL 的 B+ 树索引——但 B+ 树为精确查找优化，HNSW 为"找最相似的 K 个向量"优化，通过多层图结构实现近似最近邻搜索。
SQL document_chunks 表结构 + HNSW 索引 
-- pgvector 表结构设计
CREATE TABLE IF NOT EXISTS document_chunks (
    id              VARCHAR(256) PRIMARY KEY,  -- 确定性 ID: doc_id + "_chunk_" + index
    doc_id          VARCHAR(256) NOT NULL,
    content         TEXT NOT NULL,
    content_hash    VARCHAR(64) NOT NULL,      -- SHA-256 内容指纹
    version_id      INTEGER NOT NULL,          -- doc_version: 文档版本号
    is_latest       BOOLEAN DEFAULT TRUE,     -- is_latest: 是否为最新版本
    embedding       VECTOR(1536),              -- pgvector 向量类型 (1536 维)
    chunk_strategy  VARCHAR(64),              -- 分块策略标识
    embedding_model VARCHAR(128),             -- 使用的 Embedding 模型
    ingested_at     TIMESTAMP DEFAULT NOW(),  -- 入库时间
    UNIQUE(doc_id, content_hash)              -- 幂等约束：同一文档相同内容只入库一次
);

-- HNSW 索引（近似最近邻搜索专用索引）
-- 类比 MySQL B+ 树索引，但为向量相似度搜索优化
CREATE INDEX idx_chunks_embedding
ON document_chunks
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

-- 为 doc_id 建索引，支持按文档批量删除
CREATE INDEX idx_chunks_doc_id ON document_chunks (doc_id);
CREATE INDEX idx_chunks_is_latest ON document_chunks (doc_id, is_latest);

元数据字段说明

字段类型作用
doc_idVARCHAR文档唯一标识，关联元数据库
content_hashVARCHAR(64)chunk 内容的 SHA-256，用于 diff 比较
version_idINTEGERdoc_version：文档版本号，每次更新自增
is_latestBOOLEANis_latest：标记该 chunk 是否属于最新版本，用于查询时过滤
chunk_strategyVARCHAR分块策略标识，如 token-500-overlap-50
embedding_modelVARCHAR生成该向量使用的模型，用于 Drift 检测
ingested_atTIMESTAMP入库时间，用于按时间清理

5.2 逐块 diff + upsert 策略

与文档级"先删后增"不同，pgvector 直连方案可以在 chunk 级别做 diff——只重新 embedding 内容变化的 chunk，未变的 chunk 保持不动，大幅节省 Embedding API 调用成本。

⚠️ 框架无内置实现，以下为业界通用手写方案
Spring AI 的 VectorStore 抽象不暴露逐块 diff 能力。以下直接使用 pgvector SQL + JDBC 实现，是生产环境精细增量更新的标准做法。
SQL UPSERT — 幂等入库核心操作 
-- 幂等 UPSERT：存在则更新，不存在则插入
-- ON CONFLICT (doc_id, content_hash) 保证同一文档相同内容不重复入库
INSERT INTO document_chunks
    (id, doc_id, content, content_hash, version_id, is_latest,
     embedding, chunk_strategy, embedding_model)
VALUES ($1, $2, $3, $4, $5, TRUE, $6, $7, $8)
ON CONFLICT (doc_id, content_hash) DO UPDATE
SET is_latest    = TRUE,
    version_id   = EXCLUDED.version_id,
    ingested_at  = NOW();

-- 将旧版本 chunk 标记为 is_latest = FALSE（软删除，非物理删除）
UPDATE document_chunks
SET is_latest = FALSE
WHERE doc_id = $1 AND content_hash != $2;
Java 逐块 diff + upsert — 只 re-embedding 变化的 chunk 
/**
 * 逐块 diff：只重新 embedding 内容变化的 chunk
 * 节省 Embedding API 调用成本（未变的 chunk 不重新生成向量）
 */
@Repository
public class PgVectorChunkRepository {

    private final JdbcTemplate jdbc;
    private final EmbeddingModel embeddingModel;  // Spring AI 2.0

    public void incrementalUpsert(String docId, List<Chunk> newChunks) {
        // 查询旧 chunk 的 content_hash（不需要读取 embedding 向量）
        Map<String, String> oldHashes = getChunkHashes(docId);

        for (int i = 0; i < newChunks.size(); i++) {
            Chunk chunk = newChunks.get(i);
            String chunkId = docId + "_chunk_" + i;
            String newHash = ContentHashUtil.sha256(chunk.getText());

            // diff：哈希相同 → 内容未变，跳过
            if (newHash.equals(oldHashes.get(chunkId))) {
                continue;  // 节省一次 Embedding API 调用
            }

            // 内容变了 → 重新 embedding + upsert
            float[] embedding = embeddingModel.embed(chunk.getText());

            jdbc.update("""
                INSERT INTO document_chunks
                    (id, doc_id, content, content_hash, version_id,
                     is_latest, embedding, chunk_strategy, embedding_model)
                VALUES (?, ?, ?, ?, ?, TRUE, ?, ?, ?)
                ON CONFLICT (doc_id, content_hash) DO UPDATE
                SET is_latest = TRUE, ingested_at = NOW()
                """,
                chunkId, docId, chunk.getText(), newHash,
                chunk.getVersionId(), createVector(embedding),
                "token-500-overlap-50", "text-embedding-3-small");
        }

        // 删除多余的旧 chunk（新文档比旧文档短）
        deleteSurplusChunks(docId, newChunks.size());
    }
}
两种策略对比：文档级"先删后增"（Spring AI VectorStore）实现简单但浪费 API 调用——即使文档只改了一个字也会重新 embedding 全部 chunk。chunk 级"diff + upsert"（pgvector 直连）精细高效——只 re-embedding 变化的 chunk，但需要手写 SQL 和 diff 逻辑。生产环境推荐 chunk 级方案。
06

生产级保障：蓝绿部署 + 一致性 + reconciliation

增量更新管道解决了"怎么更新"的问题，但生产环境还需要解决"更新出错怎么办"、"怎么发现遗漏"、"怎么平滑切换模型"三个问题。

6.1 蓝绿索引部署 + golden-set eval

蓝绿部署（blue-green deployment）：类比应用发布时准备两套环境——蓝色为当前线上版本，绿色为新版本。绿色先在隔离环境运行验证，通过后一次性将流量切到绿色，蓝色保留用于回滚。在向量库场景下，"两套环境"变为两个索引——旧索引和新索引（re-embedding 后），通过 alias 原子切换。
golden-set eval：golden-set 是一组人工标注的"黄金测试问答对"，类比单元测试的断言——但评估的是检索质量而非代码逻辑。新索引必须通过 golden-set eval 的召回率和准确率门槛（gate），才能切流量上线。
⚠️ 框架无内置实现，以下为业界通用手写方案
Spring AI 不提供蓝绿索引切换和 golden-set eval。以下为业界标准实践。
Java BlueGreenIndexSwitcher.java — alias 原子切换 + eval gate 
@Service
public class BlueGreenIndexSwitcher {

    private final VectorStore vectorStore;
    private final GoldenSetEvaluator evaluator;

    /**
     * 切换流程：构建新索引 → golden-set eval → 通过 gate → alias 原子切换
     */
    public SwitchResult switchIndex(String newIndexName) {
        // 1. golden-set eval：用黄金测试集评估新索引检索质量
        EvalResult eval = evaluator.evaluate(newIndexName);
        if (!eval.isPass()) {
            // 未通过门槛 → 拒绝切换，保留旧索引
            return SwitchResult.rejected(
                "golden-set eval failed: recall=" + eval.getRecall()
                + " precision=" + eval.getPrecision());
        }

        // 2. alias 原子切换
        //    pgvector 不直接支持 alias，用事务 + 双写实现
        vectorStore.executeInTransaction(() -> {
            updateAlias("knowledge_base_active", newIndexName);
            scheduleOldIndexCleanup("knowledge_base_v1", 7); // 旧索引保留 7 天回滚
        });

        return SwitchResult.success(newIndexName);
    }
}

6.2 一致性保障：元数据库作为 source of truth + reconciliation 扫描

reconciliation（对账）：类比 MySQL 主从一致性校验——定期扫描比对两份数据源，发现并修复差异。在 RAG 场景下，两份数据源是"元数据库"（source of truth，记录每个文档应该有哪些 chunk）和"向量数据库"（实际存储的 chunk）。
tombstone（墓碑标记）：类比 Redis 的逻辑删除——不物理删除记录，而是打一个"已删除"标记。在向量库中，tombstone 标记 is_latest = FALSE，查询时过滤掉。物理删除延后执行，为回滚保留窗口。
⚠️ 框架无内置实现，以下为业界通用手写方案
reconciliation 扫描器是 RAG 生产系统核心运维组件，需手写实现。
Java ReconciliationScanner.java — 定期对账扫描 
/**
 * Reconciliation 对账扫描器
 * 类比 MySQL 主从一致性校验：定期比对元数据库与向量数据库
 * 发现并修复 Orphan / Stale / Missing 三类幽灵知识
 */
@Component
public class ReconciliationScanner {

    private final VectorStore vectorStore;
    private final DocumentMetadataRepository metadataRepo;
    private final ReEmbeddingQueue reEmbeddingQueue;

    /**
     * 每小时执行一次全量对账
     */
    @Scheduled(fixedDelay = 3600000)
    public void reconcile() {
        List<String> metaDocIds = metadataRepo.findAllActiveDocIds();
        List<String> vectorDocIds = getVectorDocIds();

        // 1. Orphan 检测：向量库有但元数据库无 → 物理删除
        Set<String> orphans = new HashSet<>(vectorDocIds);
        orphans.removeAll(metaDocIds);
        if (!orphans.isEmpty()) {
            vectorStore.delete(orphans.stream().toList());
            log.warn("Cleaned {} orphan embeddings", orphans.size());
        }

        // 2. Stale 检测：元数据库标记 is_latest=false 但向量库仍有
        List<String> staleDocIds = metadataRepo.findStaleDocIds();
        for (String docId : staleDocIds) {
            // 标记 tombstone（软删除标记）
            metadataRepo.markTombstone(docId);
            vectorStore.delete(getChunkIds(docId));
            log.warn("Cleaned stale embeddings for doc: {}", docId);
        }

        // 3. Missing 检测：元数据库有但向量库无 → 触发 re-embedding
        Set<String> missing = new HashSet<>(metaDocIds);
        missing.removeAll(vectorDocIds);
        for (String docId : missing) {
            reEmbeddingQueue.send(docId);
            log.warn("Found missing embeddings for doc: {}", docId);
        }
    }
}
source of truth 设计：元数据库（MySQL）记录每个文档的 doc_id、content_hash、version_id、is_latest、ingested_at——它是"文档应该有哪些向量"的权威来源。向量数据库（pgvector）是"实际有哪些向量"。reconciliation 扫描以元数据库为准，修正向量数据库的偏差。

6.3 异步入库：幂等键 + 重试 + DLQ

对于大批量文档更新，同步入库会阻塞用户请求。生产环境通常采用异步入库——文档变更事件通过消息队列投递，消费者端做幂等处理、自动重试、失败进 DLQ（Dead Letter Queue，死信队列）。

框架版本：Spring AMQP 3.x + Spring Retry — 提供开箱即用的 @RabbitListener（消息消费）、@Retryable（自动重试）、DLQ 绑定配置。管道编排逻辑为手写。
Java AsyncIngestionConsumer.java — 异步入库 + 重试 + DLQ 
/**
 * 异步入库消费者
 * 幂等键 = doc_id + content_hash（重复消费自动跳过）
 * 重试 3 次，失败后进入 DLQ 人工处理
 */
@Component
public class AsyncIngestionConsumer {

    private final IncrementalUpdatePipeline pipeline;
    private final AlertService alertService;

    // 正常队列：最多重试 3 次，指数退避
    @RabbitListener(queues = "doc.embedding.queue")
    @Retryable(maxAttempts = 3, backoff = @Backoff(delay = 2000, multiplier = 2))
    public void onDocumentEvent(DocumentEvent event) {
        // 幂等检查：doc_id + content_hash 已存在则跳过
        if (pipeline.isAlreadyIngested(event.getDocId(), event.getContentHash())) {
            return;  // 幂等：重复消息直接跳过
        }
        pipeline.process(event.toInput());
    }

    // 死信队列：重试耗尽后的兜底处理
    @RabbitListener(queues = "doc.embedding.dlq")
    public void onDlq(DocumentEvent event) {
        log.error("Ingestion failed permanently for doc: {}", event.getDocId());
        alertService.notify("DLQ Alert: " + event.getDocId());
    }
}
幂等入库的完整链路：异步入库场景下，消息可能被重复投递（至少一次语义）。幂等通过两层保障：①消费者端检查 doc_id + content_hash 是否已入库；②pgvector 表的 UNIQUE(doc_id, content_hash) 约束兜底。即使并发重复消费，数据库约束也会阻止重复插入。

面试口述要点

面试常问：RAG 知识库增量更新与一致性保障。以下是口述要点，按逻辑递进组织。
  1. 问题定义：RAG 知识库上线后文档会持续更新/删除，但向量库中的 Embedding 不会自动同步，导致"幽灵知识"——Stale（过期）、Orphan（孤儿）、Duplicate（重复）、Drift（漂移）、Contradictory（矛盾）五种问题。本质是向量库与源文档缺乏一致性保障。
  2. 变更检测方案：两阶段粗筛 + 精筛。粗筛比较 lastModified 时间戳（O(1) 磁盘操作，跳过未变文档）；精筛比较 content hash（SHA-256，内容级指纹，类比 Git commit hash）。只有时间戳变化时才计算哈希，避免全文读取开销。
  3. 更新策略：文档级"先删后增"（delete-then-add）——先按 doc_id 删除旧版本所有 chunk，再插入新版本。chunk 级"diff + upsert"——逐块比较 content_hash，只 re-embedding 内容变化的 chunk，节省 Embedding API 成本。生产环境推荐 chunk 级方案。
  4. 幂等机制：两层保障。①确定性 chunk ID = doc_id + "_chunk_" + index，保证重复入库不产生 Duplicate；②数据库 UNIQUE(doc_id, content_hash) 约束兜底，即使并发写入也不会重复插入。类比数据库的幂等键设计。
  5. 元数据设计：doc_id、content_hash、version_id（doc_version）、is_latest、chunk_strategy、embedding_model、ingested_at 七个字段全量落盘。元数据库（MySQL）作为 source of truth，向量库（pgvector）是"实际有哪些向量"。
  6. 一致性保障：reconciliation（对账）扫描器定期比对元数据库与向量数据库，修复三类幽灵：Orphan（向量库有但元数据库无 → 物理删除）、Stale（is_latest=false 但向量库仍有 → tombstone 软删除）、Missing（元数据库有但向量库无 → 触发 re-embedding）。类比 MySQL 主从一致性校验。
  7. 蓝绿索引部署：Embedding 模型升级时（Drift 幽灵），构建新索引 → golden-set eval（黄金测试集评估检索质量）→ 通过 gate 后 alias 原子切换 → 旧索引保留 N 天用于回滚。类比应用蓝绿部署，但"两套环境"变为两个向量索引。
  8. 异步入库：大批量更新走 Redis Stream / RabbitMQ，消费者端幂等键 + 自动重试（3 次指数退避）+ DLQ 兜底。保证最终一致性和可恢复性。

📝 术语表

术语 解释
content hash（内容哈希） 对文档全文计算 SHA-256 摘要，得到唯一"内容指纹"。类比 Git commit hash——内容改一个字符，哈希值完全不同。用于检测文档内容是否变更。
内容哈希 content hash 的中文翻译，指同一概念：对文本内容计算哈希摘要，作为变更检测的依据。本教程中与 content hash 互换使用。
幂等入库 重复执行入库操作不会产生副作用——同样的输入无论执行多少次，向量库中只保留一份记录。通过确定性 chunk ID + UNIQUE 约束实现。类比数据库的 INSERT ... ON DUPLICATE KEY UPDATE。
向量 upsert upsert = update + insert。对向量记录执行"存在则更新、不存在则插入"操作。pgvector 通过 ON CONFLICT ... DO UPDATE 实现，保证幂等性。
文档变更检测 判断文档内容是否发生变化的过程。本教程采用两阶段方案：粗筛（时间戳比较）+ 精筛（内容哈希比较），避免对未变文档做无谓的 re-embedding。
HNSW Hierarchical Navigable Small World，分层可导航小世界图。pgvector 支持的向量索引算法，类比 MySQL B+ 树索引——但 B+ 树为精确查找优化，HNSW 为"找最相似的 K 个向量"（近似最近邻搜索 ANN）优化，通过多层图结构实现亚线性检索。
doc_version 文档版本号（version_id），每次文档更新时自增。用于追踪文档变更历史，配合 is_latest 字段实现版本管理。类比 Git 的版本序列号。
is_latest 布尔标记，标识该 chunk 是否属于文档的最新版本。查询时只检索 is_latest = TRUE 的记录，避免检索到旧版本内容（Stale 幽灵）。类比 Redis 缓存的"有效标记"。
reconciliation 对账/一致性校验。定期扫描比对元数据库（source of truth）与向量数据库的实际状态，发现并修复 Orphan、Stale、Missing 三类不一致。类比 MySQL 主从一致性校验。
tombstone 墓碑标记。不物理删除向量记录，而是标记 is_latest = FALSE（软删除）。查询时自动过滤。物理删除延后执行，为回滚保留窗口。类比 Redis 的逻辑删除。
蓝绿部署 blue-green deployment。准备两套索引——蓝色为线上版本，绿色为新版本。绿色先隔离运行验证（golden-set eval），通过后 alias 原子切换流量。蓝色保留 N 天用于回滚。类比应用蓝绿发布。
golden-set eval 黄金测试集评估。预先准备一组人工标注的"标准问答对"（golden set），用新索引对这些问答做检索，评估召回率（recall）和准确率（precision）。未通过门槛（gate）则拒绝切换。类比单元测试的断言——但评估的是检索质量。
source of truth 权威数据源。本教程中元数据库（MySQL）是 source of truth——记录每个文档"应该"有哪些 chunk。向量数据库（pgvector）的实际状态以元数据库为准，偏差由 reconciliation 修正。
DLQ Dead Letter Queue，死信队列。消息重试耗尽后进入的兜底队列，由人工或告警系统处理。类比应用开发中的"异常处理兜底"——无法自动恢复的错误最终落到这里。
