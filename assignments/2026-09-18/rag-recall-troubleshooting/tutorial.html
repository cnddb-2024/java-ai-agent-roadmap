总预估时长：55 分钟 贯穿线任务 · 对应路线图「面试造飞机」第一梯队收官整合题
① 串联复盘 8min② 五维排查 15min③ 决策树 8min④ 分层策略与代价 10min⑤ 结果净化三层·Java 开箱 10min⑥ 面试口述稿 4min

一、为什么这是"收官整合题"（8min）

前面十几天的作业都是"点"：混合检索、Rerank（重排序）——类似 MySQL 先用索引粗筛 1000 行、再人工精挑 10 行，粗筛快但糙、精筛慢但准；切分、Embedding 选型各自练过。面试官在收官阶段不会单独问某个点，而是抛一个复合场景："你项目上线后发现用户问题答不对，你怎么排查？"这题考的不是记忆，而是把已学的点串成一条"排查-调优方法论"的能力。

这题在路线图面试体系里定位明确：牛客 2026-08 AI Agent 岗面经高频，考查 RAG 调优与失败分析能力。标准答案骨架就是两句话：先查检索层再查生成层（避免盲目换模型）；检索层内按五维顺序排查、按分层策略调优。本篇把这两句话展开成可下钻 2-3 层的口述稿。

复盘锚点：你已完成的三项实战在这里各归其位——混合检索+RRF 是"召回手段"、Rerank 是"降噪手段"、Recall@K 评测是"验证手段"。排查 = 决定先动哪个手段。

二、五维排查：先查哪、按什么顺序（15min）

五维排查是"从便宜到贵、从高频到低频"的顺序，每维对应你项目里一个已有组件：

维度典型症状排查动作对应手段与代价
1. Query 改写质量多轮对话、代词/省略问题召回想"它怎么部署"把改写前后的 query 打日志对比，看改写后是否补全了完整意图Spring AI 1.1+ 开箱 RewriteQueryTransformer（查询重写器，把口语化问题改写成利于检索的完整问句）；代价：多一次 LLM 调用，p95 延迟 +200~500ms
2. 切块粒度召回的片段"半句话"或"大杂烩"，答案被切碎抽查 bad case 对应的 chunk，看答案是否跨越切分边界调 TokenTextSplitter 的 chunkSize/overlap（已练）；代价：粒度变小→索引膨胀、检索变慢
3. Embedding 领域适配通用模型对领域术语相似度区分度差用金标问答对算 Recall@K（Recall@K = 前 K 条结果里命中正确答案的比例，类似"TOP-K 查准率"），换 bge 领域模型对比换 Embedding 模型需全量重嵌入，代价最高，放最后
4. 索引参数与过滤条件加了大类过滤后召回骤降检查 HNSW ef_search、元数据过滤条件是否过严调参零成本但收益有限；过滤条件写错是"静默灾难"（不报错但查不到）
5. 数据覆盖度问题涉及内容知识库里根本没有人工确认语料中是否存在答案源文档补数据是根治手段，但采集/清洗成本高；查不到就该拒答而不是硬答

顺序记忆口诀："改写→切块→换模型"（召回率低时），因为代价递增：改写只多一次 LLM 调用，切块要重建索引，换模型要全量重嵌入。

三、排查决策树（8min）

flowchart TD
    A[用户反馈回答错误] --> B{检索层能召回正确片段吗?}
    B -- 不能 --> C[检索层问题]
    B -- 能 --> D[生成层问题]
    C --> C1{Query 完整吗?}
    C1 -- 否 --> C2[改写: RewriteQueryTransformer]
    C1 -- 是 --> C3{答案被切碎吗?}
    C3 -- 是 --> C4[调切块粒度/overlap]
    C3 -- 否 --> C4b{相似度整体偏低?}
    C4b -- 是 --> C5[换领域 Embedding 重嵌入]
    C4b -- 否 --> C6[查过滤条件与索引参数]
    D --> D1{上下文里有答案但没引用?}
    D1 -- 是 --> D2[Prompt 约束 + 引用溯源 + Faithfulness 核查]
    D1 -- 否 --> D3[上下文被无关内容淹没 -> Rerank 限 Top-K]
Mermaid 是文本画图工具，把箭头逻辑写成代码即可渲染成流程图；-> 在 Mermaid 里写作 -> 或 --> 表示流向。

四、分层策略：三个场景各自的"组合拳"（10min）

场景信号策略顺序每步代价
召回率低Recall@5 < 0.6，正确片段不进前 5先改写 → 再切块 → 再换 Embedding改写 +1 次 LLM 调用；切块重建索引；换模型全量重嵌入（最贵）
噪声多正确片段在，但排名靠后被淹没加 Rerank 精排 + 限 Top-K（把 20 条粗筛结果精挑成 5 条）Cross-Encoder 逐对打分，p95 延迟 +100~300ms
多文档冲突两份文档说法不一致，模型随机采信按权威度 / 时间戳 / 置信度排序元数据，权威来源优先注入需在入库时维护 metadata（元数据，文档的"附加标签"，类似数据库表的冗余字段）；零推理成本

多文档冲突排序里"置信度"怎么来：混合检索中 RRF（倒数排序融合，把向量检索与 BM25 关键词检索的排名用 1/(k+rank) 加权合并）的融合分本身就是天然置信度信号，冲突时融合分高者靠前。

五、结果净化三层 + Java 开箱实现（10min）

"结果净化"指把检索原始结果变干净的三道工序，每道都有 Spring AI 开箱或低成本实现：

工序位置作用Spring AI 实现方式（版本）
元数据过滤召回前先按 doc_type / version 等条件缩小检索范围，避免检索后才发现不该进上下文SearchRequest 的 FilterExpression（Spring AI 1.0+，表达式如 version == 'v2'，已在灰度发布实战练过）
阈值过滤召回后把相似度低于阈值的"硬凑结果"丢弃，宁缺毋滥pgvector 查询带 <=> < :threshold 距离上限，或对 Rerank 分数做截断（阈值判断为业界通用做法）
多样性去重重排后相邻 chunk 内容高度重叠时只留一条，避免上下文被重复内容占满⚠️ 框架无内置 MMR（最大边际相关性）实现，业界普遍手写：按 embedding 余弦相似度对已选集合去重，只讲原理不做逐行实现

净化三层的顺序不能颠倒：过滤在召回前最省钱（少算距离）、阈值在召回后（分数才有依据）、去重在重排后（排序稳定了去重才有意义）。

Java 侧最小可运行骨架（Spring AI 1.1.x，仅展示过滤+阈值两条开箱路径）：

// 1) 元数据过滤（召回前）+ TopK，Spring AI 1.0+ 开箱
SearchRequest req = SearchRequest.builder()
        .query(rewrittenQuery)          // 来自 RewriteQueryTransformer 改写后的查询
        .topK(20)                        // 粗筛多召回一些，交给 Rerank 精挑
        .filterExpression("version == 'v2' && docType == 'manual'")
        .build();
List<Document> candidates = vectorStore.similaritySearch(req);

// 2) Rerank 精排（Spring AI 1.1+ ScoringModel + bge-reranker-v2-m3）
List<Document> ranked = scoringModel.score(query, candidates);

// 3) 阈值截断（业界通用做法：框架无统一内置开关）
List<Document> clean = ranked.stream()
        .filter(d -> d.getMetadata().getOrDefault("rerank_score", 0.0) instanceof Double s && s > 0.35)
        .limit(5)
        .toList();

面试要"结合项目真实数字"，示例复盘表（数字换成你项目的实测值）：

纯向量检索0.5280msbaseline，多义词问题召回失败
+ 混合检索（RRF）0.68110msBM25 救回关键词命中，+30ms
+ Rerank Top-50.81260ms噪声排序问题解决，+150ms（Cross-Encoder 逐对打分）
+ 改写（多轮场景）0.86510ms代词消解生效，+250ms（多一次 LLM 调用）
口述模板（60 秒版）："召回问题我先按'先检索层后生成层'归因，检索层内按五维顺序排查：改写质量、切块粒度、Embedding 适配、索引与过滤、数据覆盖度，原则是代价递增才往后走。我们项目 Recall@5 从 0.52 提到 0.86，用了混合检索 + Rerank + 改写三级，代价是 p95 从 80ms 涨到 510ms，其中改写那 250ms 我们评估过用小模型专用改写来压。如果五维都查过仍召回不到，那大概率是数据覆盖度问题，正确姿势是拒答而不是让模型硬编。"

📝 术语表（本篇解释过的非白名单术语）

  • Rerank（重排序）：类似 MySQL 索引粗筛 1000 行再人工精挑 10 行；Cross-Encoder 逐对打分准但慢。
  • Recall@K：前 K 条检索结果中命中正确答案的比例，衡量"该找到的有没有找到"。
  • RewriteQueryTransformer：Spring AI 1.1+ 开箱的查询重写器，把口语化/带代词的问题改写成利于检索的完整问句。
  • metadata（元数据）：文档入库时附带的标签字段（类型/版本/时间戳），类似表的冗余列，用于召回前过滤。
  • RRF（倒数排序融合）：用 1/(k+rank) 把多路检索排名合并为一个分数，天然表达"各路一致认可"的置信度。
  • MMR（最大边际相关性）：去重策略——既要与问题相关，又要与已选结果不重复；Spring AI 无内置，业界手写。
