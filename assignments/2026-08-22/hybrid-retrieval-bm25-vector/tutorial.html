混合检索实战：向量检索 + BM25 关键词检索融合（Spring AI + Elasticsearch/PGVector）

总预估时长：约 60 分钟（互补原理 10min / BM25 与 RRF 公式 12min / PGVector 双通道实现 20min / Spring AI 与 LangChain4j 路径 10min / 面试串联 8min）· 主线 Java（Spring AI + LangChain4j 双路径），Python 仅辅助

一、为什么纯向量检索不够（10min）

稠密向量检索擅长"语义匹配"——"怎么省钱"能召回"成本优化方案"。但它有三种典型翻车场景：

  • 精确实体：查"K8s 节点 node-abc-123 的告警"，向量把注意力分散到语义，型号/主机名这类精确 token 反而排不上来。
  • 版本号与代码标识符：查"Spring Boot 3.4 的 bug CVE-2025-22233"，向量检索对数字串几乎无感，BM25 一发命中。
  • 低频专有名词：企业内部黑话、产品代号在训练语料里没出现过，向量空间里没有良好表征。

BM25 这类稀疏关键词检索恰好互补：它是精确词项匹配（TF-IDF 家族），对实体、版本号、代号零失误，但对同义改写无能为力。两者融合 = 语义泛化能力 + 精确匹配能力，这就是混合检索被称为 RAG 检索优化"黄金组合前半段"的原因（后半段是 Rerank，见后续任务）。

面试一句话版本：稠密检索解决"意思相近"，稀疏检索解决"字面一致"，RRF 把两路排名融合成一个统一排序，互为兜底。

二、BM25 与 RRF 融合公式（12min）

2.1 BM25 三要素

BM25 打分由三部分构成：词频饱和（TF 越高得分越高但增量递减，避免一个词重复刷分）、逆文档频率 IDF（越稀有的词越重要）、文档长度归一化（长文档不因词多而占便宜）。相比原始 TF-IDF，它对"长文档偏置"和"高频词刷分"做了修正，是 30 年来最难被替代的经典算法。

2.2 RRF（Reciprocal Rank Fusion）

两路检索的分数量纲完全不同（余弦相似度 0~1，BM25 可以到几十），直接加权需要先归一化，容易踩坑。RRF 的思路是只看排名不看分数：

score(d) = SUM over r in R of 1 / (k + rank_r(d))     // k 默认 60

某文档在向量检索排第 1（贡献 1/61）、在 BM25 排第 3（贡献 1/63），总分约 0.0323；一个只在单路排第 1 的文档只有 0.0164。两路都靠前的文档天然胜出，且对异常分数完全免疫。k=60 是 Elastic、Azure AI Search 等各家实践沉淀的默认值——它让第 1 名和第 60 名贡献差距约 61 倍，头部权重高但中段不至于清零。

RRF 优点：免归一化、免调权、对分数分布鲁棒。缺点：丢弃了分数信息，两路置信度差异无法表达——如果需要精细加权，用加权归一化（Linear fusion），生产首选仍是 RRF 起步。

三、PGVector + tsvector 单库双通道实现（20min）

PostgreSQL 一个库就能做混合检索：pgvector 负责 HNSW 向量近邻，tsvector + GIN 索引负责全文检索。建表：

CREATE TABLE docs (
    id BIGSERIAL PRIMARY KEY,
    content TEXT,
    content_tsv TSVECTOR,          -- 全文检索列
    embedding VECTOR(1024)         -- bge-large-zh 维度
);
CREATE INDEX idx_docs_tsv ON docs USING GIN (content_tsv);
CREATE INDEX idx_docs_vec ON docs USING hnsw (embedding VECTOR_COSINE_OPERATORS);

入库时同步写入两列（Java 侧用 Spring JDBC / MyBatis 均可）：

-- to_tsvector 需选对中文分词配置：simple 或 zhparser/jieba 扩展
INSERT INTO docs (content, content_tsv, embedding)
VALUES (
    'Spring Boot 3.4 升级注意事项',
    to_tsvector('simple', 'Spring Boot 3.4 升级注意事项'),
    '[0.12, -0.35, ...]'::vector
);

检索时一条 SQL 完成"双路召回 + RRF 融合"，这是混合检索最优雅的单库实现：

WITH vec AS (                       -- 向量通道：取 Top 20
    SELECT id, ROW_NUMBER() OVER (ORDER BY embedding <=> :query_vec) AS rank
    FROM docs
    ORDER BY embedding <=> :query_vec
    LIMIT 20
),
bm25 AS (                           -- 关键词通道：取 Top 20
    SELECT id, ROW_NUMBER() OVER (ORDER BY ts_rank_cd(content_tsv, query) DESC) AS rank
    FROM docs, plainto_tsquery('simple', :query_text) AS query
    WHERE content_tsv @@ query
    ORDER BY rank
    LIMIT 20
)
SELECT d.id, d.content,
       COALESCE(1.0 / (60 + vec.rank), 0) +
       COALESCE(1.0 / (60 + bm25.rank), 0) AS rrf_score
FROM vec
FULL OUTER JOIN bm25 ON vec.id = bm25.id
JOIN docs d ON d.id = COALESCE(vec.id, bm25.id)
ORDER BY rrf_score DESC
LIMIT 10;
中文分词坑：PG 原生 tsvector 对中文按字切分效果差，生产要么装 zhparser/jieba 扩展，要么在 Java 侧分好词再拼 tsquery。这是"PG 单库方案"最大的工程代价，也是很多人转向 Elasticsearch 的原因。

四、Spring AI 与 LangChain4j 融合路径（10min）

4.1 Spring AI：RetrievalAugmentationAdvisor

Spring AI 1.x 的 RAG 模块把检索抽象为 Retriever + PostProcessor 管道，多路检索结果可以自定义融合：

// 向量通道
DocumentRetriever vectorRetriever = VectorStoreDocumentRetriever.builder()
        .vectorStore(vectorStore)
        .similarityThreshold(0.6)
        .topK(20)
        .build();

// 混合检索 Advisor：检索后接自定义 RRF 后处理器
RetrievalAugmentationAdvisor advisor = RetrievalAugmentationAdvisor.builder()
        .documentRetriever(vectorRetriever)
        .documentPostProcessor(documents -> rrfMerge(documents, bm25Top20(query)))
        .build();

String answer = chatClient.prompt()
        .advisors(advisor)
        .user(query)
        .call()
        .content();

4.2 LangChain4j：ContentRetriever + ContentAggregator

LangChain4j 原生为多路检索设计了 ContentAggregator（聚合多路内容并统一重排），官方还提供 RelevanceScoreAggregator，与 RRF 思路同构：

ContentRetriever vectorRetriever = EmbeddingStoreContentRetriever.builder()
        .embeddingStore(embeddingStore)
        .embeddingModel(embeddingModel)
        .maxResults(20)
        .build();

RetrievalAugmentor augmentor = DefaultRetrievalAugmentor.builder()
        .queryRouter(new DefaultQueryRouter(vectorRetriever, bm25Retriever))
        .contentAggregator(new RelevanceScoreAggregator())  // 多路融合
        .contentInjector(new DefaultContentInjector())
        .build();

4.3 Elasticsearch 声明式 RRF

如果向量库选 ES，RRF 直接内置为 retriever，无需手写融合逻辑：

GET /docs/_search
{
  "retriever": {
    "rrf": {
      "retrievers": [
        { "standard": { "query": { "match": { "content": "混合检索" } } } },
        { "knn": { "field": "embedding", "query_vector": [0.12, ...], "k": 20, "num_candidates": 100 } }
      ],
      "rank_constant": 60,
      "rank_window_size": 20
    }
  }
}

五、面试串联与验收（8min）

5.1 第一梯队考点：「混合检索 + Rerank 原理」

  • 为什么互补：稠密向量覆盖语义泛化，BM25 覆盖字面精确匹配；单路召回率天花板明显，融合后 Recall@5 普遍能提升 20 个百分点以上（你的评测任务要用真实数字验证这句话）。
  • RRF 公式手写：score(d) = Σ 1/(k + rank_r(d))，强调"只看排名不看分"，规避两路分数归一化难题。
  • 与 Rerank 的分工：混合检索负责"召回全"（多路粗排，Top 20-50），Rerank（Cross-Encoder 精排）负责"排得准"（Top 5-10 进上下文）——这是黄金组合的完整逻辑链。
  • 量化话术（路线图验收标准原话）："混合检索（向量+BM25）使 Recall@5 从 62% 提升至 89%"——今天写的 SQL 就是你评测报告的实验基座。

5.2 动手验收清单

  1. 建好 docs 双列表 + 双索引，灌入 20 条以上中文文档。
  2. 跑通 RRF 融合 SQL，用一个含精确标识符的查询（如版本号/代号）对比纯向量结果与混合结果差异。
  3. 把 k 从 60 改成 10/200 各跑一遍，观察头部排名稳定性，记录进技术决策日志。
  4. （进阶）用 LangChain4j ContentAggregator 复刻同一实验，与 SQL 版对比结果一致性。
