技术决策日志 #02：Rerank 方案选型 Cohere API vs 本地 bge-reranker（成本/延迟/质量三权衡）

总预估时长：约 45 分钟（决策框架 8min / 数据收集与对比表 12min / 决策矩阵与结论 10min / Java 侧接入方式 8min / 面试口述练习 7min）。主线 Java（Spring AI 1.1.x + LangChain4j 1.x），Python 仅辅助验证。

一、决策框架：先定评估维度，再看方案（8min）

你已经完成 Rerank 重排序实战（Cohere / bge-reranker 都接过了）和 RAG 评测实战（有 MRR@10 等指标）。今天的任务不是学新技术，而是把"选哪个"落成一份可追溯、可复盘、可面试复述的决策日志——这是路线图贯穿线"每个技术选型记为什么选它/放弃了什么/代价是什么"的第二次实战。

ADR（Architecture Decision Record，架构决策记录）复盘：一份一页纸的文档，结构为 背景 → 决策 → 理由 → 放弃的方案 → 撤销条件。两个模板流派：

模板适用本决策该用哪个
Simple（轻量）结论明确、权衡少✅ 本决策：两方案、三个维度，一页讲清
MADR 4.0（结构化）多选项、难逆转、跨团队留给未来"MCP vs Function Call"这类多方案权衡
先定维度再找数据：生产级选型的顺序是——先写下评估维度（质量/延迟/成本/合规/运维），再去每个维度找数据。反过来"先有结论再凑数据"是面试官一眼能看穿的减分项。本决策的五个维度，数据来源全部可追溯。

二、数据收集：三维度实测对比（12min）

Cross-Encoder（交叉编码器）召回一下：Rerank 用的模型把"问题+文档片段"拼在一起整体打分，精度高但慢——这正是两个方案都要付的"精排税"，选型之争本质是这笔税交给谁（云端 API vs 本地算力）。

2.1 质量维度（金标集 MRR@10）

社区在中文知识库场景的实测数据（Dify 环境脱敏实测）：

方案MRR@10说明
BGE-Reranker-v2-M3（本地）0.721开源、中文优化、可自托管
Cohere Rerank v3（API）0.749闭源商业 API，多语言强
Jina Reranker v2（API）0.698长文本敏感场景

质量差 3.9 个百分点——是"可感知但非碾压"的差距，不足以单独决定，进入下两个维度。

2.2 延迟维度（每查询）

方案延迟波动来源
BGE-Reranker-v2-M3（CPU/本地）~86ms批大小、序列长度
Cohere Rerank（API）~215ms网络往返 + 排队
Cohere Rerank 4 Pro（API）~614ms更强模型，长文档场景

本地方案延迟约 2.5 倍优势且无网络抖动尾部——对内网 P95 SLA 友好。你的项目 P95 延迟预算（评测报告里写的 680ms 全链路）里，Rerank 占比必须可控。

2.3 成本维度（规模敏感）

成本红线（Cost Threshold）概念：选型前先算"日查询量 × 单次成本"到多少时方案优劣反转。Cohere 按检索 token 计费（商业计价约 $2.00/1k searches 量级），bge 自托管近乎零边际成本但要付 3.2GB 显存/内存常驻。按个人项目与中小团队日万级查询估算：

月成本对比（按 1 万查询/日估算）
Cohere API:   10000 × 30 × $0.002 ≈ $600/月，随量线性增长
bge 本地:     一台 4GB 内存节点，摊销后 ≈ 固定 $30-50/月
反转点:      日查询量低于 ~500 时，API 免运维优势大于成本差

三、决策矩阵与结论（10min）

五个维度汇总（质量/延迟/成本/合规/运维），用加权打分（权重按你项目上下文定：内网部署 + 成本敏感 + 个人运维）：

维度权重Cohere API本地 bge-reranker胜者
质量（MRR@10）30%0.7490.721（差 3.9pt）Cohere（微弱）
延迟（P95）25%215ms+网络尾部86ms 无外网抖动bge
成本（万级 QD）20%线性增长 ~$600/月固定 ~$40/月bge
合规（数据出域）15%文档内容发往第三方全内网闭环bge
运维负担10%零运维模型更新/显存管理自理Cohere
加权总分—3.554.05bge-reranker

结论：选本地 bge-reranker-v2-m3，放弃 Cohere API。代价明确：占 ~3GB 内存、模型迭代要自己跟、质量让出 3.9 个 MRR 点。撤销条件：若日查询量跌回百级、或延迟预算放宽至 500ms+、或企业采购了 Cohere 企业协议，则重评。

口述模板（面试直接用）："Rerank 选型我做过完整决策：质量上 Cohere 高 3.9 个 MRR 点，但本地 bge 在延迟（86ms vs 215ms，且无网络尾部）、成本（固定 vs 线性）、合规（数据不出域）三项占优，加权后选本地。代价是 3GB 内存和自运维，撤销条件写进了 ADR。"——这就是"讲清 why"的完整弹药。

四、Java 侧接入方式（8min）

4.1 Spring AI 路径（开箱优先）

Spring AI 1.1.x 提供开箱的 Rerank 体系（你 08-23 教程已学过 ScoringModel / ReRankingContentAggregator），本地 bge 接入走 ONNX Runtime 或自建 scoring 服务：

// Spring AI 1.1.x：ReRankingContentAggregator 装配（开箱组件）
@Bean
public ContentAggregator reRankingAggregator(ScoringModel scoringModel) {
    // QueryTransformer 改写 + ScoringModel 精排，参数 maxCandidates 控制延迟
    return new ReRankingContentAggregator(
            scoringModel, 20, ReRankingContentAggregator.DEFAULT_LIMIT
    );
}
// ScoringModel 实现：自部署 bge-reranker HTTP 服务（如 TEI/Xinference 起）
// 路线图参考项目 springai-knowledge-server 即用 bge-reranker-v2-m3 + bge-large-zh 全链路

4.2 LangChain4j 路径（对比参照）

LangChain4j 1.x 的 ScoringModel 抽象同样支持自托管端点（community 模块含 Cohere 与 Xinference 集成），写法类似 Spring AI——两框架在这一层都是"接口 + 端点适配"，印证 ADR 结论与框架无关：

// LangChain4j 1.x：本地端点 ScoringModel（示意）
ScoringModel localBge = XinferenceScoringModel.builder()
        .baseUrl("http://localhost:9997")   // 本地 bge-reranker 服务
        .modelName("bge-reranker-v2-m3")
        .build();
// score 后取 Top-K 注入 ContextAggregator，与 Spring AI 用法同构

ADR 正文里建议附一段 20 行以内的最小验证代码（两框架各一段），证明决策在两条主线路径都可行——这是 Java 工程师决策日志的差异化细节。

五、面试口述练习（7min）

  • 第一问"为什么不用 Cohere？"（预设追问）：不是"贵"一个字，而是三维度数据 + 加权矩阵 + 撤销条件的完整链路；
  • 第二问"bge 质量差 3.9 个点你不在乎？"（下钻）：答"质量差距在金标集 MRR 上 4 个点，但我的延迟预算里 Rerank 只能占 ~100ms，网络尾部抖动会直接打穿 P95——用可量化的预算逻辑回应"；
  • 第三问"什么情况下你改主意？"（开放）：直接背撤销条件：量跌回百级 / 预算放宽 / 企业协议——展示"决策可逆且条件化"的工程思维。
