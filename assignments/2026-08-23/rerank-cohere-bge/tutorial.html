Rerank 重排序实战：Cohere Rerank / bge-reranker 接入 + 召回排序优化与延迟代价评估

总预估时长：约 60 分钟（原理定位 10min / 方案对比 12min / LangChain4j 实战 20min / Spring AI 路径 8min / 延迟评估与面试要点 10min）。主线 Java（LangChain4j 优先 + Spring AI 辅助），Python 仅辅助验证。

一、Rerank 在 RAG 链路中的位置（10min）

你的混合检索（向量 + BM25 融合）已经把候选片段召回出来了，但召回结果只是"粗排"——它快，但分不清候选片段之间谁更相关。Rerank 重排序（类似 MySQL 先用索引粗筛出 100 行，再人工精挑 10 行——粗筛快但糙，精筛慢但准）就是在检索之后、喂给大模型之前，加一道精排关卡：用一个更强的模型对每个候选片段与 query 逐一深度比对，重新打分排序，只把最相关的 topN 送进上下文。

两阶段检索的标准流水线（图中三个新词先说人话：Bi-Encoder 双编码器 = query 和文档各自独立编码成向量再比对，快、用于粗排；Cross-Encoder 交叉编码器 = query 和文档拼在一起深度比对打分，准、用于精排；上下文组装 = 精排后把片段拼装成最终 Prompt 的环节，正是你今天的主线任务）：

用户 Query
   │
   ▼
第一阶段：粗排召回（Bi-Encoder 向量检索 + BM25，RRF 融合）── 取 top 50
   │
   ▼
第二阶段：Rerank 精排（Cross-Encoder 逐对深度打分）── 取 top 5
   │
   ▼
上下文组装 → LLM 生成回答

为什么要这么设计？因为粗排与精排的算力代价差一个数量级：粗排是向量内积，毫秒级扫完百万级片段；精排要逐对跑一个几百 M 参数的模型，只能对 top50 做精挑。这个"漏斗"和你写 SQL 时"索引范围扫描 → 回表精查"是同一个思路。

二、原理：Bi-Encoder vs Cross-Encoder（10min）

Bi-Encoder（双编码器）：query 和文档各自独立编码成向量，再用余弦相似度比对——像 Redis 里两把 key 各自 hash 后比对槽位，快、可预先建索引，但两段文本从没"见过面"，损失交互细节。

Cross-Encoder（交叉编码器）：把 query 和文档拼接成一对同时送进模型，直接输出相关性分数——好比把"面试题和简历"放在一起让面试官综合比对，而不是分别打分再凑对。精度高得多，但每对都要跑一次完整前向计算，无法预建索引，只能在线逐对算。

维度Bi-Encoder（Embedding 检索）Cross-Encoder（Rerank 精排）
输入方式query / 文档各自编码query + 文档拼接后一起编码
精度中等（语义压缩有损）高（逐 token 交互）
速度毫秒级，可 ANN 索引逐对推理，50~100 对/秒（单卡 A100）
能否离线预计算文档向量可离线入库不能，必须在线算
适合位置第一阶段粗排第二阶段精排
黄金组合（第一梯队面试题「混合检索 + Rerank 原理」的核心答案）：稠密向量管语义泛化、BM25 管关键词精确命中、RRF 融合两者排名，再用 Cross-Encoder 精排兜住精度——四者各司其职，这就是面试官想听的"为什么是黄金组合"。

三、方案对比：Cohere Rerank API vs 本地 bge-reranker-v2-m3（12min）

Java 侧可选的 Rerank 方案主要两条路：Cohere Rerank 云 API（商用多语言模型 rerank-multilingual-v3.0）与本地部署 BAAI/bge-reranker-v2-m3（568M 参数的多语言 Cross-Encoder，基于 XLM-RoBERTa-Large，中文社区验证充分）。

维度Cohere Rerank API本地 bge-reranker-v2-m3
效果商用闭源模型，多语言强开源 568M，多语言，中文效果口碑好
延迟网络 RTT + 推理，约 100~300ms本地推理：GPU 约 50~100 对/秒；CPU 明显变慢
成本按量计费（每次调用收费）无按次费用，但有 GPU/服务器固定成本
数据合规数据需出境到第三方数据不出内网（企业知识库刚需）
部署复杂度零部署，拿 API Key 即用需 ONNX / Docker / 推理服务自建
演进方向依赖厂商版本可换 v2-gemma（2.51B）等更大模型，或量化压缩

选型建议（对照你的技术决策日志习惯）：个人项目 / 原型验证用 Cohere API（零部署快速见效）；企业知识库生产环境优先本地 bge-reranker-v2-m3（数据不出内网 + 成本可控），这正好呼应 Phase 1 验收标准里"rerank 延迟代价"的讲法。

四、LangChain4j 实战：ScoringModel + ReRankingContentAggregator（20min）

LangChain4j 对 Rerank 的抽象非常干净：ScoringModel（评分模型——框架里专职给「query + 文档」对打相关性分数的组件，类比 Spring 的 HandlerAdapter，专职适配一层）负责打分，ReRankingContentAggregator（内容聚合器——把多路召回结果汇聚、按分数重排淘汰的管道组件）负责排序淘汰。官方已提供 Cohere、Jina、Voyage 等云实现与本地 ONNX 实现。

4.1 云 API 路径：CohereScoringModel

<!-- pom.xml -->
<dependency>
    <groupId>dev.langchain4j</groupId>
    <artifactId>langchain4j-cohere</artifactId>
    <version>1.0.1-beta6</version>
</dependency>
// 1. 配置评分模型（Cohere 多语言 rerank）
ScoringModel scoringModel = CohereScoringModel.builder()
    .apiKey(System.getenv("COHERE_API_KEY"))
    .modelName("rerank-multilingual-v3.0")
    .build();

// 2. 重排序聚合器：精排 + 低分淘汰
ContentAggregator contentAggregator = ReRankingContentAggregator.builder()
    .scoringModel(scoringModel)
    .minScore(0.8)   // 相关性低于 0.8 的片段直接淘汰，防止噪声进上下文
    .build();

// 3. 组装两阶段检索增强器
RetrievalAugmentor retrievalAugmentor = DefaultRetrievalAugmentor.builder()
    .contentRetriever(contentRetriever)    // 第一阶段：向量/BM25 粗排 top50
    .contentAggregator(contentAggregator)  // 第二阶段：Cross-Encoder 精排
    .build();

// 4. 挂到 AiService（你熟悉的 LangChain4j 高层 API）
Assistant assistant = AiServices.builder(Assistant.class)
    .chatLanguageModel(model)
    .retrievalAugmentor(retrievalAugmentor)
    .build();

4.2 本地路径：BgeScoringModel（ONNX 进程内推理）

不想出境数据时，用 langchain4j-embeddings-bge-small-zh 同族的本地评分方案，或直接把 bge-reranker-v2-m3 导出为 ONNX 在 JVM 进程内跑（ONNX Runtime：跨平台机器学习推理引擎，类比把 Python 模型"编译"成 Java 可直接调用的本地库）：

ScoringModel scoringModel = new BgeScoringModel(
    Paths.get("bge-reranker-v2-m3.onnx"),   // 模型文件
    Paths.get("tokenizer.json")             // 分词器
);

// 其余组装代码与 4.1 完全一致，只换 scoringModel 实现类
ContentAggregator aggregator = ReRankingContentAggregator.builder()
    .scoringModel(scoringModel)
    .maxResultsToEmbed(50)  // 最多送 50 对进精排，控制算力
    .build();

4.3 自建推理服务路径（生产推荐）

也可以把 bge-reranker-v2-m3 用 Python（FastAPI/TEI）包一层 HTTP 服务，Java 侧用 RestClient 调——硅基流动等平台已直接提供该模型的 /rerank 端点，接口形态如下：

@Service
public class RerankService {

    private final RestClient restClient = RestClient.builder()
        .baseUrl("https://api.siliconflow.cn/v1")
        .defaultHeader("Authorization", "Bearer " + System.getenv("SF_API_KEY"))
        .build();

    /**
     * 对候选文档重排序，返回按相关性降序的 (index, score)
     */
    public List<RerankResult> rerank(String query, List<String> documents, int topN) {
        Map<String, Object> body = Map.of(
            "model", "BAAI/bge-reranker-v2-m3",
            "query", query,
            "documents", documents,
            "top_n", topN,
            "return_documents", false
        );
        RerankResponse resp = restClient.post()
            .uri("/rerank")
            .contentType(MediaType.APPLICATION_JSON)
            .body(body)
            .retrieve()
            .body(RerankResponse.class);

        // resp.results(): [{index: 3, relevance_score: 0.97}, {index: 0, ...}]
        return resp.results().stream()
            .sorted(Comparator.comparingDouble(RerankResult::relevanceScore).reversed())
            .toList();
    }
}

注意 relevance_score（相关性分数——Cross-Encoder 输出的 0~1 相关性概率，类似搜索引擎对每条结果的打分）的语义：分数不是绝对阈值，分布随 query 变化，所以生产上更稳妥的做法是"按分数排序取 topN + 极低分兜底过滤"双保险。

五、Spring AI 路径：在 Advisor 管道里插入精排（8min）

Spring AI 1.x 尚未内置独立 Rerank 抽象，推荐做法是在 RetrievalAugmentationAdvisor 的管道前后自定义一个精排 Advisor（你已掌握 Advisor 机制，这里就是把日志拦截换成重排序拦截）：

public class RerankAdvisor implements CallAdvisor<ChatResponse> {

    private final RerankService rerankService; // 第四节封装的服务

    @Override
    public ChatResponse adviseCall(ChatClient.ChatClientRequestSpec request,
                                    CallAdvisorChain chain) {
        // 1. 从 Advisor 上下文取出检索到的文档
        // 2. 调 rerankService.rerank(query, contents, topN=5)
        // 3. 只保留高分片段重写 userMessage 后放行
        return chain.nextCall(request);
    }

    @Override
    public String getName() { return "RerankAdvisor"; }
}
对比记忆：LangChain4j 把 Rerank 做成了声明式管道组件（ScoringModel + ContentAggregator 一行换实现），Spring AI 需要你手写 Advisor 织入——这也是"灵活工具箱 vs 企业基础设施"框架定位差异的又一个例证，面试聊双框架选型时可以顺手带出来。

六、延迟代价评估与优化（10min）

Phase 1 验收标准明确要求你能讲清"rerank 延迟代价"。给出一组可直接引用的量化口径（单卡 A100 参考）：

环节典型耗时说明
向量粗排 top5010~50msANN 索引检索
bge-reranker-v2-m3 精排 50 对500ms~1s50~100 对/秒
Cohere API 精排 50 对100~300ms含网络 RTT
LLM 生成1~3s流式首 token 前

四个压延迟手段（面试加分点）：

  • 截断候选数：粗排只取 top30~50 进精排，不要把 200 条全塞进去；
  • 并行打分：50 对拆批并行提交（CompletableFuture 分组），GPU 利用率拉满；
  • 高频 query 缓存：rerank 结果按 (query, docIds) 哈希缓存进 Redis，热点问题命中率可观；
  • 降级开关：精排超时（如 P99 超 800ms）自动降级用粗排顺序，保可用性——这就是你日志里"放弃了什么/代价是什么"的素材。

七、面试要点速记

  • 第一梯队「混合检索 + Rerank 原理」：稠密/稀疏互补 + RRF 融合（1/(k+rank) 只看排名不看分）+ Cross-Encoder 精排 + 为何是黄金组合；
  • 追问"为什么不用 Cross-Encoder 直接检索"：无法离线建索引，百万文档在线逐对算不可行——两阶段是必然；
  • 追问"rerank 值不值"：用你自己的评测数字回答（明天 RAG 评测任务产出 Recall@5 前后对比）；
  • 追问"生产怎么选 Cohere vs 本地"：数据合规 + 成本结构 + 延迟 SLO 三角权衡，引你的技术决策日志 #02。

📝 术语表

  • Rerank（重排序）：检索后用更强模型对候选片段重新打分排序的精排环节，类比"索引粗筛 100 行 → 人工精挑 10 行"。
  • Bi-Encoder（双编码器）：query 与文档各自独立编码成向量再比对相似度，快但损失交互细节，用于粗排。
  • Cross-Encoder（交叉编码器）：query 与文档拼接后一起送入模型直接输出相关性分数，精度高但只能在线逐对算，用于精排。
  • ScoringModel（评分模型）：LangChain4j 中专职给「query + 文档」对打相关性分数的组件抽象，类比 Spring 的 HandlerAdapter。
  • ReRankingContentAggregator（重排序内容聚合器）：LangChain4j 管道中汇聚多路召回、按评分重排并淘汰低分片段的组件。
  • relevance_score（相关性分数）：Cross-Encoder 输出的 0~1 相关性概率，随 query 分布变化，生产上按排序 + 兜底阈值双保险使用。
  • ONNX Runtime：跨平台机器学习推理引擎，把训练好的模型转成 ONNX 格式后可在 JVM 进程内直接推理。
