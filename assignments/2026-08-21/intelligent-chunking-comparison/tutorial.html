总预估时长：约 60 分钟（原理 10min / 三种策略实现 25min / 对比实验 15min / 面试串联 10min）· 主线 Java（LangChain4j + Spring AI 双路径），Python 仅辅助

一、切分为什么决定 RAG 上限（10min）

检索的最小单元是 chunk 而不是文档：chunk 太大，向量语义被稀释、命中精度下降；chunk 太小，上下文碎片化、回答缺依据。经验区间是 256-512 token 为甜点区，overlap 取 chunk_size 的 10%-20%（LangChain4j 社区基准与多个 2026 年测评均指向该区间）。切分策略的演进逻辑只有一条主线：从"按长度切"到"按语义结构切"。

二、三种策略的 Java 实现（25min）

策略一：TokenTextSplitter（Spring AI）

Spring AI 的 TokenTextSplitter 使用 CL100K_BASE 编码按 token 数切分，是 ETL 管道里的默认组件：

import org.springframework.ai.transformer.splitter.TokenTextSplitter;
import org.springframework.ai.document.Document;

TokenTextSplitter splitter = TokenTextSplitter.builder()
        .withDefaultChunkSize(400)       // 每个 chunk 的 token 上限
        .withMinChunkSizeChars(120)      // 最小字符数，防碎块
        .withMinChunkSizeToEmbed(30)
        .withKeepSeparator(true)
        .build();

List<Document> chunks = splitter.apply(List.of(document));

它的问题：不懂结构，会把句子、列表、代码块从中间切断。俄罗斯 Raiffeisenbank 的 JVM RAG 实践就记录了这个坑——默认配置很快遇到"表格被腰斩"的质量问题，这正是要引入递归切分的原因。

策略二：递归字符切分（LangChain4j DocumentSplitters）

递归切分是 LangChain 系的默认策略，也是生产环境约 80% 场景的选择：按分隔符层级递归（段落 → 行 → 空格 → 字符），尽可能保住语义单元的完整性。LangChain4j 对应实现：

import dev.langchain4j.data.document.DocumentSplitter;
import dev.langchain4j.data.document.splitter.DocumentSplitters;
import dev.langchain4j.model.embedding.Tokenizer;

DocumentSplitter splitter = DocumentSplitters.recursive(
        512,   // chunk_size：甜点区间上限
        64,    // overlap：约 12%
        tokenizer
);

List<TextSegment> segments = splitter.split(document);

策略三：按标题多粒度切分（自实现）

对 Markdown 语料，标题层级是天然切分锚点：H2/H3 内聚成块、标题路径写入元数据，检索命中后可回溯上下文。Spring AI 没有现成的 MarkdownHeaderTextSplitter，自己实现核心逻辑只需 30 行：

public List<Document> splitByHeadings(String markdown, String source) {
    List<Document> result = new ArrayList<>();
    Deque<String> headingStack = new ArrayDeque<>();
    StringBuilder current = new StringBuilder();

    for (String line : markdown.split("\n", -1)) {
        Matcher m = Pattern.compile("^(#{1,4})\\s+(.*)$").matcher(line);
        if (m.matches()) {
            if (current.length() > 0) {
                result.add(new Document(current.toString(),
                        Map.of("source", source, "headings", String.join(" > ", headingStack))));
                current = new StringBuilder();
            }
            int level = m.group(1).length();
            while (headingStack.size() >= level) headingStack.pollLast();
            headingStack.offerLast(m.group(2));
        }
        current.append(line).append("\n");
    }
    if (current.length() > 0) {
        result.add(new Document(current.toString(),
                Map.of("source", source, "headings", String.join(" > ", headingStack))));
    }
    return result;
}
多粒度的真正含义：标题块太大时（>512 token）在其内部再跑一次递归切分，并让父块元数据（标题路径）跟随子块——检索命中子块，展示带上下文，这是"小块检索、大块生成"（small-to-big）思想的雏形。路线图推荐项目 springai-knowledge-server 提供了分块策略在线热调整的生产级参照。

三、对比实验设计（15min）

三种策略必须用同一份语料 + 同一批问题跑对比，否则结论不可信。最小实验设计：

策略参数观察指标预期结果
TokenTextSplitterchunk=400Recall@5 / 断句破坏率基线，表格/列表易被切断

四、面试串联（10min）

第一梯队面试题「RAG 完整链路 + Chunking」的切分环节标准答法：

  • 翻车点：固定长度切分把表格一行劈成两个 chunk，检索命中半行，回答必然残缺。
  • 原理：递归切分按语义边界（段落→句子→词）层级回退；多粒度切分让结构与检索粒度解耦（small-to-big）。
  • 数据：报出你自己实验的 Recall@5 变化，如"递归切分 + overlap 让 Recall@5 从 62% 提到 74%"——有数字的答案才能过第一梯队。
