一、先立选型框架，再看数据（10min）

向量库选型最常见的翻车方式是"看 benchmark 焦虑"——论文里 QPS 最高的那个未必适合你。Java 背景转 AI Agent 的工程师选型，先固定五个维度再谈优劣：

  • 规模：企业知识库多为 10 万~500 万向量级，不是亿级互联网场景。
  • 运维成本：多引入一个独立组件 = 多一个故障域 + 备份恢复 + 监控告警。
  • 混合检索：RAG 刚需闭环要求向量 + 关键词（BM25/tsvector）融合，谁能一条 SQL/一次 API 搞定。
  • 事务一致性：元数据与向量同库才能同事务写入，异库必有最终一致窗口。
  • 团队栈：会 PostgreSQL 的团队用 pgvector 的边际学习成本接近零。

数据要点解读：2026 年 arXiv 的系统性实证评测显示，Qdrant 在完整数据库中延迟最优（中位 4.55ms）、Weaviate 开箱召回最高；51CTO 的中文实测里 Milvus+GPU 极致性能但 pgvector 在中小规模完全够用；dev.to 的 2026 对比则点破关键——pgvector 在百万向量以下没问题，超过百万且无专用 ANN 索引时差距才明显拉开。而企业知识库 RAG 的典型规模恰好在安全区内。

pgvector 的 HNSW 参数直接决定质量：m=16, ef_construction=64 起步，查询时 SET hnsw.ef_search = 40（默认）向上调可换召回。混合检索实践中，两侧各取 20 候选再融合（RRF）是经过验证的起点。路线图推荐项目 rag-knowledge-system 用 PostgreSQL 17 + pgvector(HNSW) + pg_trgm 做双通道混合检索；spring-al-alibaba-customer 用 pgvector + tsvector 落地企业级客服——两个"在学"项目都选了 pgvector，这不是巧合。

技术决策日志的固定三问（路线图贯穿线要求）：为什么选它 / 放弃了什么 / 代价是什么。本任务的产出就是按此模板写下 #01 篇：

# 技术决策日志 #01：RAG 项目向量库选型

## 决策：pgvector（PostgreSQL 17）

## 为什么选它
1. 知识库规模预估 < 500 万向量，pgvector HNSW recall>98%、
   混合检索延迟 15-30ms，满足 SLA 且无余量焦虑；
2. 元数据与向量同库同事务，文档入库无最终一致窗口；
3. 混合检索一条 SQL 完成（pgvector + tsvector + RRF），
   是 Phase1「混合检索+Rerank」任务的基础设施前提；
4. 复用团队 PostgreSQL 运维体系（备份/监控/主从），
   边际学习成本最低，符合在职转型的时间预算。

## 放弃了什么
- Qdrant：延迟最优，但引入独立组件 + 新故障域，
  收益（p99 从 ~10ms 到 ~5ms）对本场景无感；
- Milvus：吞吐/扩展天花板最高，但分布式运维成本
  与 300 万以下向量规模完全不匹配。

## 代价是什么
- 百万向量以上规模需重新评估（预埋迁移方案：
  Spring AI VectorStore 抽象层换实现类）；
- 向量+强元数据过滤存在查询计划器陷阱，
  需要 iterative_scan 与预热查询规避；
- 极致性能场景（<5ms p99）让位于运维简单性。

## 复核触发条件
向量数 > 3百万 或 p99 > 200ms 持续一周，重开选型。
迁移预案的技术依托：Spring AI 的 VectorStore 接口与 LangChain4j 的 EmbeddingStore 抽象让"换库"收敛为换一个 starter 依赖 + 建表脚本，这是框架层的解耦红利，也是决策"可逆性"的来源——可逆的决策才敢快做。

四、面试话术（10min）

对应第一梯队「RAG 评测三层指标」与「混合检索 + Rerank」的选型追问，30 秒版本：

  • 被问"为什么不用专门的向量数据库"：先报规模与 SLA（<500 万向量 / p99 <200ms），再讲事务一致性与运维复用，最后给迁移预案——体现的是工程权衡而非技术跟风。
  • 被追问"pgvector 的坑"：向量+元数据过滤的计划器陷阱、HNSW 内存开销、百万级以上 ANN 索引差距——能讲坑才证明真用过。
  • 被追问"什么时候换"：报出决策日志里的复核触发条件（3 百万向量 / p99 超标），决策有边界才可信。
