2Function Calling 原理图解

2.1 一个最常见的误解：LLM 真的"调用"了函数吗？

很多初学者第一次用 Function Calling 时会形成这样一个错觉：模型在对话过程中"伸手"去执行了你写的 Java/Python 方法。这是本知识点最大的认知陷阱，也是面试中最容易被追问的地方。

❌ 常见误解

LLM 直接调用了函数

以为模型在推理时通过某种 RPC / 远程调用机制，真的运行了 getWeather()，函数就在模型的"体内"被执行了。

✅ 实际真相

LLM 只输出一段结构化 JSON

模型自始至终只做一件事——生成下一个 token。它只是被训练成在合适时机生成一段符合格式的 JSON"调用意图"，由你的外部代码解析并真正执行，再把结果回填给模型。

2.2 底层真相：受控的结构化文本生成

从底层看，所谓"调用工具"，是模型被微调成在恰当的时机生成一段符合特定格式的结构化文本（通常是 JSON），然后由外部代码（SDK / 你的应用）解析这段文本、真正执行对应的函数，再把结果作为一条新消息塞回去。模型的工具调用能力强弱，本质上反映的是它在"理解工具语义 + 生成合法 JSON + 正确填参数"这件事上的训练程度。

这意味着：工具调用的可靠性，本质上是模型生成正确格式 JSON 的概率。这也是为什么 GPT-4、Claude 等都对工具调用做了专项强化训练。

面试高频口述（务必背熟）

"Function Calling 的本质是受控的文本生成，不是模型真的执行了函数。模型只负责生成一段结构化的 JSON 调用指令，真正的函数执行发生在我这边的业务代码里。执行完，我把结果作为 ToolMessage 回填给模型，模型再基于这个结果生成最终的自然语言回答。所以工具调用的可靠性，本质上是模型生成正确 JSON 的概率。"

2.3 完整的 Tool Use 五步流程图

把上面的机制抽象成流程，Tool Use 是一个"模型 ↔ 应用"之间的多轮对话闭环。无论你用 OpenAI 原生 API、Spring AI 还是 LangChain4j，底层都在重复这五步：

1
携带工具发起请求
应用把 user 提问 + 一组工具定义（name/description/参数 schema）一起发给 LLM
→
2
LLM 决策并返回调用意图
模型判断需要工具，返回 tool_use：工具名 + 入参 JSON（而非纯文本）
→
3
应用执行业务逻辑
代码根据工具名找到对应方法，用模型给的参数真正执行，拿到结果
→
4
结果回填 LLM
把执行结果作为 tool_result 消息追加，再次请求模型
→
5
LLM 生成最终回答
模型基于工具结果，输出用户能看懂的自然语言回答（或继续调用下一个工具）
🔑
一个关键工程细节

模型在返回 tool_use 时已经"暂停"推理——它不会继续往下生成，必须等代码把结果喂回去才会继续。这意味着工具执行的延迟会直接累加进整个响应时间。所以工具本身的性能优化（缓存、异步、超时控制）和 LLM 推理速度同样重要。

@Tool 注解的核心属性

name：工具名，不填则用方法名，同一请求内必须唯一；description：最关键，告诉模型"何时、如何"调用，强烈建议详细描述；returnDirect：结果是否直接返回客户端而不回填模型（适合纯数据检索）；resultConverter：自定义返回值转字符串逻辑。方法可为任意可见性、静态或实例。

对照无工具 vs 有工具

同一个问题"475695037565 的平方根"：不给工具时模型会猜出 689710（接近但错误）；给 squareRoot 工具后，模型先返回 squareRoot(475695037565) 调用意图 → 框架执行得到 689706.486532 → 回填后模型输出准确答案。这正是 Function Calling 的价值：把模型"不擅长的事"外包给确定性代码。

4.3 @P 参数描述：必填 / 可选 / 默认值

默认所有参数都视为必填（写进 schema 的 required 数组）。三种让参数"可选"的方式：

  • @P(required = false) 显式声明可选；
  • 参数声明为 Optional<T>；
  • @P(defaultValue = "10")：LLM 省略时框架自动填默认值（最省心）。
⚠️
参数名丢失的坑

未加 @P 的 name 且未开启 javac 的 -parameters 选项时，反射只能拿到 arg0、arg1，模型会困惑。Spring 和 Quarkus 默认开启 -parameters，所以用这些框架时通常没事；纯 Maven 项目建议在 pom 里加上 <parameters>true</parameters>。

4.4 工具可见性：ALWAYS_VISIBLE 与搜索发现

LangChain4j 支持控制工具的可见性策略：@Tool(searchBehavior = ALWAYS_VISIBLE) 的工具在整个 AI Service 调用期间始终可见、不参与"工具搜索"筛选；其余工具遵循正常的搜索流程。这是"多工具选择策略"在框架层面的落地（见 5.3）。

5.2 工具描述最佳实践：Schema 设计五原则

工具的 JSON Schema 不只是给代码用的接口定义，它同时是给 LLM 看的自然语言指令。这是工具设计里最容易被低估的部分——同一个函数，描述写得好坏，调用准确率能差出 20%~30%。

原则要点反例 → 正例
① 用 enum 而非自由文本取值有限时一律 enum 约束，从根本消除拼写/大小写问题"status":"string" → "enum":["pending","shipped"]
② description 写"何时用"不只说做什么，更要写清使用边界"查询数据" → "按订单状态搜索用户订单，仅支持已存在订单，不能创建"
③ 控制工具数量超过 20~30 个时选择准确率显著下降（占用 context + 增加混淆）用分层路由拆分
④ 参数命名见名知意命名本身是给模型的隐性提示p1 → user_email
⑤ 统一返回信封所有工具返回结构一致，避免模型幻觉时而数组时而对象 → 统一 {success,data,error}
 
json · Schema 反例 vs 正例

5.3 多工具选择策略：分层路由

当工具数量膨胀到几十个，一次性全塞进 context 会让模型选择准确率骤降。解法是分层路由：先用一个"调度工具"让 LLM 判断属于哪个领域（订单/库存/物流），再在该领域内暴露具体工具集——相当于给 LLM 做一次"目录导航"。

6工具调用与 Agent 的关系

很多人把"工具调用"和"Agent"混为一谈。准确的关系是：Tool Use 是 Agent 的原子能力，Agent 是在 Tool Use 之上加了"规划—行动—观察"循环的编排模式。

Tool Use（工具调用）

单次"决策 → 执行 → 回填"

一次 Tool Use = 一个工具的调用闭环。它是无状态的、原子的。框架（Spring AI / LangChain4j）帮你自动跑完第 2 节的五步。

Agent（智能体）

多轮"思考 → 行动 → 观察"循环

Agent = 在 Tool Use 之外加上目标拆解、状态记忆、多步规划。它把多次工具调用串成一个完成复杂任务的流程（ReAct 模式：Reason + Act）。

🔗
一句话定位

没有 Tool Use，Agent 就只能"空想"（无法获取实时数据、无法执行动作）；有了 Tool Use，Agent 才能真正"动手干活"。本任务掌握的 Tool Calling，正是 Phase 1 构建 Agent 的积木。Phase 2 验收要求"能讲 Function Call 底层"——底层就是第 2 节那套"LLM 不执行函数、只生成 JSON"的机制。

7面试口述要点

Function Calling / 工具调用是 JD 中极高频率的需求，"Function Call 底层原理—LLM 不执行函数"更是面试第一梯队问题。下面是高频问答模板，建议对照代码理解后用自己的话复述。

Q1Function Calling 的底层原理是什么？LLM 真的调用了函数吗？

没有。 LLM 自始至终只做一件事：生成下一个 token。所谓"调用工具"，是模型被训练成在合适时机生成一段符合格式的结构化 JSON 调用指令（含工具名和入参），由我这边的外部代码解析并真正执行。执行完，我把结果作为 ToolMessage 回填给模型，模型再基于结果生成最终的自然语言回答。

所以工具调用的可靠性，本质上是模型生成正确格式 JSON 的概率。这也是 GPT-4、Claude 等专门做工具调用微调的原因。

Q2完整描述一次 Tool Use 的流程。

五步闭环：① 应用把用户提问 + 工具定义（name/description/参数 schema）发给 LLM；② LLM 判断需要工具，返回工具名和入参 JSON（而非答案）；③ 应用代码根据工具名找到方法、用入参真正执行，拿到结果；④ 把结果作为 tool_result 消息回填，再次请求 LLM；⑤ LLM 基于结果生成最终回答（或继续调用下一个工具）。在模型返回 tool_use 时它已"暂停"，必须等结果回填才会继续。

Q3Function Calling / Tool Use / Plugin / Action 是一回事吗？

概念上是同一件事的不同命名。OpenAI 早期叫 Function Calling，后统一为 Tool Use；Anthropic 一直叫 Tool Use；LangChain 里叫 Tool/Action；ChatGPT Plugin 是更早的产品化叫法（已被 Tool Use 取代）。底层机制完全一致：模型生成结构化调用指令 → 外部执行 → 结果回注。

Q4为什么有时模型该调用工具却不调用，或不该调用却调用了？

三个常见原因：① 工具 description 不够清晰，模型判断不出适用场景；② System Prompt 没有明确的工具使用策略（如"涉及实时数据必须调用工具，不要依赖训练知识"）；③ 用户问题意图模糊。生产中可用 tool_choice 参数强制模型在特定场景必须调用工具。

Q5Spring AI 和 LangChain4j 实现 Tool Calling 有什么区别？

都是把"五步闭环"封装起来。Spring AI 用 @Tool + @ToolParam，通过 ChatClient.tools() 注册，由 Advisor 链里的 ToolCallingAdvisor 自动调度，深度融入 Spring Boot 自动装配。LangChain4j 用 @Tool + @P，通过 AiServices 生成代理接口自动调度，框架中立；底层还提供 ToolSpecification + ChatModel 让你手动看清每一步。两者背后是同一套机制。

Q6工具调用失败时，要不要把原始异常堆栈给 LLM 看？

不要。原始堆栈（如 NullPointerException at line 247）对 LLM 决策没帮助，还浪费 token、泄露系统内部实现（安全风险）。正确做法是做错误转译：把技术异常转成 LLM 能理解并行动的语义化描述，如"数据查询暂时不可用，建议稍后重试或换个查询条件"，让模型决定重试还是放弃。

Q7工具数量很多时怎么保证准确率？

超过 20~30 个工具时准确率显著下降（占用 context + 选项过多增加混淆）。解法是分层路由：先用一个调度工具让 LLM 判断领域，再注入该领域的具体工具集。Spring AI 2.0 的 Tool Search、LangChain4j 的 searchBehavior=ALWAYS_VISIBLE 都是这一策略的官方实现。
