Embedding 模型选型与接入实战：bge-large-zh / text-embedding-3 / m3e 对比 + Spring AI 接入

总预估时长：约 60 分钟（选型维度 10min / 三模型对比 12min / Spring AI 三种接入 25min / 决策与面试串联 13min）· 主线 Java（Spring AI + LangChain4j 双路径），Python 仅辅助

一、Embedding 选型为什么是 RAG 的"地基决策"（10min）

在 RAG 链路里，Embedding 模型决定了"语义空间"的形状：文档切块后向量化入库（离线阶段）、查询向量化后近邻检索（在线阶段）用的是同一个模型，换模型 = 全量重建向量库。这意味着它是所有环节里切换成本最高的决策，必须在项目初期就认真选。

选型要看五个维度，缺一不可：

  • 中文效果：C-MTEB（中文 MTEB）评测体系下的检索（Retrieval）、语义相似度（STS）得分，中文场景必须看中文榜，不能照搬英文 MTEB 排名。
  • 维度与存储成本：维度直接决定向量库存储与索引内存。1024 维 vs 3072 维，HNSW 索引内存差距接近 3 倍。
  • 上下文长度：bge-m3 支持 8192 token，bge-large-zh-v1.5 是 512 token——长文档切分策略要跟着上下文长度走。
  • 部署形态：API 调用（按 token 计费、免运维）vs 本地部署（Ollama/ONNX，数据不出域但吃 GPU/CPU）。
  • 延迟：本地小模型毫秒级出向量，跨国 API 调用可能几百毫秒起。
面试视角：这一节对应路线图面试体系第一梯队的「RAG 完整链路 + Chunking 策略」——面试官问"Embedding 怎么选"，标准答案结构就是：中文评测分数 + 维度/存储 + 上下文长度 + 部署成本四件套，最后落到你项目的真实取舍。

m3e 的定位：m3e 是 C-Pack 评测体系出来前的中文开源代表，如今在 C-MTEB 上已被 bge-v1.5 系列明显反超。把它放进对比矩阵的价值是理解"中文开源模型迭代很快，选型要看评测日期"。

三、Spring AI 三种接入路径实战（25min）

Spring AI 的 EmbeddingModel 是统一抽象接口，提供 embed(String)、embed(List<String>)、embedForResponse() 等方法，切换实现只换 starter 依赖和配置。下面三条路径分别对应 API 调用、本地 Ollama、进程内 ONNX。

路径一：OpenAI text-embedding-3（API 调用）

引入 spring-ai-starter-model-openai-sdk，通过配置切换 small/large 与维度：

<!-- pom.xml -->
<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-model-openai-sdk</artifactId>
</dependency>
# application.yml
spring:
  ai:
    openai:
      api-key: ${OPENAI_API_KEY}
      embedding:
        options:
          model: text-embedding-3-small   # 或 text-embedding-3-large
          dimensions: 1024                # large 支持降维，省存储
EmbeddingModel embeddingModel; // 自动注入 OpenAiSdkEmbeddingModel

// 单文本向量化
float[] vector = embeddingModel.embed("Spring AI 如何接入向量模型？");

// 批量向量化（入库阶段，注意控制批量大小）
List<float[]> vectors = embeddingModel.embed(
        List.of("文档块1内容", "文档块2内容", "文档块3内容"));

System.out.println("维度: " + vector.length);   // 1024
System.out.println("首值: " + vector[0]);

路径二：Ollama 本地部署 bge（数据不出域）

引入 spring-ai-starter-model-ollama，调用 Ollama 的 /api/embed 端点。本地先拉模型：

# 拉取中文 embedding 模型（GGUF 格式）
ollama pull quentinz/bge-large-zh-v1.5
# 或多语言混合检索向 bge-m3 升级
ollama pull bge-m3
spring:
  ai:
    ollama:
      base-url: http://localhost:11434
      embedding:
        model: quentinz/bge-large-zh-v1.5
        options:
          temperature: 0.0    # embedding 不需要创造性
      init:
        pull-model-strategy: when_missing   # 缺模型时自动拉取
// OllamaEmbeddingModel 自动装配，接口与 OpenAI 路径完全一致
float[] zhVector = embeddingModel.embed("中文语义检索测试：Spring Boot 3 微服务实战");

// 相似度对比：同义句应明显高于无关句
float[] v1 = embeddingModel.embed("如何配置 Redis 缓存");
float[] v2 = embeddingModel.embed("Redis 缓存怎样设置");
float[] v3 = embeddingModel.embed("今天中午吃什么");
double sim12 = cosine(v1, v2);   // 预期 > 0.85
double sim13 = cosine(v1, v3);   // 预期 < 0.5

路径三：Transformers ONNX 进程内推理（零外部服务）

TransformersEmbeddingModel 用 ONNX Runtime 在 JVM 进程内直接跑 HuggingFace 模型，适合离线场景。先用 optimum-cli 把模型导出为 ONNX：

optimum-cli export onnx -m BAAI/bge-small-zh-v1.5 ./bge-onnx
<dependency>
    <groupId>org.springframework.ai</groupId>
    <artifactId>spring-ai-starter-model-transformers</artifactId>
</dependency>
spring:
  ai:
    embedding:
      transformer:
        onnx:
          model-uri: file:///opt/models/bge-onnx/model.onnx
        tokenizer:
          uri: file:///opt/models/bge-onnx/tokenizer.json
        # 默认 all-MiniLM-L6-v2：384 维、MTEB 58.8 分、模型仅 80MB
ONNX 路径的取舍：进程内推理免运维、延迟极低，但模型加载吃 JVM 内存，且 CPU 推理吞吐有限——适合中小规模（百万级以下 chunk）或演示环境；生产高并发仍建议 Ollama 或专用推理服务。

向量入库串联（LangChain4j 侧对照）

LangChain4j 的 EmbeddingStoreIngestor 把切分 + 向量化 + 入库串成一条管道，与 Spring AI ETL 等价：

EmbeddingStoreIngestor ingestor = EmbeddingStoreIngestor.builder()
        .documentSplitter(DocumentSplitters.recursive(400, 40))
        .embeddingModel(embeddingModel)      // 同样是统一抽象
        .embeddingStore(embeddingStore)      // Qdrant / pgvector / Milvus
        .build();
ingestor.ingest(document);

4.1 决策矩阵（可直接抄进你的技术决策日志）

4.2 面试串联

  • 「RAG 完整链路 + Chunking 策略」追问 Embedding 选型：按"中文评测 → 维度/存储 → 上下文长度 → 部署成本"四步答，强调"换模型要全量重建向量库"的迁移成本意识。
  • 「混合检索 + Rerank」追问向量质量：指出稠密向量对精确实体/型号/代码标识符弱，这正是要配 BM25 稀疏检索的原因；bge-m3 原生支持稀疏模式，可减少一路模型。
  • 维度降维追问：text-embedding-3 的 dimensions 参数是 Matryoshka 式训练，降维只损失尾部精度；传统模型直接截断维度会严重掉点。
  • 量化结果话术（呼应路线图验收标准）："我们对比 bge-large-zh 与 text-embedding-3-small，在 20 题中文评测集上 Recall@5 分别为 X% 与 Y%，最终选 bge 本地部署，节省每月 API 成本 Z 元"——有数字才有说服力。

4.3 动手验收清单

  1. 跑通 OpenAI 路径：embed 一个中文问题，打印维度与向量前 5 个值。
  2. 跑通 Ollama 路径：同义句/无关句余弦相似度对比，验证语义空间有效性。
  3. 完成决策矩阵填空：为你的 RAG 项目写下选型结论 + 一条放弃理由（写进技术决策日志）。
