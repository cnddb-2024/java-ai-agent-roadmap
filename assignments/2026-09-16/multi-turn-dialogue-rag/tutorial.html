1 为什么需要查询改写 — 指代消解问题场景

在多轮对话 RAG 系统中，用户经常使用代词（如"它"、"这个"、"上面提到的"）来指代前文提到的实体。这类查询如果直接送入向量数据库做检索，召回率会极低——因为代词本身没有语义信息，向量数据库无法将"它"映射到正确的上下文实体。

问题场景

第一轮对话中用户询问"丹麦的首都"，模型正确回答"哥本哈根"。第二轮用户问"它的大城市有哪些？"——此时"它"指代"丹麦"，但向量检索直接搜索"它的大城市有哪些"几乎不可能召回丹麦相关文档。

这就是指代消解要解决的核心问题：将含代词的查询与对话历史"JOIN"在一起，生成一个上下文自包含的独立查询，再送入向量数据库检索。

桥梁式解释

指代消解：类比 SQL 的 JOIN 操作。JOIN 将两个表中通过外键关联的行合并成一行；指代消解将对话历史中的上下文实体与当前查询中的代词"关联合并"，使"它的大城市"变为"丹麦的大城市"。Spring AI 中由 CompressionQueryTransformer 承担此职责。

查询改写：类比 MySQL 的查询优化器。优化器在执行 SQL 前会重写查询计划（如子查询展开、谓词下推）以提升性能；查询改写器在向量检索前重写用户问题（如关键词扩展、语义归一化），以提升向量搜索的召回率。Spring AI 中由 RewriteQueryTransformer 承担此职责。

无查询改写 vs 有查询改写

以下代码展示没有查询改写时的检索失败场景与有查询改写后的正确流程对比：

// ========== 无查询改写（检索失败） ==========
// 第一轮
User:     "丹麦的首都是哪里？"
Assistant: "丹麦的首都是哥本哈根。"

// 第二轮 —— "它" 指代不明，向量检索召回率极低
User: "它的大城市有哪些？"
// 向量搜索原始 query: "它的大城市有哪些？"
// → embedding("它的大城市有哪些") 与丹麦相关文档相似度极低
// → 召回噪声文档，最终回答可能偏离主题

// ========== 有查询改写（检索成功） ==========
// 第二轮 —— CompressionQueryTransformer 消解指代
User: "它的大城市有哪些？"
// Step 1: MessageChatMemoryAdvisor 注入历史 → "丹麦的首都是哥本哈根"
// Step 2: CompressionQueryTransformer 改写 → "丹麦的大城市有哪些？"
// Step 3: RewriteQueryTransformer 优化 → "丹麦主要大城市列表"
// Step 4: 向量检索 "丹麦主要大城市列表" → 召回丹麦城市文档
// Step 5: LLM 基于检索文档生成回答 → "丹麦的大城市包括奥胡斯、奥登塞、奥尔堡..."

2 Spring AI ChatMemory 架构（开箱实现，Spring AI 2.0+）

Spring AI 2.0 的 ChatMemory 架构由三个核心组件构成：ChatMemory（记忆容器）、ChatMemoryRepository（持久化后端）、MessageChatMemoryAdvisor（记忆注入 Advisor）。下面逐一解析。

桥梁式解释 — ChatMemory

ChatMemory：类比 Spring Boot 的 Session 机制。Session 存储 HTTP 请求之间的用户会话状态（如登录信息、购物车），ChatMemory 存储 LLM 对话之间的消息历史（如用户消息、AI 回复）。就像 Session 可以持久化到 Redis 一样，ChatMemory 通过 ChatMemoryRepository 持久化到 Redis 或 JDBC 数据库。

2.1 整体架构流程

Spring AI 2.0 多轮 RAG 管道的 Advisor 执行顺序如下：

用户查询
"它的大城市有哪些？"
↓
MessageChatMemoryAdvisor
注入历史对话 (Redis)
↓
CompressionQueryTransformer
指代消解：→ "丹麦的大城市"
↓
RewriteQueryTransformer
查询重写优化检索
↓
DocumentRetriever
向量检索 Top-K 文档
↓
LLM (ChatClient)
基于检索文档生成回答
↓
更新 ChatMemory
写入新消息到 Redis
执行顺序：记忆注入 → 查询改写 → 文档检索 → LLM 生成 → 更新记忆
关键：执行顺序

记忆注入必须先于查询改写和检索。只有先通过 MessageChatMemoryAdvisor 将历史对话注入上下文，CompressionQueryTransformer 才能读取到"丹麦"这个实体，进而将"它的大城市"消解为"丹麦的大城市"。如果顺序反了，查询改写器无法获取上下文，指代消解将失效。

2.2 ChatMemoryRepository — 持久化后端

ChatMemoryRepository 是记忆持久化接口，Spring AI 2.0 提供了 JDBC 和 Redis 两种开箱实现。类比 Spring Data 的 Repository 模式：你只需声明接口，框架提供默认实现。

// Spring AI 2.0+ — JDBC 持久化 ChatMemory
// 类比 Spring Data JPA 的 Repository：声明即用
@Bean
public ChatMemoryRepository chatMemoryRepository(JdbcClient jdbcClient) {
    return JdbcChatMemoryRepository.builder()
        .jdbcClient(jdbcClient)
        .dialect(PostgresDialect.create())
        .build();
}

// Spring AI 2.0+ — Redis 持久化 ChatMemory
// 类比 Spring Session 的 Redis 存储：高速读写 + TTL 过期
@Bean
public ChatMemoryRepository redisChatMemoryRepository(
        RedisTemplate<String, String> redisTemplate) {
    return RedisChatMemoryRepository.builder()
        .redisTemplate(redisTemplate)
        .build();
}

2.3 MessageWindowChatMemory — 滑动窗口

MessageWindowChatMemory 是 Spring AI 2.0 的默认 ChatMemory 实现，采用滑动窗口策略保留最近 N 条消息，类比 TCP 滑动窗口协议——只保留窗口内的消息，旧消息自动淘汰，防止 Token 超出模型上下文限制。

// Spring AI 2.0+ — 滑动窗口记忆
// maxMessages = 20：保留最近 20 条消息，防止 Token 爆炸
@Bean
public ChatMemory chatMemory(ChatMemoryRepository repository) {
    return MessageWindowChatMemory.builder()
        .chatMemoryRepository(repository)
        .maxMessages(20)
        .build();
}

2.4 MessageChatMemoryAdvisor — 替代已废弃的 PromptChatMemoryAdvisor

Spring AI 2.0 引入了 MessageChatMemoryAdvisor，替代已废弃的 PromptChatMemoryAdvisor。核心区别：

特性 PromptChatMemoryAdvisor (已废弃) MessageChatMemoryAdvisor (2.0+)
注入方式 将历史拼接到 prompt 文本字符串 将历史作为独立 Message 列表注入
角色区分 无法区分 user/assistant 角色 保留 Message 的 role 信息
LLM 理解 模型可能混淆历史与当前查询 模型清晰区分对话轮次 
// Spring AI 2.0+ — MessageChatMemoryAdvisor（推荐）
// 替代已废弃的 PromptChatMemoryAdvisor
@Bean
public MessageChatMemoryAdvisor messageChatMemoryAdvisor(ChatMemory chatMemory) {
    return MessageChatMemoryAdvisor.builder()
        .chatMemory(chatMemory)
        .build();
}

2.5 Conversation ID 必填机制

Spring AI 2.0 中，使用 MessageChatMemoryAdvisor 时必须提供 conversationId。这类似于 Spring Session 的 sessionId——只有通过唯一 ID 才能从 Redis/JDBC 中找到对应的对话历史。

必填机制

如果不传 conversationId，Spring AI 2.0 会抛出异常或使用默认值导致不同用户的对话串扰。生产环境中必须为每个用户会话生成唯一 ID（如 UUID 或 userId + sessionId 组合）。

// conversationId 必填：标识对话会话（类比 Session ID）
String response = chatClient.prompt()
    .user("它的大城市有哪些？")
    .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, "conv-001"))
    .call()
    .content();

3 查询改写两件套：CompressionQueryTransformer + RewriteQueryTransformer

Spring AI 2.0 提供了两个开箱的 QueryTransformer 实现，分别解决指代消解和查询重写两个问题。它们可以单独使用，也可以在 RetrievalAugmentationAdvisor 中链式组合。

桥梁式解释 — QueryTransformer

QueryTransformer：类比 Spring MVC 的 HandlerInterceptor。拦截器在请求到达 Controller 前对请求做预处理（如鉴权、日志）；QueryTransformer 在查询到达向量数据库前对查询做预处理（如指代消解、关键词扩展），输出一个更适合向量检索的查询字符串。

3.1 CompressionQueryTransformer — 指代消解

CompressionQueryTransformer 利用 LLM 将对话历史 + 当前查询压缩为一个上下文自包含的独立查询。它内部会读取 MessageChatMemoryAdvisor 注入的历史消息，识别代词指代的实体，生成消解后的查询。

// Spring AI 2.0+ — CompressionQueryTransformer
// 输入：历史对话 "丹麦的首都是哥本哈根" + 当前查询 "它的大城市有哪些？"
// 输出：消解后查询 "丹麦的大城市有哪些？"
QueryTransformer compressionTransformer = CompressionQueryTransformer.builder()
    .chatClientBuilder(chatClientBuilder)
    .build();

其内部 Prompt 大致为："根据对话历史，将用户最新问题重写为一个不含代词的独立问题。"——LLM 读取历史消息后，识别出"它"指代"丹麦"，输出自包含查询。

3.2 RewriteQueryTransformer — 查询重写优化检索

RewriteQueryTransformer 利用 LLM 重写查询以优化向量检索的召回率。与 Compression 的区别：Compression 侧重消解指代（解决"它"指代谁），Rewrite 侧重优化表达（将口语化查询改写为更适合向量搜索的关键词组合）。

// Spring AI 2.0+ — RewriteQueryTransformer
// 输入：消解后查询 "丹麦的大城市有哪些？"
// 输出：优化查询 "丹麦主要大城市列表 包括人口规模"
QueryTransformer rewriteTransformer = RewriteQueryTransformer.builder()
    .chatClientBuilder(chatClientBuilder)
    .build();

3.3 链式组合执行顺序

在 RetrievalAugmentationAdvisor 中，QueryTransformer 按注册顺序链式执行。推荐顺序：Compression → Rewrite——先消解指代，再优化表达。

// Spring AI 2.0+ — 链式组合查询转换器
// 执行顺序：Compression (指代消解) → Rewrite (查询重写) → Retrieve (检索)
RetrievalAugmentationAdvisor ragAdvisor = RetrievalAugmentationAdvisor.builder()
    .queryTransformers(compressionTransformer, rewriteTransformer)
    .documentRetriever(documentRetriever)
    .build();

3.4 框架无内置实现的场景 — 自定义查询分解

⚠️ 框架无内置实现

Spring AI 2.0 仅提供 CompressionQueryTransformer 和 RewriteQueryTransformer 两种转换器。如果需要多查询分解（如将"比较 A 和 B"拆分为"查询 A"+"查询 B"两个子查询并分别检索），框架没有对应能力，需要手写 QueryTransformer 实现。

// ⚠️ 框架无内置实现：多查询分解 QueryTransformer
// Spring AI 2.0 仅有 Compression 和 Rewrite 两种，查询分解需手写
public class DecompositionQueryTransformer implements QueryTransformer {

    private final ChatClient chatClient;

    public DecompositionQueryTransformer(ChatClient chatClient) {
        this.chatClient = chatClient;
    }

    @Override
    public String transform(String query, Map<String, Object> context) {
        String prompt = """
            将以下问题分解为多个独立的子查询，每行一个，不要编号：
            问题：%s
            """.formatted(query);
        return chatClient.prompt()
            .user(prompt)
            .call()
            .content();
    }
}

// 使用：注册到 RetrievalAugmentationAdvisor
RetrievalAugmentationAdvisor advisor = RetrievalAugmentationAdvisor.builder()
    .queryTransformers(
        compressionTransformer,           // 1. 指代消解
        rewriteTransformer,                // 2. 查询重写
        new DecompositionQueryTransformer(chatClient)  // 3. 查询分解（手写）
    )
    .documentRetriever(documentRetriever)
    .build();

4.3 方案 A — RetrievalAugmentationAdvisor + 查询改写（推荐）

这是生产级多轮 RAG 的推荐方案。通过 RetrievalAugmentationAdvisor 组合查询转换器链 + 文档检索器，实现指代消解 + 查询重写 + 向量检索的一体化管道。

package com.example.multiturnrag.config;

import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.chat.memory.*;
import org.springframework.ai.chat.memory.repository.*;
import org.springframework.ai.vectorstore.VectorStore;
import org.springframework.ai.vectorstore.redis.RedisVectorStore;
import org.springframework.ai.rag.advisor.RetrievalAugmentationAdvisor;
import org.springframework.ai.rag.query.retriever.VectorStoreDocumentRetriever;
import org.springframework.ai.rag.query.transformer.CompressionQueryTransformer;
import org.springframework.ai.rag.query.transformer.RewriteQueryTransformer;
import org.springframework.ai.rag.query.transformer.QueryTransformer;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.data.redis.core.RedisTemplate;

@Configuration
public class MultiTurnRagConfig {

    // --- 1. ChatMemoryRepository（Redis 持久化）---
    @Bean
    public ChatMemoryRepository chatMemoryRepository(
            RedisTemplate<String, String> redisTemplate) {
        // Spring AI 2.0+ 开箱实现：对话记忆持久化到 Redis
        return RedisChatMemoryRepository.builder()
            .redisTemplate(redisTemplate)
            .build();
    }

    // --- 2. ChatMemory（滑动窗口，maxMessages=20）---
    @Bean
    public ChatMemory chatMemory(ChatMemoryRepository repository) {
        return MessageWindowChatMemory.builder()
            .chatMemoryRepository(repository)
            .maxMessages(20)
            .build();
    }

    // --- 3. MessageChatMemoryAdvisor（替代已废弃的 PromptChatMemoryAdvisor）---
    @Bean
    public MessageChatMemoryAdvisor memoryAdvisor(ChatMemory chatMemory) {
        return MessageChatMemoryAdvisor.builder()
            .chatMemory(chatMemory)
            .build();
    }

    // --- 4. DocumentRetriever（向量检索 Top-5）---
    @Bean
    public VectorStoreDocumentRetriever documentRetriever(VectorStore vectorStore) {
        return VectorStoreDocumentRetriever.builder()
            .vectorStore(vectorStore)
            .topK(5)
            .build();
    }

    // --- 5. RetrievalAugmentationAdvisor（查询改写 + 检索）---
    @Bean
    public RetrievalAugmentationAdvisor ragAdvisor(
            ChatClient.Builder chatClientBuilder,
            VectorStoreDocumentRetriever documentRetriever) {

        // 5a. 指代消解："它的大城市" → "丹麦的大城市"
        QueryTransformer compressionTransformer =
            CompressionQueryTransformer.builder()
                .chatClientBuilder(chatClientBuilder)
                .build();

        // 5b. 查询重写：优化检索表达
        QueryTransformer rewriteTransformer =
            RewriteQueryTransformer.builder()
                .chatClientBuilder(chatClientBuilder)
                .build();

        // 5c. 组合：Compression → Rewrite → Retrieve
        return RetrievalAugmentationAdvisor.builder()
            .queryTransformers(compressionTransformer, rewriteTransformer)
            .documentRetriever(documentRetriever)
            .build();
    }

    // --- 6. ChatClient（组装 Advisor 链）---
    @Bean
    public ChatClient chatClient(
            ChatClient.Builder chatClientBuilder,
            MessageChatMemoryAdvisor memoryAdvisor,
            RetrievalAugmentationAdvisor ragAdvisor) {

        // Advisor 执行顺序：
        //   1. MessageChatMemoryAdvisor → 注入历史对话
        //   2. RetrievalAugmentationAdvisor → 查询改写 + 检索 + 增强
        return chatClientBuilder
            .defaultAdvisors(memoryAdvisor, ragAdvisor)
            .build();
    }
}

4.4 方案 B — MessageChatMemoryAdvisor + QuestionAnswerAdvisor（简易 RAG）

如果不需要查询改写（如单轮问答场景），可以使用更简单的 QuestionAnswerAdvisor 替代 RetrievalAugmentationAdvisor。它只做检索增强，不经过查询转换器。

// 简易方案：MessageChatMemoryAdvisor + QuestionAnswerAdvisor
// 无查询改写，适合简单 RAG 场景（无指代消解需求）
@Bean
public ChatClient simpleChatClient(
        ChatClient.Builder chatClientBuilder,
        MessageChatMemoryAdvisor memoryAdvisor,
        VectorStore vectorStore) {

    QuestionAnswerAdvisor qaAdvisor = QuestionAnswerAdvisor.builder()
        .documentRetriever(VectorStoreDocumentRetriever.builder()
            .vectorStore(vectorStore)
            .topK(5)
            .build())
        .build();

    return chatClientBuilder
        .defaultAdvisors(memoryAdvisor, qaAdvisor)
        .build();
}

4.5 多轮对话调用示例

package com.example.multiturnrag.service;

import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.chat.memory.ChatMemory;
import org.springframework.stereotype.Service;

@Service
public class MultiTurnRagService {

    private final ChatClient chatClient;

    public MultiTurnRagService(ChatClient chatClient) {
        this.chatClient = chatClient;
    }

    public String chat(String userMessage, String conversationId) {
        // conversationId 必填：标识对话会话（类比 Session ID）
        // MessageChatMemoryAdvisor 据此从 Redis 加载历史
        // RetrievalAugmentationAdvisor 据此读取历史做指代消解
        return chatClient.prompt()
            .user(userMessage)
            .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, conversationId))
            .call()
            .content();
    }
}

// ========== 使用示例 ==========
// 第一轮
service.chat("丹麦的首都是哪里？", "conv-001");
// → "丹麦的首都是哥本哈根。"

// 第二轮 —— "它" 被自动消解为 "丹麦"
service.chat("它的大城市有哪些？", "conv-001");
// 内部流程：
//   1. MessageChatMemoryAdvisor 从 Redis 加载历史 "丹麦的首都是哥本哈根"
//   2. CompressionQueryTransformer 改写 → "丹麦的大城市有哪些？"
//   3. RewriteQueryTransformer 优化 → "丹麦主要大城市列表"
//   4. VectorStoreDocumentRetriever 检索 Top-5 丹麦城市文档
//   5. LLM 生成回答 → "丹麦的大城市包括奥胡斯、奥登塞、奥尔堡..."

// 不同用户使用不同 conversationId，互不干扰
service.chat("日本的首都是哪里？", "conv-002");  // 独立会话

5 LangChain4j 对照（了解即可）

LangChain4j 是 JVM 生态的另一个 LLM 框架，提供了与 Spring AI 对标的 ChatMemory 和查询改写能力。以下为对照参考。

Spring AI 2.0+ GA

  • ChatMemory → MessageWindowChatMemory
  • ChatMemoryRepository (JDBC / Redis)
  • MessageChatMemoryAdvisor
  • CompressionQueryTransformer
  • RewriteQueryTransformer
  • RetrievalAugmentationAdvisor

LangChain4j 1.0+

  • ChatMemory → MessageWindowChatMemory
  • ChatMemoryStore (InMemory / Redis)
  • ChatMemoryProvider
  • CompressingQueryTransformer
  • RewritingQueryTransformer
  • DefaultRetrievalAugmentor
// LangChain4j 对照实现（了解即可）
// 1. ChatMemory + ChatMemoryStore
ChatMemory chatMemory = MessageWindowChatMemory.withMaxMessages(20);
ChatMemoryStore memoryStore = new InMemoryChatMemoryStore();
// 或 RedisChatMemoryStore（社区实现）

// 2. QueryTransformer（对标 Spring AI 的 Compression / Rewrite）
QueryTransformer compressionTransformer =
    new CompressingQueryTransformer(chatLanguageModel);
QueryTransformer rewriteTransformer =
    new RewritingQueryTransformer(chatLanguageModel);

// 3. RetrievalAugmentor（对标 Spring AI 的 RetrievalAugmentationAdvisor）
RetrievalAugmentor augmentor = DefaultRetrievalAugmentor.builder()
    .queryTransformer(compressionTransformer)
    .contentRetriever(contentRetriever)
    .build();

// 4. AIServices 组装（对标 Spring AI 的 ChatClient + Advisor）
Assistant assistant = AiServices.builder(Assistant.class)
    .chatLanguageModel(model)
    .chatMemoryProvider(memoryId ->
        MessageWindowChatMemory.withMaxMessages(20))
    .retrievalAugmentor(augmentor)
    .build();

// 使用
String answer = assistant.chat("它的大城市有哪些？");
框架选择建议

如果项目已经使用 Spring Boot 3/4，优先选择 Spring AI 2.0+——与 Spring 生态深度集成，ChatMemory 的 Redis/JDBC 实现开箱即用，Advisor 链与 Spring AOP 理念一致。LangChain4j 更适合非 Spring 项目或需要与 Python LangChain 对齐 API 的场景。

6 面试口述要点

以下为路线图面试题（第一梯队）的口述要点，按 RAG 完整链路 + Chunking 和 Agent 记忆系统 两条线组织。

Q1: 多轮对话 RAG 中指代消解为什么重要？Spring AI 如何解决？

多轮对话中用户常用代词（如"它"）指代前文实体，直接用原始查询做向量检索，召回率极低——因为代词没有语义信息。Solution：Spring AI 2.0 的 CompressionQueryTransformer 读取 MessageChatMemoryAdvisor 注入的对话历史，利用 LLM 将代词消解为具体实体，生成上下文自包含的独立查询后再检索。

关键点：记忆注入必须先于查询改写，否则改写器无法获取上下文。

Q2: Spring AI 2.0 ChatMemory 的完整架构？

三层架构：ChatMemory（记忆容器，MessageWindowChatMemory 滑动窗口）→ ChatMemoryRepository（持久化层，JDBC/Redis 开箱实现）→ MessageChatMemoryAdvisor（注入层，将历史 Message 注入 ChatClient 请求）。Conversation ID 必填，类比 Session ID 标识会话。

升级点：MessageChatMemoryAdvisor 替代废弃的 PromptChatMemoryAdvisor，以 Message 列表注入而非文本拼接，保留 role 信息。

Q3: CompressionQueryTransformer 和 RewriteQueryTransformer 的区别？

Compression：指代消解，解决"它"指代谁的问题，输入历史 + 当前查询，输出自包含查询。类比 SQL JOIN 合并上下文。

Rewrite：查询重写，优化检索表达，将口语化查询改写为更适合向量搜索的关键词组合。类比 MySQL 查询优化器重写执行计划。

组合顺序：Compression → Rewrite → Retrieve（先消解指代，再优化表达）。

Q4: RAG 完整链路是什么？多轮对话场景需要哪些额外组件？

单轮 RAG 链路：文档加载 → Chunking 分块 → Embedding 向量化 → 存入向量数据库 → 用户查询 → 向量检索 Top-K → 拼接到 Prompt → LLM 生成回答。

多轮额外组件：ChatMemory（历史对话存储）+ MessageChatMemoryAdvisor（记忆注入）+ CompressionQueryTransformer（指代消解）+ RewriteQueryTransformer（查询重写）+ RetrievalAugmentationAdvisor（编排检索管道）。

Q5: Agent 记忆系统如何设计？滑动窗口有什么局限？

滑动窗口（MessageWindowChatMemory）保留最近 N 条消息，简单高效，但旧消息直接丢弃——如果关键上下文在窗口外，模型会"遗忘"。

改进方向：1）摘要记忆——定期将旧消息压缩为摘要（需手写实现，Spring AI 无内置）；2）向量记忆——将历史消息向量化，按当前查询做相似度检索召回（类比 RAG 检索历史）；3）分层记忆——短期窗口 + 长期摘要 + 向量检索三层组合。

Q6: RetrievalAugmentationAdvisor 和 QuestionAnswerAdvisor 的区别？何时用哪个？

RetrievalAugmentationAdvisor：支持查询转换器链（Compression + Rewrite）+ 文档检索器，适合多轮对话 RAG。每轮额外调用 LLM 做查询改写。

QuestionAnswerAdvisor：简易 RAG，直接用原始查询检索，无查询改写。适合单轮问答或无代词场景。无额外 LLM 调用。

选型：多轮对话 → RetrievalAugmentationAdvisor；单轮问答 → QuestionAnswerAdvisor。

7 📝 术语表

术语 桥梁式解释（类比 Java/Spring/MySQL/Redis） 在本教程中的角色
ChatMemory 类比 Spring Boot 的 Session（存储 HTTP 会话状态）→ ChatMemory 存储 LLM 对话消息历史 多轮对话的记忆容器
MessageWindowChatMemory 类比 TCP 滑动窗口协议（只保留窗口内数据包）→ 只保留最近 N 条消息，旧消息淘汰 控制上下文长度，防止 Token 超限
ChatMemoryRepository 类比 Spring Data 的 Repository（声明接口 + 框架实现）→ 对话记忆的持久化接口 记忆持久化层（JDBC / Redis）
MessageChatMemoryAdvisor 类比 Spring MVC HandlerInterceptor（请求前注入数据）→ 在 LLM 调用前注入历史 Message 将记忆注入 ChatClient 请求
PromptChatMemoryAdvisor 已废弃的前代记忆 Advisor，将历史拼接到 prompt 文本而非 Message 列表 已被 MessageChatMemoryAdvisor 替代
指代消解 类比 SQL JOIN（合并关联表数据）→ 将代词与上下文实体"关联合并"使查询自包含 解决"它"指代不明的问题
查询改写 类比 MySQL 查询优化器（重写执行计划提升性能）→ 重写用户问题以提升向量检索召回率 优化向量搜索的召回率
CompressionQueryTransformer Compression = 压缩（将历史 + 查询压缩为自包含查询），类比 SQL JOIN 合并上下文 指代消解："它" → "丹麦"
RewriteQueryTransformer 类比 MySQL 优化器重写 SQL → 重写查询表达以优化向量搜索 查询重写：优化检索召回率
QueryAugmenter Augmenter = 增强器，类比 Spring AOP 的 Advice（增强目标方法）→ 增强用户查询的上下文 查询增强器接口（QueryTransformer 的上层概念）
RetrievalAugmentationAdvisor 类比 Spring AOP 的链式 Advice（多个 Advice 顺序执行）→ 组合查询转换器 + 检索器的 Advisor RAG 核心编排器
QuestionAnswerAdvisor 简易版 RetrievalAugmentationAdvisor，无查询改写，直接检索 + 增强 简易 RAG 方案（无指代消解）
Conversation ID 类比 Session ID（标识 HTTP 会话）→ 标识 LLM 对话会话 隔离不同用户的对话上下文
