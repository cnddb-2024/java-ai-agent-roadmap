一、为什么文档入库要过消息队列（12min）

你在 Phase 1 的 RAG 知识库里，文档入库链路是「解析 → 切分 → 向量化 → 写向量库」，整条同步跑下来一个 50 页的 PDF 要几十秒。如果这是用户上传文档后触发的 HTTP 接口，请求早超时了。解决方案和你熟悉的电商场景一模一样：下单接口只负责把订单写库 + 发一条"去发货"的消息，真正的发货逻辑由消费端慢慢处理——把"要做的重活"从请求线程里剥离出去。

RabbitMQ（一个基于 AMQP 协议的消息队列服务器）就是干这个的。消息队列（MQ）可以类比为"跨进程的阻塞队列"：你在 Java 里用过的 BlockingQueue 只能在同一个 JVM 内解耦生产者和消费者，MQ 把这个队列搬到了独立的服务进程里，两边通过网络读写——于是上游服务崩了不影响下游消费，下游慢了消息先排队不会压垮上游，这就是异步解耦。

AMQP（Advanced Message Queuing Protocol）是消息队列的通用协议标准，地位类似 JDBC 之于 MySQL：你面向 AMQP 编程，RabbitMQ 只是其中一个实现。Spring Boot 的 spring-boot-starter-amqp 开箱封装了全部常用能力（本篇全部用它，不引第三方）。

1.1 本篇目标架构

用户上传文档
     |
     v
[rag-web 服务]                          [rag-ingest 服务]（同一应用的两个模块也可）
     | 1. 存原始文件（本地/MinIO）              |
     | 2. 写 doc_id 幂等记录                    | 3. @RabbitListener 收到消息（手动 ACK）
     | 3. convertAndSend(队列, 消息) --------> | 4. 幂等检查：Redis setIfAbsent(doc_id)
     | 4. publisher-confirm 收到 broker 确认    | 5. PDFBox 解析 -> TokenTextSplitter 切分
     |                                         |    -> EmbeddingModel 向量化 -> VectorStore.add
     |                                         | 6. 成功: basicAck / 业务失败: basicNack(requeue=false)
     |                                         v
     |                                   [业务死信队列 dlq.doc.ingest]
     |                                         |
     v                                         v
  秒级返回 "已受理"                      告警 / 人工重放 / 定时补偿
可靠性三件套对应关系：不丢消息靠 publisher-confirm + 持久化 + 手动 ACK；不重复处理靠幂等键（doc_id）；失败不吞靠 nack 进死信队列（DLQ）。这是面试「MQ 可靠性」的高频三问，路线图 knowledgeops-agent 项目里就是「幂等键 + 重试 + DLQ」这套组合。

1.2 核心概念速览

概念一句话解释你熟悉的类比
Exchange 交换机消息的入口，按规则转发到队列，本身不存消息邮局分拣员
routing key生产者发消息时贴的"地址标签"收件地址
Binding 绑定交换机与队列之间的转发规则分拣规则表
Queue 队列真正存消息的缓冲区，FIFO待办箱
手动 ACK消费者处理完才确认，崩溃未确认的消息会重新投递签收快递，不签不算送达
DLQ 死信队列存放被拒绝/过期/超长的"死消息"的兜底队列退件柜
TTL消息或队列的存活时间，过期即死信验证码有效期

二、部署 RabbitMQ 并接入 Spring Boot（15min）

2.1 Docker 一条命令起服务

docker run -d --name rabbitmq \
  -p 5672:5672 -p 15672:15672 \
  rabbitmq:3.13-management

# 5672 = AMQP 通信端口（应用连它）；15672 = 管理控制台
# 浏览器打开 http://localhost:15672 ，默认账号密码 guest/guest

2.2 依赖与配置

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-amqp</artifactId>
</dependency>
spring:
  rabbitmq:
    host: localhost
    port: 5672
    username: guest
    password: guest
    publisher-confirm-type: correlated   # 开启发送方确认（broker 收到后回调 ConfirmCallback）
    publisher-returns: true              # 路由不到队列时回退消息（ReturnCallback 可感知）
    listener:
      simple:
        acknowledge-mode: manual         # 手动 ACK，处理完成才确认
        prefetch: 5                      # 每个消费者最多预取 5 条未确认消息，防止压垮
        default-requeue-rejected: false  # 抛异常被拒后不再自动重入队（交给 DLQ）
Spring Boot 3.3.x 对应 Spring AMQP 3.2.x，以上配置项全部开箱支持，无需任何额外代码。prefetch 的意义：默认不限流时 broker 会把队列消息全推给消费者打爆内存，类似 MySQL 连接池必须设 maxPoolSize。

2.3 声明交换机、队列、死信拓扑（开箱 Bean 方式）

业务队列通过 x-dead-letter-exchange 参数绑定死信交换机——被 nack 拒绝的消息会自动转入死信队列，这是 RabbitMQ 开箱的 DLQ 机制，不需要你手动搬运消息。

@Configuration
public class MqTopologyConfig {

    public static final String EXCHANGE_DOC = "ex.doc.ingest";
    public static final String QUEUE_DOC = "q.doc.ingest";
    public static final String DLX = "ex.doc.dlx";
    public static final String DLQ_DOC = "dlq.doc.ingest";

    @Bean
    public TopicExchange docExchange() {
        return ExchangeBuilder.topicExchange(EXCHANGE_DOC)
                .durable(true)          // 持久化：broker 重启后交换机仍在
                .build();
    }

    @Bean
    public Queue docQueue() {
        return QueueBuilder.durable(QUEUE_DOC)
                .withArgument("x-dead-letter-exchange", DLX)   // 死信去哪
                .withArgument("x-dead-letter-routing-key", "doc.dead")
                .build();
    }

    @Bean
    public Binding docBinding() {
        return BindingBuilder.bind(docQueue())
                .to(docExchange()).with("doc.ingest.#");   // topic 通配：doc.ingest.pdf 等
    }

    @Bean
    public DirectExchange dlxExchange() {
        return ExchangeBuilder.directExchange(DLX).durable(true).build();
    }

    @Bean
    public Queue dlqQueue() {
        return QueueBuilder.durable(DLQ_DOC).build();
    }

    @Bean
    public Binding dlqBinding() {
        return BindingBuilder.bind(dlqQueue()).to(dlxExchange()).with("doc.dead");
    }
}

三、生产端：上传后发消息 + 发送确认（10min）

上传接口只做三件事：存文件、发消息、秒回"已受理"。消息体里只放定位信息（docId、文件路径、文档类型），不带文件内容——消息队列传大文件是反模式，类似你不会把整个 Excel 塞进 Kafka 的 key。

@RestController
@RequestMapping("/api/documents")
public class DocumentController {

    private final RabbitTemplate rabbitTemplate;
    private final ObjectMapper objectMapper;

    public DocumentController(RabbitTemplate rabbitTemplate, ObjectMapper objectMapper) {
        this.rabbitTemplate = rabbitTemplate;
        this.objectMapper = objectMapper;
    }

    /** 上传接口：同步部分只做落盘 + 投递，秒级返回 */
    @PostMapping("/upload")
    public Map<String, Object> upload(@RequestParam MultipartFile file) throws IOException {
        String docId = UUID.randomUUID().toString();
        Path saved = Files.write(
                Path.of("/data/docs", docId + "-" + file.getOriginalFilename()),
                file.getBytes());

        Map<String, String> msg = Map.of(
                "docId", docId,
                "path", saved.toString(),
                "type", "pdf");

        rabbitTemplate.convertAndSend(
                MqTopologyConfig.EXCHANGE_DOC, "doc.ingest.pdf",
                objectMapper.writeValueAsString(msg));

        return Map.of("docId", docId, "status", "ACCEPTED");
    }

    /** 发送方确认：broker 是否真的收到了（开箱回调，注册一次全局生效） */
    @PostConstruct
    public void initConfirmCallback() {
        rabbitTemplate.setConfirmCallback((correlationData, ack, cause) -> {
            if (!ack) {
                // 真实项目在此落库补偿或告警，demo 打日志即可
                System.err.println("消息未到达 broker: " + cause);
            }
        });
        rabbitTemplate.setReturnsCallback(returned ->
                System.err.println("消息路由失败(无匹配队列): " + returned.getMessage()));
    }
}

四、消费端：解析 → 切分 → 向量化 → 入库，幂等 + 手动 ACK + 死信（15min）

消费端复用你 Phase 1 已掌握的 Spring AI 开箱组件（TokenTextSplitter、EmbeddingModel、VectorStore，Spring AI 2.0.1 GA），本篇新增的只有 MQ 这一层壳。

4.1 幂等消费：Redis setIfAbsent 挡重

为什么必然重复：手动 ACK 模式下，消费者处理完但 ACK 网络丢失、或进程在 ACK 前被杀，broker 会重新投递——至少一次投递（at-least-once）是 MQ 的默认语义，重复不可避免，只能靠业务侧幂等兜住。幂等消费指同一条消息被处理多次，结果和处理一次相同（你在知识库增量更新任务里做过的"内容哈希幂等入库"是同一思想：入库动作必须能安全重放）。

最简单的挡重实现：Redis setIfAbsent（即 SETNX，key 不存在才写入并返回 true），docId 作为幂等键。它相当于数据库唯一索引的缓存版，但注意 SETNX 方案要求"检查 + 占位"原子完成，setIfAbsent 一条命令天然满足。

public boolean tryLockDoc(String docId) {
    // 90 天过期：防止 Redis 堆积；入库成功的 docId 短期内不该再处理
    Boolean first = stringRedisTemplate.opsForValue()
            .setIfAbsent("rag:ingested:" + docId, "1", Duration.ofDays(90));
    return Boolean.TRUE.equals(first);
}
更硬的兜底是数据库唯一索引：向量库的 metadata 里给 doc_id 建唯一约束，即使 Redis 键过期后消息重放，入库也会被唯一索引拒绝。Redis 挡重 + DB 唯一索引兜底 = 双保险，面试答到这两层就完整了。

4.2 完整监听器（手动 ACK + 失败进 DLQ）

@Component
public class DocIngestListener {

    private final DocumentReaderFactory readerFactory;   // 你的解析封装（PDFBox/POI）
    private final TokenTextSplitter splitter = new TokenTextSplitter();
    private final EmbeddingModel embeddingModel;
    private final VectorStore vectorStore;
    private final StringRedisTemplate stringRedisTemplate;

    public DocIngestListener(DocumentReaderFactory readerFactory,
                             EmbeddingModel embeddingModel,
                             VectorStore vectorStore,
                             StringRedisTemplate stringRedisTemplate) {
        this.readerFactory = readerFactory;
        this.embeddingModel = embeddingModel;
        this.vectorStore = vectorStore;
        this.stringRedisTemplate = stringRedisTemplate;
    }

    @RabbitListener(queues = MqTopologyConfig.QUEUE_DOC, ackMode = "MANUAL")
    public void onMessage(Message message, Channel channel) throws IOException {
        long deliveryTag = message.getMessageProperties().getDeliveryTag();
        String body = new String(message.getBody(), StandardCharsets.UTF_8);
        String docId = null;
        try {
            Map<String, String> msg = objectMapper.readValue(body, new TypeReference<>() {});
            docId = msg.get("docId");

            // 1. 幂等挡重：重复投递直接 ACK 跳过（视为处理成功）
            if (!tryLockDoc(docId)) {
                channel.basicAck(deliveryTag, false);
                return;
            }

            // 2. 解析（Phase 1 已掌握：PDFBox / POI reader）
            Document doc = readerFactory.read(msg.get("type"), Path.of(msg.get("path")));

            // 3. 切分 + 补充 docId 元数据，再向量化入库（Spring AI 开箱链路）
            List<Document> chunks = splitter.apply(List.of(doc));
            chunks.forEach(c -> c.getMetadata().put("doc_id", docId));
            vectorStore.add(chunks);   // 内部走 EmbeddingModel 向量化后写入向量库

            // 4. 成功：手动确认
            channel.basicAck(deliveryTag, false);
        } catch (Exception e) {
            // 业务失败：nack 且不重入队 -> 按队列死信配置自动进 DLQ
            // 注意：重复 3 次以上仍失败的消息，人工在 DLQ 里排查（解析损坏文件等永久错误）
            channel.basicNack(deliveryTag, false, false);
        }
    }
}
两种失败的区分（你写 Python requests 调 LLM API 时遇到过的同款问题）：瞬时错误（网络抖动、embedding 服务超时）值得重试，可以配置 spring.rabbitmq.listener.simple.retry 让框架在内存里重试 N 次后才进死信；永久错误（文件损坏、密码格式错误）重试无意义，直接 nack 进 DLQ。demo 阶段先统一进 DLQ，生产再加区分。

5.2 面试高频问答（对应路线图岗位要求「分布式 / 缓存 / 消息队列」）

面试题30 秒答法
怎么保证消息不丢？三段：生产端 publisher-confirm + returns 回调兜底；broker 端交换机/队列/消息持久化；消费端手动 ACK，处理完才确认。
怎么保证不重复消费？MQ 本身只能做到 at-least-once，幂等在业务层：Redis setIfAbsent 挡重 + 向量库 doc_id 唯一约束兜底。
消费失败怎么办？区分瞬时/永久错误：瞬时错误框架级重试（退避），永久错误 nack 进 DLQ 告警 + 人工/定时补偿重放。
为什么用 MQ 而不是线程池异步？线程池在 JVM 内，重启丢任务且无法水平扩展；MQ 持久化消息、天然多消费者分摊、上下游独立伸缩。

📝 术语表

术语一句话解释
RabbitMQ / 消息队列（MQ）跨进程的"阻塞队列"服务器：生产者把消息投进队列就返回，消费者按自己的节奏取件处理，实现异步解耦。
AMQP消息队列的通用协议标准，类似 JDBC 之于 MySQL——面向协议编程，换实现不用改代码。
Exchange / routing key / Binding邮局分拣三件套：交换机按消息上的地址标签（routing key）和分拣规则（Binding）把消息投进队列。
异步解耦重活从请求线程剥离到队列另一端，上游不被下游拖慢，下游崩溃也不丢任务。
publisher-confirm / returns发送方确认：broker 收到消息回调 ConfirmCallback；消息路由不到任何队列时回调 ReturnsCallback。
手动 ACK消费者处理完才"签收"，进程崩溃时未签收的消息会被 broker 重新投递。
prefetch每个消费者最多预取的未确认消息数，防止 broker 疯狂推送打爆消费者内存，类似连接池 maxPoolSize。
幂等消费同一消息处理多次结果不变；实现上用 Redis setIfAbsent（SETNX）挡重 + 数据库唯一索引兜底。
死信队列（DLQ）被拒绝/过期/超长的消息的兜底队列，等价于快递的退件柜，供告警与人工重放。
TTL消息/队列的存活时间，过期未消费即转入死信。
at-least-onceMQ 默认投递语义：消息至少送达一次，可能重复——所以业务侧幂等是标配而非可选项。
瞬时错误 / 永久错误网络抖动类重试有意义；文件损坏类重试无意义，应直接进死信。（你在 Python requests 篇已接触同款概念）
