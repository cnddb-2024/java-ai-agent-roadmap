01为什么离线 90 分线上会翻车

你在 08-27 学过的 RAG 评测（Recall@K / nDCG / LLM-as-Judge）解决的是离线评测：拿固定测试集打分。但生产环境的真相是——离线分数高不等于线上体验好。两类根因必须能脱口而出：

A
根因一：测试集分布失真
离线集（几百条人工标注 QA）与线上真实 query 分布不一致：线上是长尾、口语化、含错别字、多轮指代的问法；离线集偏"干净高频"。知识库更新后离线集没同步，时效性也失真。类比：单元测试全用"正常参数"，生产环境全是边界值。
B
根因二：指标过拟合 / 评测口径不一致
离线用 RAGAS / LLM-judge 打连续分（0-1），线上用行为信号（点踩/追问/转人工），度量对象不同，相关性自然弱；对着同一评测集反复调阈值/提示词会过拟合；LLM-as-judge 自身偏差被固化；离线不覆盖兜底/拒答路径，而线上大量流量走兜底。
✅ 一句话总结（面试金句） "离线评测验证'检索+生成'质量，线上指标验证'用户体验'，两者必须做对齐闭环：线上指标发现问题 → 回流 bad case → 补进离线评测集 → 回归验证修复 → 再观察线上指标。"这就是评测闭环（Evaluation Loop）。

02五个线上体验指标：定义与埋点方案

统一思路：埋点（Instrumentation）= 在用户行为的关键节点打点计数，配合 MeterRegistry（指标注册表）和维度标签（model / channel / knowledge_base）。类比：你平时用 Micrometer 给 Spring Boot 加 @Timed 统计接口耗时，思路完全一致，只是这里统计的是"用户体验信号"。

指标定义（分子 ÷ 分母）业务含义
点踩率 thumbs_down_rate点踩会话数 ÷ 有反馈会话数回答质量差的直接信号
追问率 followup_rate同会话内重复/换法再问的会话数 ÷ 总会话数首次回答没解决问题的信号
转人工率 escalation_rate主动转人工/转接的会话数 ÷ 总会话数RAG 兜不住、需人工介入
空回答率 empty_answer_rate无检索结果/拒答的请求数 ÷ 总请求数检索召回或拒答阈值问题
会话解决率 session_resolution_rate未点踩、未追问、未转人工且正常收尾的会话数 ÷ 总会话数综合体验的健康度
ℹ️ 配套指标 时延与 Token 用量直接用 Spring AI 自带的 OTel GenAI 指标（gen_ai_client_operation_seconds 等），无需自己埋——官方文档 Observability 章节有完整指标表。

03Micrometer 埋点实操（Spring AI 2.0.1）

3.1 反馈事件埋点（点踩 / 追问 / 转人工）

Java · Counter 计数器埋点
@RestController
@RequestMapping("/api/v1")
public class FeedbackController {

    private final MeterRegistry meterRegistry;
    private final FeedbackRepository repository; // 事件落库（供 bad case 回流复用）

    public FeedbackController(MeterRegistry meterRegistry, FeedbackRepository repository) {
        this.meterRegistry = meterRegistry;
        this.repository = repository;
    }

    // 前端点 👎 时上报
    @PostMapping("/feedback/thumbs-down")
    public void thumbsDown(@RequestBody FeedbackReq req) {
        // ① Counter 计数，带维度标签
        meterRegistry.counter("rag.feedback.thumbs_down",
                "model", req.model(),
                "knowledge_base", req.kb()).increment();

        // ② 结构化事件落库：query + 上下文快照 + 配置版本（bad case 回流原料）
        repository.save(new FeedbackEvent(
                req.sessionId(), req.messageId(),
                req.query(), req.contextChunks(),
                req.answer(), "thumbs_down", req.configVersion()));
    }
}

3.2 空回答率埋点（ChatClient 返回后判断）

Java · 空回答 / 兜底路径埋点
@Service
public class RagService {

    private final ChatClient chatClient;
    private final MeterRegistry meterRegistry;
    private final FeedbackRepository repository;

    public String chat(String sessionId, String query) {
        String answer = chatClient.prompt(query).call().content();

        // 空回答：无内容或命中"无依据拒答"模板
        if (answer == null || answer.isBlank()
                || answer.contains("无法回答")) {
            meterRegistry.counter("rag.empty_answer",
                    "reason", "no_context_or_refusal").increment();
            // 同时把 query + 上下文快照写入 bad case 表
            repository.save(new FeedbackEvent(
                    sessionId, null, query, null, answer,
                    "empty_answer", configService.getConfigVersion()));
        }
        return answer;
    }
}
✅ 指标看板思路 Counter/Timer 数据接 Prometheus + Grafana（你项目里已有），按天/按知识库分组看趋势；点踩率、空回答率是"红绿灯指标"，超过阈值触发告警。类比你们现有接口成功率看板，只是监控对象从"接口"变成"用户体验信号"。

04bad case 回流评测集：四步闭环

bad case（坏案例）是线上表现差的真实样本（点踩、空回答、转人工的 query + 上下文快照）。回流 = 把这些真实样本转成离线评测集的增量，让离线评测永远跟着线上跑。四步闭环：

1
采集
从反馈事件表捞取负反馈/空回答/转人工的 query + 上下文快照 + 配置版本（configVersion 必须存，否则无法复现）。
2
标注
人工或 LLM 辅助打错误类型标签：检索漏召回 / 排序差 / 幻觉 / 拒答误判——分层定位问题归属（检索层 vs 生成层）。
3
回流
去重（与 golden set 比对、防泄露污染）后写入评测集/回归集。
4
修复验证
调参后跑回归集，确认 bad case 转好且无新回归（no regression）。
Java · bad case 回流（事件监听 + 夜间回流 Job）
@Component
public class BadCaseReflowJob {

    private final FeedbackRepository feedbackRepository;
    private final EvalCaseRepository evalCaseRepository;

    // 每日夜间：负反馈 → 标注（简化为按规则打标签）→ 回流评测集
    @Scheduled(cron = "0 0 2 * * *")
    public void reflow() {
        List<FeedbackEvent> badCases = feedbackRepository
                .findByTypes(List.of("thumbs_down", "empty_answer", "escalation"));

        for (FeedbackEvent e : badCases) {
            // ① 去重：按 (query 归一化 + configVersion) 判断是否已在评测集
            if (evalCaseRepository.existsByQueryAndConfigVersion(
                    normalize(e.query()), e.configVersion())) {
                continue;
            }
            // ② 写入评测集（含上下文快照，保证可复现）
            evalCaseRepository.save(new EvalCase(
                    e.query(), e.contextChunks(), e.answer(),
                    e.feedbackType(), e.configVersion()));
        }
    }

    private String normalize(String q) {
        return q == null ? "" : q.trim().toLowerCase();
    }
}

05CI 质量门禁：让回归测试自动卡关

CI 质量门禁（Quality Gate）指把评测跑进构建流程，不达标构建失败——和你项目里已有的 SonarQube 门禁、单元测试覆盖率门禁一个套路，只是评测对象换成 RAG 质量。建议用"黄金测试集（golden set）+ 回流 bad cases"双层裁判：

裁判内容门禁规则防什么
黄金测试集人工标注、只增不改的稳定集通过率 < 阈值 或 较基线下降 > 1pp 即失败调优过拟合、无依据改动
回流 bad cases线上负反馈转化、持续增长的回归集新增 bad case 通过率 > 阈值修 A 坏 B 的回归
Java · EvalRunner（Spring AI Evaluator 接口）
// Spring AI 2.0.1：评估核心接口在 spring-ai-commons 的 org.springframework.ai.evaluation 包
// Evaluator / EvaluationRequest / EvaluationResponse（@FunctionalInterface）

public class EvalRunner {

    private final Evaluator evaluator;      // 可自行实现：构造 LLM-as-judge 打分
    private final VectorStore vectorStore;

    public boolean runRegression(List<EvalCase> cases) {
        int pass = 0;
        for (EvalCase c : cases) {
            // 用检索上下文构造 EvaluationRequest（RetrievalAugmentationAdvisor 的 DOCUMENT_CONTEXT）
            EvaluationRequest req = new EvaluationRequest(
                    c.query(), c.contextChunks(), null);
            EvaluationResponse resp = evaluator.evaluate(req);
            if (resp.isPass()) pass++;
        }
        double rate = (double) pass / cases.size();
        // 门禁：通过率 < 90% 即失败（值按项目实际定）
        return rate >= 0.90;
    }
}
⚠️ 版本陷阱（务必记住） 研究确认：RelevancyEvaluator / FactCheckingEvaluator 这些开箱评估类在 Spring AI 1.1.x 可用，但在 2.0.1 的 evaluation 包源码中不存在（官方 2.0 文档存在与源码错位，页面标注 still in development）。2.0 下要么用 1.1.8 依赖，要么自行实现 Evaluator 接口。教程代码按"自行实现 Evaluator"给出，最稳。

06可观测性平台对照：LangSmith 在线评估 + Annotation Queues

如果你不想全手写，业界平台已把"bad case 回流"产品化。以 LangSmith 为例（LangChain 官方平台，支持 LangChain4j 接入）：

LangSmith 能力对应我们手写的环节
Trace 全链路一次对话从 query → 检索 → 生成的全链路追踪（可复现）
在线 Evals（filters + sampling rate + LLM-as-judge）自动化给生产 trace 打分（RAG 分层评估：context precision / faithfulness）
Annotation Queues（标注队列）领域专家评审生产 trace，反馈直接进评测数据集 = bad case 回流的产品化实现
数据集版本化 + 批量评估黄金测试集管理，可脚本化接 CI

分工建议：Micrometer/Prometheus 负责基础设施级指标（延迟/错误/量），LangSmith 类平台负责质量级评估（回答好坏/检索相关），两者互补不冲突。

📝 术语表

线上体验对齐把离线评测指标与线上用户体验信号（点踩/追问/转人工）对齐闭环的工程实践，防止"离线高分线上翻车"。
埋点（Instrumentation）在用户行为关键节点打点计数/记录事件，类比给 Spring Boot 接口加耗时统计，这里统计的是体验信号。
MeterRegistry（指标注册表）Micrometer 的指标容器，Counter/Timer/Gauge 都在这里注册，接 Prometheus/Grafana 展示——你项目已用。
bad case（坏案例）线上表现差的真实样本（点踩/空回答/转人工的 query + 上下文快照 + 配置版本），是回流评测集的原料。
回流（Reflow）把线上 bad case 去重、标注后写回离线评测集的过程，让离线评测永远跟线上同步。
黄金测试集（golden set）人工标注、只增不改的稳定评测集，作为调优裁判防过拟合——类比"期末考试题不泄题"。
CI 质量门禁（Quality Gate）把评测跑进构建流程、不达标构建失败的自动化卡关，类比 SonarQube 门禁。
评测闭环（Evaluation Loop）线上指标发现问题 → 回流 bad case → 离线回归验证 → 再观察线上指标的持续循环。
LLM-as-Judge（大模型当裁判）用 LLM 给回答/检索打分（如 faithfulness），前面 08-27 已学过，这里作为在线 evals 的打分引擎复用。
Annotation Queues（标注队列）LangSmith 的专家评审机制：领域专家评审生产 trace，反馈直接进评测数据集。
