1. RAG 全链路概览（10min）

RAG（Retrieval-Augmented Generation，检索增强生成）是让 LLM 基于你的私有文档回答问题的核心技术。它通过在生成回答前先检索相关文档片段，将检索到的上下文注入到 Prompt 中，从而减少幻觉、提升事实准确性。

上半部分为离线索引阶段（Indexing），下半部分为在线检索阶段（Retrieval）

核心概念速记
  • Indexing（索引）：离线预处理文档 → 分块 → Embedding → 存入向量数据库
  • Retrieval（检索）：在线将用户提问向量化 → 相似度搜索 → 注入上下文 → LLM 生成
  • 为什么需要分块？：LLM 上下文窗口有限，且小片段检索精度更高
  • 为什么需要 Embedding？：将文本转为数学向量，支持语义相似度计算

3. 文档加载与分块 Chunking（12min）

文档加载和分块是 RAG 的第一步，直接影响检索质量。分块太大导致检索精度下降，太小则丢失上下文。

Spring AI
LangChain4j
import org.springframework.ai.document.Document;
import org.springframework.ai.reader.pdf.PagePdfDocumentReader;
import org.springframework.ai.reader.tika.TikaDocumentReader;
import org.springframework.ai.transformer.splitter.TokenTextSplitter;
import org.springframework.ai.vectorstore.VectorStore;

@Service
public class RagIngestionService {

    private final VectorStore vectorStore;

    public RagIngestionService(VectorStore vectorStore) {
        this.vectorStore = vectorStore;
    }

    public void ingestDocuments(String filePath) {
        // 1. 文档加载（支持 PDF/TXT/DOCX，Tika 自动识别格式）
        TikaDocumentReader reader = new TikaDocumentReader(filePath);
        List<Document> documents = reader.get();

        // 2. 分块（Chunking）— 按 token 分割
        TokenTextSplitter splitter = new TokenTextSplitter(
            800,   // 每块最大 800 token
            200,   // 每块最小 200 token
            100,   // 重叠 100 token（保留上下文连续性）
            10000, // 单文档最大 token
            true    // 是否保留分隔符
        );
        List<Document> chunks = splitter.apply(documents);

        // 3. 存入向量数据库（自动 Embedding + 存储）
        vectorStore.add(chunks);

        System.out.println("已入库 " + chunks.size() + " 个文档片段");
    }
}
import dev.langchain4j.data.document.Document;
import dev.langchain4j.data.document.DocumentSplitter;
import dev.langchain4j.data.document.DocumentParser;
import dev.langchain4j.data.document.loader.FileSystemDocumentLoader;
import dev.langchain4j.data.document.parser.TextDocumentParser;
import dev.langchain4j.data.document.splitter.DocumentSplitters;
import dev.langchain4j.data.segment.TextSegment;
import dev.langchain4j.store.embedding.EmbeddingStoreIngestor;

@Service
public class RagIngestionService {

    public void ingestDocuments(String dirPath) {
        // 1. 加载目录下所有文档（Tika 自动解析 PDF/DOCX/TXT）
        List<Document> documents =
            FileSystemDocumentLoader.loadDocuments(dirPath);

        // 2. 配置分块策略
        DocumentSplitter splitter = DocumentSplitters.recursive(
            800,   // 每块最大 800 token
            100,   // 重叠 100 token
            new HuggingFaceTokenizer() // token 计算器
        );

        // 3. 创建 Ingestor（自动 Embedding + 存储）
        EmbeddingStoreIngestor ingestor = EmbeddingStoreIngestor.builder()
            .documentSplitter(splitter)
            .embeddingModel(embeddingModel)
            .embeddingStore(embeddingStore)
            .build();

        // 4. 执行入库
        ingestor.ingest(documents);

        System.out.println("文档入库完成");
    }
}
Chunking 策略选择（面试高频）
策略适用场景优缺点
固定大小分块（按 token）通用场景、快速 demo简单高效，但可能截断语义
递归分块（按段落→句子→词）结构化文档（Markdown/HTML）语义完整性好，推荐首选
滑动窗口 + 重叠长文连续性要求高上下文连续，但存储增大
语义分块（按 Embedding 相似度）高精度检索质量最高，但计算成本大

推荐分块参数

  • 块大小：500-800 token（约 375-600 个中文字），兼顾检索精度和上下文完整性
  • 重叠：10-15% 的块大小（如 800 token 块设 80-120 重叠），避免边界信息丢失
  • 分离器：优先按段落（\n\n）→ 句号（。）→ 逗号分割

4. 向量检索与 RAG 问答链路（15min）

文档入库后，用户提问时需要：将问题向量化 → 在向量数据库中检索相似片段 → 将检索结果注入 Prompt → 发送给 LLM 生成回答。

方案 A：QuestionAnswerAdvisor（简单 RAG）

@Service
public class RagQaService {

    private final ChatClient chatClient;
    private final VectorStore vectorStore;

    public RagQaService(ChatClient.Builder builder, VectorStore vectorStore) {
        this.vectorStore = vectorStore;
        this.chatClient = builder.build();
    }

    public String ask(String question) {
        // 一行代码实现 RAG：Advisor 自动检索 + 注入上下文
        return chatClient.prompt()
            .user(question)
            .advisors(QuestionAnswerAdvisor.builder(vectorStore)
                .searchRequest(SearchRequest.builder()
                    .similarityThreshold(0.70)  // 相似度阈值
                    .topK(5)                  // 取 top 5 相关片段
                    .build())
                .build())
            .call()
            .content();
    }
}

方案 B：RetrievalAugmentationAdvisor（高级 RAG）

public String advancedAsk(String question) {
    // 模块化 RAG：查询改写 + 检索 + 上下文增强
    Advisor ragAdvisor = RetrievalAugmentationAdvisor.builder()
        // Pre-Retrieval：查询改写（提高检索质量）
        .queryTransformers(RewriteQueryTransformer.builder()
            .chatClientBuilder(chatClient.mutate())
            .build())
        // Retrieval：向量检索
        .documentRetriever(VectorStoreDocumentRetriever.builder()
            .vectorStore(vectorStore)
            .similarityThreshold(0.50)
            .topK(5)
            .build())
        // Post-Retrieval：上下文增强
        .queryAugmenter(ContextualQueryAugmenter.builder()
            .allowEmptyContext(false)  // 无检索结果时拒答（防幻觉）
            .build())
        .build();

    return chatClient.prompt()
        .user(question)
        .advisors(ragAdvisor)
        .call()
        .content();
}

ContentRetriever retriever = EmbeddingStoreContentRetriever.builder()

    .embeddingModel(embeddingModel)

    .contentRetriever(retriever)

        .chatModel(chatModel)
        .build())

        .build())
    .build();
防幻觉技巧：在 Prompt 模板中明确要求"如果上下文中没有相关信息，请回答'我不知道'"，这是生产环境 RAG 的标配。Spring AI 的 ContextualQueryAugmenter.allowEmptyContext(false) 和 LangChain4j 的 minScore 都能从机制上防止无依据回答。

6. 面试题精讲（3min）

Q1（第一梯队）：请口述 RAG 完整链路及每个环节的 why
答题框架：RAG 分为离线索引和在线检索两个阶段。
索引阶段：DocumentLoader 加载文档 → Splitter 分块（why：LLM 上下文有限，小片段检索精度高）→ Embedding 向量化（why：将语义转为数学向量支持相似度计算）→ VectorStore 存储（why：支持高效近似最近邻搜索）。
检索阶段：用户提问向量化 → VectorStore 相似度检索 topK → 将检索结果注入 Prompt 模板 → LLM 基于上下文生成回答（why：减少幻觉，回答有据可查）。
Chunking 策略：推荐 recursive 分块（按段落→句子→词递归分割），块大小 500-800 token，重叠 10-15%。太大会降低检索精度，太小会丢失上下文。
Q2（第一梯队）：混合检索 + Rerank 原理
混合检索：结合向量检索（语义相似）和关键词检索（BM25/TF-IDF），两者互补。向量检索擅长理解同义词和语义，关键词检索擅长精确匹配专有名词和代码。
融合方法：RRF（Reciprocal Rank Fusion）是常用融合算法，公式 score = Σ 1/(k + rank_i)，k 通常取 60。
Rerank：检索后用 Cross-Encoder 模型对 topK 候选重新打分排序。与 Bi-Encoder（Embedding 模型）不同，Cross-Encoder 同时编码 query 和 document，精度更高但速度慢。典型流程：向量检索召回 50 条 → Rerank 精排取 top 5。

@RestController
@RequestMapping("/api/rag")
public class RagController {

    private final RagQaService ragQaService;
    private final RagIngestionService ingestionService;

    @PostMapping("/ingest")
    public String ingest(@RequestParam String filePath) {
        ingestionService.ingestDocuments(filePath);
        return "文档入库成功";
    }

    @PostMapping("/ask")
    public String ask(@RequestParam String question) {
        return ragQaService.ask(question);
    }
