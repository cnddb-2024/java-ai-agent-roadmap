二、工程结构：DDD 分包 + Maven 多模块（15min）

DDD 分层（Domain-Driven Design，领域驱动设计）：按业务职责分包而不是按技术类型分包。对 RAG 项目来说，"领域"就是检索链路的各个环节—— ingestion（入库）、retrieval（检索）、generation（生成）。这与你熟悉的 Controller/Service/DAO 三层不冲突，是把 Service 内部再按领域切细。

2.2 什么时候升 Maven 多模块

Maven 多模块（Multi-Module）：把一个工程拆成多个子 pom（如 starter / rag-engine / llm-adapter / web-api），各自独立编译。适合团队协作或组件复用；个人项目用 2.1 的单模块 DDD 分包即可，避免过度设计。参考 LangChain4j 企业级落地教程的模块划分方式：

<!-- 多模块示例：父 pom 打包类型为 pom -->
<modules>
    <module>rag-engine</module>      <!-- 检索引擎核心 -->
    <module>llm-adapter</module>     <!-- 大模型适配层：OpenAI/Ollama 切换 -->
    <module>web-api</module>         <!-- REST/SSE 接口层 -->
</modules>

企业知识库 RAG 全链路：混合检索 + Rerank + 引用溯源 + 评测回归。

| 配置 | Recall@5 | nDCG@10 | P95 延迟 |

四、决策文档（ADR）归档（10min）

ADR（Architecture Decision Record，架构决策记录）：每个重要技术选型写一份小文档，记录"为什么选它 / 放弃了什么 / 代价是什么"。类比：技术方案评审的会议纪要，但结构固定、随代码入库。Michael Nygard 提出的这个轻量实践在业界广泛使用。你已经写过决策日志 #01（向量库选型），今天把两份 ADR 归档进 docs/adr/ 并统一编号。

轻量 ADR 模板（Simple 风格，适合个人项目）：

# ADR-0002：Rerank 方案选型——Cohere API vs 本地 bge-reranker

日期：2026-09-15
状态：已接受

## 背景
混合检索 RRF 融合后 Top-10 召回噪声仍偏多，需 Cross-Encoder 精排。

## 决策
选本地 bge-reranker-v2-m3（CPU 推理），放弃 Cohere Rerank API。

## 理由（数据支撑）
- 质量：金标集 MRR@10 0.749(Cohere) vs 0.721(bge)，差距 4% 可接受
- 延迟：86ms(bge) vs 215ms(Cohere)，本地无网络抖动
- 成本：内网部署零 API 费用；数据不出域（企业合规）
- 代价：占用 ~3GB 内存；模型更新需自行运维

## 放弃的方案
Cohere Rerank：质量略优但按 token 计费、依赖外网。
LLM-as-Reranker：延迟 >1s，不满足 P95 预算。

## 撤销条件
若延迟预算放宽至 500ms+ 且预算充足，可切回 API 方案。
决策日志是路线图贯穿线：面试"讲清 why"的弹药库。每份 ADR 控制在一页内——Nygard 的经验是"没人读大文档，但不知道决策理由会导致灾难性后果"。完整对比数据放在配套的评测报告里，ADR 只留结论。

五、工程化三件套：可观测 / 回归 / CI 门禁（8min）

5.1 可观测（Spring AI 开箱）

Spring AI 的 Micrometer 可观测你在 Phase 0 已接入（spring-boot-starter-actuator + micrometer-registry-prometheus），工程化整理时只需确认三个关键指标进 Grafana：token 用量、检索命中率、P95 生成延迟。

5.2 评测回归：一条脚本

#!/bin/bash
# run_eval.sh —— 金标集回归：指标低于阈值即退出码非 0
set -e
python3 eval/compute_metrics.py --golden eval/golden_set.jsonl \
  --api http://localhost:8080/api/rag/query \
  --out docs/evaluation-report.md
python3 eval/check_threshold.py --min-recall 0.85   # CI 门禁阈值

5.3 CI 门禁（GitHub Actions）

CI 门禁（Quality Gate）：评测指标低于阈值就让流水线失败，防止检索质量悄悄劣化合并进主干——类比单元测试覆盖率门禁。参考项目 rag-knowledge-system 用 Testcontainers（用 Docker 容器起真实 pgvector 的集成测试工具，Java 测试界相当于"每个 PR 自动起一套真实中间件"）做检索质量回归。

# .github/workflows/eval.yml 核心片段
- name: Run retrieval regression
  run: |
    ./mvnw verify -Peval        # Testcontainers 起 pgvector
    ./eval/run_eval.sh          # 指标低于阈值则失败

📝 术语表

术语一句话解释
DDD 分层按业务领域（入库/检索/生成）分包，而非按技术类型（Controller/Service）分包的组织方式
Maven 多模块一个父工程拆多个子 pom 独立编译，类比把单体应用按组件拆成多个 jar
ADR（架构决策记录）记录"为什么选它/放弃了什么/代价是什么"的一页小文档，随代码入库
