Redis 会话记忆与缓存实战：Spring AI ChatMemory 持久化到 Redis + 会话状态缓存（Phase2 中间件补齐）

总预估时长：约 55min（体系理清 12min / Redis Repository 手写 20min / 装配与会话缓存 15min / 验收与面试 8min） · 技术栈：Spring AI 2.0.1 GA + Spring Boot 3.3 + Redis 7

一、为什么默认的内存版会话记忆不够用（10min）

你在多轮对话 RAG 任务里用过的 MessageWindowChatMemory 默认把对话历史存在 JVM 内存里（InMemoryChatMemoryRepository，本质是一个 ConcurrentHashMap）。这在生产有两个致命问题，你其实早就见过同款：应用一重启，所有用户的对话记忆清零；部署两个实例后，用户第一次请求落在实例 A、第二次落在实例 B，B 根本没有这个会话的历史。

解法你闭着眼都能想到——把存储从 JVM 内存挪到 Redis。这和传统 Web 里 HttpSession 存内存、生产换 Spring Session + Redis 共享会话是同一个演进：Redis 在你的知识体系里本来就是"带 TTL 的分布式 HashMap"，会话记忆不过是又一个 key 而已。本篇要做的只有一件事：给 Spring AI 的记忆体系换一个 Redis 存储后端。

二、Spring AI ChatMemory 体系 5 分钟理清（12min）

Spring AI 2.0.1 GA 的记忆体系分三层，各层职责如下（你多轮对话任务里接触过其中两个，这里把关系串起来）：

组件职责类比
ChatMemory（接口）对上层提供"按会话读写消息"的门面，默认实现 MessageWindowChatMemory 负责裁剪窗口MyBatis 的 SqlSession 门面
ChatMemoryRepository（接口）真正存取消息的仓库，可替换存储后端MyBatis 的 Mapper / DAO 层
MessageChatMemoryAdvisor（顾问）拦截器式的 Advisor：请求前把历史消息注入 Prompt，响应后把新消息写回仓库AOP 环绕通知
Conversation ID（会话标识）区分不同对话的 key，通常一个浏览器会话/一个用户一个Redis 里的 key / session id

MessageChatMemoryAdvisor 就是那个"记忆顾问"：每次你调 ChatClient 时它自动把 conversationId 对应的历史拼进请求、拿到回答后再把这一轮问答写回去——你的业务代码一行都不用改。MessageWindowChatMemory 则像滑动窗口日志：仓库里可能存了 100 条历史，但它只取最近 N 条（默认 20）注入 Prompt，防止 Token 爆炸。

三、⚠️ 框架无内置实现：手写 RedisChatMemoryRepository（20min）

以下为业界通用手写方案（Spring AI 2.0.1 GA 的 ChatMemoryRepository 接口签名）。核心思路：每个会话存成一个 Redis Hash，field 自增序号保证消息顺序，value 存 JSON；再给 key 设 TTL 自动清理冷会话——这正是你熟悉的"分布式 HashMap + EXPIRE"用法。

3.1 存储结构设计

Redis 结构key 示例说明
Hash（会话消息）rag:chat:conv:{conversationId}field=消息序号，value=消息 JSON；按序号排序取窗口
Set（会话清单）rag:chat:conversations记录所有 conversationId，供 findConversationIds 返回
String（会话状态缓存）rag:chat:state:{conversationId}第四节的会话状态缓存，与消息体分离

消息 JSON 不直接序列化 Spring AI 的 Message 对象（其内部结构复杂且版本间易变），业界做法是存一个精简 DTO（role + text），读出来时按 role 重建 UserMessage / AssistantMessage——存取协议自己可控，框架升级不受影响。

3.2 接口实现（完整可运行）

/** 消息的精简存储 DTO */
public record StoredMessage(String role, String text) {}

/** 序列化工具（Spring Boot 自带 Jackson，无需额外依赖） */
@Component
public class StoredMessageCodec {
    private final ObjectMapper mapper = new ObjectMapper();

    public String encode(Message message) {
        try {
            return mapper.writeValueAsString(
                    new StoredMessage(message.getMessageType().getValue(),
                            message.getText()));
        } catch (JsonProcessingException e) {
            throw new IllegalStateException("消息序列化失败", e);
        }
    }

    public Message decode(String json) {
        try {
            StoredMessage sm = mapper.readValue(json, StoredMessage.class);
            return "USER".equals(sm.role())
                    ? new UserMessage(sm.text())
                    : new AssistantMessage(sm.text());
        } catch (JsonProcessingException e) {
            throw new IllegalStateException("消息反序列化失败", e);
        }
    }
}
@Component
public class RedisChatMemoryRepository implements ChatMemoryRepository {

    private static final String CONV_KEY = "rag:chat:conv:";
    private static final String CONV_SET = "rag:chat:conversations";
    private static final Duration TTL = Duration.ofDays(7);   // 冷会话自动过期

    private final StringRedisTemplate redis;
    private final StoredMessageCodec codec;

    public RedisChatMemoryRepository(StringRedisTemplate redis, StoredMessageCodec codec) {
        this.redis = redis;
        this.codec = codec;
    }

    @Override
    public List<String> findConversationIds() {
        return new ArrayList<>(redis.opsForSet().members(CONV_SET));
    }

    @Override
    public List<Message> findByConversationId(String conversationId) {
        // Hash 的 field 是自增序号，按数值排序取出，保证消息顺序
        Map<Object, Object> entries =
                redis.opsForHash().entries(CONV_KEY + conversationId);
        return entries.entrySet().stream()
                .sorted(Comparator.comparingLong(e -> Long.parseLong((String) e.getKey())))
                .map(e -> codec.decode((String) e.getValue()))
                .toList();
    }

    @Override
    public void saveAll(String conversationId, List<Message> messages) {
        // 全量覆盖语义：窗口裁剪由上层 MessageWindowChatMemory 完成，仓库只管存
        String key = CONV_KEY + conversationId;
        redis.delete(key);
        Map<String, String> hash = new LinkedHashMap<>();
        for (int i = 0; i < messages.size(); i++) {
            hash.put(String.valueOf(i), codec.encode(messages.get(i)));
        }
        redis.opsForHash().putAll(key, hash);
        redis.expire(key, TTL);
        redis.opsForSet().add(CONV_SET, conversationId);
    }

    @Override
    public void deleteByConversationId(String conversationId) {
        redis.delete(CONV_KEY + conversationId);
        redis.opsForSet().remove(CONV_SET, conversationId);
    }
}
接口契约提醒：saveAll 是全量覆盖语义——窗口裁剪发生在上层 MessageWindowChatMemory，仓库层不要自己再截断，否则两层裁剪叠加会出现丢消息的诡异 bug。TTL 设 7 天是常见默认：会话记忆不是审计日志，过期即弃。

四、装配与验证 + 会话状态缓存（15min）

4.1 把 Redis 仓库装配进 ChatClient

装配只要两步：声明 MessageWindowChatMemory 指定我们的 Redis 仓库，再挂上 MessageChatMemoryAdvisor。之后每个请求带 conversationId，记忆自动持久化到 Redis——业务代码与内存版完全一致，这就是接口替换后端的好处。

@Configuration
public class ChatMemoryConfig {

    @Bean
    public ChatMemory chatMemory(RedisChatMemoryRepository redisRepository) {
        // 窗口 20 条：注入 Prompt 的最多最近 20 条，防止 Token 爆炸
        return MessageWindowChatMemory.builder()
                .chatMemoryRepository(redisRepository)
                .maxMessages(20)
                .build();
    }
}

@RestController
@RequestMapping("/api/chat")
public class ChatController {

    private final ChatClient chatClient;

    public ChatController(ChatClient.Builder builder, ChatMemory chatMemory) {
        this.chatClient = builder
                .defaultAdvisors(MessageChatMemoryAdvisor.builder(chatMemory).build())
                .build();
    }

    @PostMapping
    public String chat(@RequestBody Map<String, String> req) {
        return chatClient.prompt()
                .user(req.get("question"))
                .advisors(a -> a.param(ChatMemory.CONVERSATION_KEY, req.get("conversationId")))
                .call()
                .content();
    }
}

4.2 会话状态缓存：同一套 Redis 的第二用法

会话里除了消息历史，还有一堆会话状态：该会话上次检索用的知识库 namespace、用户画像摘要、上轮 rerank 结果等。它们和消息一样要求"重启不丢、多实例共享"，直接用 StringRedisTemplate 缓存即可，注意与消息体分开存（不同生命周期、不同清理策略）：

@Service
public class SessionStateService {

    private final StringRedisTemplate redis;

    public SessionStateService(StringRedisTemplate redis) {
        this.redis = redis;
    }

    public void saveState(String conversationId, String stateJson) {
        redis.opsForValue().set("rag:chat:state:" + conversationId,
                stateJson, Duration.ofHours(2));   // 状态短 TTL，消息长 TTL
    }

    public String loadState(String conversationId) {
        return redis.opsForValue().get("rag:chat:state:" + conversationId);
    }
}

5.2 面试高频问答

面试题30 秒答法
多轮对话的会话记忆怎么设计？分层：ChatMemory 窗口层裁剪 Token（默认 20 条）+ Repository 层可插拔存储。生产把 Repository 换成 Redis 实现多实例共享，会话按 conversationId 隔离、TTL 自动回收。
短期记忆和长期记忆的区别？短期记忆 = 当前对话窗口内的消息历史（Redis Hash 存消息 JSON）；长期记忆 = 跨会话的用户事实沉淀，做法是把要点向量化存 RedisVectorStore，新会话开始时按相似度检索注入（路线图 Redis 官方示例的双 Advisor 架构）。
为什么不用内存版 ChatMemory 上生产？重启丢会话 + 多实例不共享，和 HttpSession 不能单机存是同一个问题，换 Redis Repository 即可，业务代码零改动。
消息历史会不会把 Token 打爆？MessageWindowChatMemory 只注入最近 N 条；更精细的做法是摘要压缩（历史太长时让 LLM 先总结再入窗口）。

📝 术语表

术语一句话解释
ChatMemoryRepository（记忆存储仓库）Spring AI 里真正存取消息的接口，可插拔存储后端，类似 DAO 层——换 Redis 只需要换这个实现。
MessageWindowChatMemory（滑动窗口记忆）ChatMemory 默认实现：仓库存全量，注入 Prompt 只取最近 N 条，像日志的滑动窗口。
MessageChatMemoryAdvisor（记忆顾问）拦截器式 Advisor：请求前把历史注入 Prompt、响应后把新问答写回仓库，业务代码无感。
Conversation ID（会话标识）区分不同对话的 key，Redis 里就是 key 的一部分，等价于 session id。
RedisVectorStoreRedis 官方的向量检索存储（RediSearch 模块），用于把长期记忆向量化后按相似度取回。
短期记忆 / 长期记忆短期 = 当前对话窗口内的消息历史；长期 = 跨会话沉淀的用户事实，向量化存储、按需检索注入。
TTL（存活时间）即 Redis 的 EXPIRE：key 到期自动删除。冷会话记忆 7 天过期、会话状态 2 小时过期。
全量覆盖语义（saveAll）仓库的 saveAll 每次整体替换该会话的全部消息，窗口裁剪发生在上层，仓库只管存。
JacksonSpring Boot 自带的 JSON 序列化库，负责消息对象与 JSON 字符串互转。
