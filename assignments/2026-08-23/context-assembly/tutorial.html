上下文组装实战：检索片段排序 + Token 预算控制 + Lost-in-the-Middle 缓解（Spring AI QueryAugmenter）

总预估时长：约 60 分钟（问题定位与 U 型曲线 12min / 排序策略 10min / Token 预算控制 10min / Spring AI QueryAugmenter 实战 18min / LangChain4j 对照 6min / 面试要点 4min）。主线 Java（Spring AI + LangChain4j 双路径）。

一、上下文组装：RAG 链路里最容易被忽视的一环（12min）

上下文组装（Context Assembly——检索完成后、调用大模型之前，把若干检索片段"拼装"成最终 Prompt 的环节，类似 MyBatis 把查询结果映射成 Java 对象前的结果装配）决定了大模型"看到什么"。检索再准，如果片段顺序不对、超长被截断、噪声占预算，回答照样翻车。它要回答三个问题：

  • 排序：哪些片段放前面？——答案藏在本节的 U 型曲线里；
  • 预算：上下文窗口有限、API 按 token 计费，给每个片段多少预算？
  • 格式：片段怎么标注来源、怎么和用户问题拼接？

1.1 Lost-in-the-Middle：为什么要专门管顺序

Lost-in-the-Middle（中间遗忘现象）：Stanford 等机构 2023 年的研究发现，大模型对长上下文里开头和结尾的信息利用率高，对中间的信息显著"失明"——性能随相关信息位置呈 U 型曲线（类似人背单词表时对首尾单词记得最牢的"系列位置效应"）。这意味着：你把最相关的片段随手放在 Prompt 中段，模型可能恰好忽略它。

片段位置模型利用率组装策略
开头高（首因效应）放最重要的片段
结尾高（近因效应）放次重要的片段
中间低（U 型谷底）放最弱/兜底片段
实用排序法：按相关性分数降序排好后，把第 1 名放最前、第 2 名放最后、第 3 名放中间……这比单纯降序排列在评测中更稳，也是明天 RAG 评测任务里"改造前后对比"的现成实验变量。

二、Token 预算控制（10min）

Token 预算控制（在上下文窗口和成本约束内，给系统提示、历史对话、检索片段分配 token 配额的机制——类比 JVM 堆内存分区：各区域各得其所，超了就按策略淘汰）是生产级 RAG 的硬需求。典型预算分配：

总预算（假设 8K token，预留 1K 给输出）
├── 系统提示 + 工具说明      ~500 token（固定）
├── 多轮历史对话（截断/压缩）~1000 token（滑动窗口）
├── 检索片段区              ~5500 token（主战场）
└── 用户当前问题 + 拼接模板  ~500 token

检索片段区的三种淘汰策略（预算不够时按序触发）：

  • 按分数淘汰：低于阈值的整段丢弃（你昨天混合检索里的 minScore 思路平移过来）；
  • 按片段截断：保留每片段前 N token（配合引用溯源标注"内容有截断"）；
  • 按配额递减：排名越靠后的片段配额越少——第 1 名 1500、第 2 名 1000、第 3 名 700……像限流算法里按优先级分配令牌。

三、Spring AI 实战：QueryAugmenter + Advisor 管道（18min）

Spring AI 中承担组装职责的核心抽象是 QueryAugmenter（查询增强器——把检索到的文档内容与用户 Query 拼装成最终提示词的组件，可以理解为 Spring AI 版的"Prompt 总装车间"）。开箱实现 ContextualQueryAugmenter 支持模板化拼接与空文档兜底：

3.1 基础用法：ContextualQueryAugmenter

QueryAugmenter queryAugmenter = ContextualQueryAugmenter.builder()
    .allowEmptyContext(false)          // 检索结果为空时拒绝硬编答案
    .build();

RetrievalAugmentationAdvisor advisor = RetrievalAugmentationAdvisor.builder()
    .documentRetriever(vectorRetriever)
    .queryAugmenter(queryAugmenter)
    .build();

String answer = ChatClient.create(chatModel)
    .prompt()
    .advisors(advisor)
    .user("我们知识库里关于报销流程的规定是什么？")
    .call()
    .content();

allowEmptyContext(false) 是防幻觉的第一道闸门：检索不到内容时不给模型"无米之炊"的上下文，让它老老实实说"知识库中没有相关内容"——这与你明天的「引用与防幻觉」任务直接衔接。

3.2 自定义增强器：排序 + 预算 + 编号溯源一体

默认实现不管顺序和预算，生产上需要自定义。实现 QueryAugmenter 接口，把第一节、第二节的策略落进代码：

public class BudgetAwareAugmenter implements QueryAugmenter {

    private static final int CONTEXT_BUDGET = 5500; // 检索片段区 token 预算

    @Override
    public Query augment(Query query, List<Document> documents) {
        // 1. 按相关性分数降序排序
        //    （分数可来自 Rerank——昨天任务的精排环节，用 Cross-Encoder
        //     交叉编码器把 query 和文档拼在一起深度比对打分——
        //     或直接用向量相似度分数）
        List<Document> sorted = documents.stream()
            .sorted(Comparator.comparingDouble(this::score).reversed())
            .toList();

        // 2. Lost-in-the-Middle 缓解：第1名最前、第2名最后、其余居中
        List<Document> arranged = arrangeByUShape(sorted);

        // 3. 预算内逐段装入，配额递减；超预算立即停止
        StringBuilder context = new StringBuilder();
        int used = 0;
        int quota = 1500;
        for (int i = 0; i < arranged.size() && quota > 0; i++) {
            String chunk = truncate(arranged.get(i).getText(), quota);
            context.append("[片段").append(i + 1).append("] ")
                   .append(chunk).append("\n\n");
            used += estimateTokens(chunk);
            quota = Math.min(1500, CONTEXT_BUDGET - used) / 2; // 配额递减
        }

        // 4. 带编号溯源的拼接模板（引用溯源：回答时按片段编号标注依据）
        String augmented = """
            请仅依据以下知识库片段回答问题，并标注引用片段编号：
            %s
            问题：%s
            """.formatted(context, query.text());

        return new Query(augmented);
    }

    private List<Document> arrangeByUShape(List<Document> sorted) {
        // 首位放第1名，末位放第2名，中间按剩余顺序填入
        if (sorted.size() < 3) return sorted;
        List<Document> result = new ArrayList<>();
        result.add(sorted.get(0));
        result.addAll(sorted.subList(2, sorted.size()));
        result.add(sorted.get(1));
        return result;
    }
}

3.3 多轮对话的上下文压缩

多轮问答时，历史对话也要占预算。Spring AI 的 MessageChatMemoryRetriever 思路是"只把与当前问题相关的历史取回组装"——LangChain4j 对应 CompressionQueryTransformer（查询压缩器——把长对话历史压缩改写成一句独立完整问题的组件，类似把多轮聊天记录"蒸馏"成单次提问）。Spring AI Alibaba 的教程对此有完整示例（见来源列表）。

四、LangChain4j 对照：RetrievalAugmentor 管道（6min）

LangChain4j 把组装拆成两个可插拔组件：ContentAggregator（内容聚合器——多路召回结果的重排与淘汰，昨天 Rerank 已接触）与 ContentInjector（内容注入器——把最终片段注入 Prompt 模板的最后一环）：

ContentInjector contentInjector = ContentInjector.builder()
    .promptTemplate(PromptTemplate.from("""
        回答以下问题。可用上下文：
        {{contents}}
        问题：{{userMessage}}
        """))
    .metadataKeysToInclude(List.of("source", "segment")) // 片段带来源元数据
    .build();

RetrievalAugmentor augmentor = DefaultRetrievalAugmentor.builder()
    .contentRetriever(contentRetriever)
    .contentAggregator(contentAggregator)   // Rerank 精排（昨天成果）
    .contentInjector(contentInjector)       // 组装注入（今天主题）
    .build();
双框架对比记忆点：Spring AI 用 QueryAugmenter 一个抽象覆盖"拼接"并靠你自定义扩展排序与预算；LangChain4j 把"聚合排序"与"模板注入"拆成两个组件自由组合——粒度更细，学习曲线略陡。面试聊双框架选型时，这是 RAG 环节的具体差异例证。

五、面试要点速记（4min）

  • 第一梯队「RAG 完整链路 + Chunking 策略」的组装部分：能画出"检索 → 重排 → 组装（排序/预算/格式）→ 生成"完整链路并讲清每环节 why；
  • Lost-in-the-Middle：说出 U 型曲线结论 + "首尾放重要片段"对策，再补一句"这与人类记忆的系列位置效应同构"即出彩；
  • Token 预算：讲清"预算分配表 + 三级淘汰策略"，落在成本数字上（预算超 10% 响应成本涨多少）；
  • 空上下文兜底：allowEmptyContext(false) / 无依据拒答，衔接明天「引用与防幻觉」任务。

📝 术语表

  • 上下文组装（Context Assembly）：检索后、生成前，把检索片段排序、截断、拼接成最终 Prompt 的环节，类比 MyBatis 的结果装配。
  • Lost-in-the-Middle（中间遗忘）：LLM 对长上下文首尾信息利用率高、中间显著下降的 U 型曲线现象，类比人类记忆的系列位置效应。
  • Token 预算控制：在上下文窗口与成本约束内为各内容区分配 token 配额并按策略淘汰的机制，类比 JVM 堆内存分区管理。
  • QueryAugmenter（查询增强器）：Spring AI 中把文档内容与用户 Query 拼装成最终提示词的组件抽象，开箱实现为 ContextualQueryAugmenter。
  • ContentInjector（内容注入器）：LangChain4j 管道中把最终片段按模板注入 Prompt 的最后一环组件，与 ContentAggregator 配合。
  • CompressionQueryTransformer（查询压缩器）：LangChain4j 中把多轮对话历史压缩改写成单句独立问题的组件，用于控制历史 token 占用。
  • 引用溯源：回答中按片段编号标注依据来源的机制，是防幻觉与可信度验收的基础（明天任务展开）。
