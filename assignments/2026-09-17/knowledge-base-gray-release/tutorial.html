01为什么需要灰度发布："直接删旧写新"的三个风险

知识库更新最朴素的思路是"删掉旧数据，写入新数据"——就像你更新 MySQL 表数据时 DELETE FROM t WHERE id=1 再 INSERT。但在 RAG 系统里，这个朴素思路有三个致命问题，你需要能脱口而出：

风险表现类比
① 无验证就上线新切分/新内容没经过测试集验证，直接上线后检索质量跳水代码不跑测试就合并到 main
② 不可回滚上线发现 bad case 想回退，旧数据已被删除，只能重新解析重嵌入数据库没备份就执行了 DROP TABLE
③ 新旧污染更新是分批进行的，检索时新旧 chunk 混在 top-k 里，答案自相矛盾同一张表里两条互相冲突的配置都生效

灰度发布（Gray Release / Canary Release）的解决思路与微服务灰度一致：新老版本并存、验证通过再切流量、随时一键回滚。只不过这里"流量"是检索请求，"版本"是知识库快照。

02灰度发布五步流程总览

1
打版本标签（chunk version 标签）
写入新版本 chunk 时给每条记录的 metadata 打 version=v2，与旧数据共存不删。类比：给数据行加一个 version 列。
2
双 namespace 并行
单索引 + version 字段隔离，或双索引/双集合物理隔离；双索引方案用别名（alias）原子切换。
3
测试集双跑验证
同一批固定测试问题，分别对 v1 / v2 过滤条件各跑一次，对比 recall@k、命中率，量化"新版本更好还是更差"。
4
版本过滤切换
验证通过后，把检索入口的过滤条件从 version==v1 切到 version==v2（配置/开关级变更，秒级生效；可先 10% 流量灰度）。
5
清旧 chunk（一键回滚兜底）
稳定运行一段时间后，按过滤表达式删除旧版本数据；回滚只需把过滤条件切回旧版本。

03第 1-2 步：打版本标签 + 双 namespace 并行

3.1 打版本标签（Spring AI 2.0.1）

Spring AI 的 VectorStore（向量存储）接口把 metadata（元数据，即键值对标签）作为一等公民——写入时打标、查询时过滤、删除时按表达式删。给 chunk 打 version 标签就像给 MySQL 行加版本列：

Java · 写入带 version 标签的文档
// 1. 构建新版本文档，metadata 携带 version / embedding_model / doc_id
Document doc = new Document(content, Map.of(
        "version", "v2",
        "embedding_model", "text-embedding-3-large",
        "doc_id", "kb-1001"));

// 2. 写入向量库：与 v1 数据共存于同一 collection / 表
vectorStore.add(List.of(doc));

3.2 两种并行拓扑对比

拓扑原理优点缺点适用
单索引 + version 字段隔离同一 collection，靠过滤表达式隔离新旧成本最低、代码最简大版本切换需注意过滤+ANN 索引的召回损耗中小知识库、本文主线
双索引/双集合（物理隔离）两个 collection/index，用别名原子切换可独立重建、物理隔离更干净存储翻倍、需要别名管理大知识库、多环境并行
ℹ️ 双索引的别名切换（Elasticsearch 标准做法） 双索引方案切换时用别名（alias）原子完成：一个 POST /_aliases 请求里同时 remove 旧索引、add 新索引，客户端永远只访问别名，切换对应用无感——类比 Nginx upstream 平滑切换后端。

04第 3 步：测试集双跑验证（检索一致性）

双跑验证（A/B 检索对比）是灰度发布的核心决策依据：固定测试问题集（每问带标准答案/期望文档集），同一批 query 分别对 v1、v2 过滤条件各检索一次，对比命中率。类比：上线新推荐算法前，用同一批用户请求对老/新算法各算一遍指标。

4.1 双跑验证的指标口径

指标口径判据
recall@ktop-k 中命中标准文档的比例v2 ≥ v1 且无关键退化
命中标准文档数每个问题的期望文档是否出现在结果中v2 不丢失 v1 已命中的
答案采纳率（可选）LLM-as-judge 对答案质量打分v2 ≥ v1

4.2 检索一致性检查（关键）

若 embedding 模型未变，v2 相对 v1 的召回差异应只来自 chunk 切分/内容更新，而非向量分布漂移。若模型也换了，必须先单独评估跨模型可比性，否则"双跑结论"失真。这就是下文第 7 节的"三重版本耦合"陷阱。

Java · LangChain4j 1.20 双跑验证（Filter DSL）
// LangChain4j 元数据过滤 DSL：按 version 字段构造过滤器
Filter v1 = metadataKey("version").isEqualTo("v1");
Filter v2 = metadataKey("version").isEqualTo("v2");

// 同一 queryEmbedding 分别带 v1 / v2 filter 各查一次
List<EmbeddingMatch<TextSegment>> r1 = store.search(
        EmbeddingSearchRequest.builder()
                .queryEmbedding(q).filter(v1).maxResults(5).build()).matches();
List<EmbeddingMatch<TextSegment>> r2 = store.search(
        EmbeddingSearchRequest.builder()
                .queryEmbedding(q).filter(v2).maxResults(5).build()).matches();

// 断言：v2 命中标准答案集 ≥ v1 且无关键退化 → 通过
boolean pass = recall(r2, goldenAnswers) >= recall(r1, goldenAnswers);

05第 4-5 步：版本过滤切换 + 清旧 chunk（一键回滚）

5.1 版本过滤切换（配置级秒级生效）

验证通过后，把检索入口的过滤条件从 version==v1 切到 version==v2。这是配置/开关级变更，不需要重建索引；可先按 10% 流量灰度，观察线上指标再全量。

Java · Spring AI 2.x 按当前版本过滤检索
// 读取配置的当前版本（如配置中心 kb.version=v2）
String currentVersion = configService.getKbVersion();

// 构造过滤表达式：version == 'v2'（Spring AI 的 Filter Expression）
var expr = new FilterExpressionBuilder()
        .eq("version", currentVersion).build();

List<Document> docs = vectorStore.similaritySearch(
        SearchRequest.builder()
                .query("公司报销流程是什么")
                .topK(5)
                .filterExpression(expr)   // 只检索当前版本 chunk
                .build());

5.2 清旧 chunk + 一键回滚

Java · 按过滤表达式删除旧版本 + 回滚切换
// 回滚：只需把配置切回 v1，秒级生效，无需重建索引
// 当前版本 = "v1"（配置中心一键切换）

// 灰度结束、稳定运行后：删除旧版本 chunk（Spring AI 表达式删除）
vectorStore.delete("version == 'v1'");
// 对应 Qdrant: delete_by_filter(version='v1')
// 对应 pgvector: DELETE WHERE version='v1'
⚠️ 回滚顺序铁律 旧数据清理后回滚就只能依赖快照（向量库 snapshot 或对象存储备份）。推荐顺序：先切回旧版本 → 再重建/恢复。若旧数据已清理，务必有快照兜底——和 MySQL binlog 备份一个道理。

06Spring AI 2.0.1 完整链路示例

把五步串成一个可运行的服务：写入带版本标签 → 按当前版本过滤检索 → 按表达式清理。Spring AI 官方参考文档内置 "Document Versioning Use Case"（文档版本化用例）章节，说明这是官方认可的标准用法。

Java · 知识库灰度发布服务（Spring AI 2.0.1）
@Service
public class KnowledgeBaseService {

    private final VectorStore vectorStore;
    private final ConfigService config; // 当前版本配置（如 Nacos/本地配置）

    public KnowledgeBaseService(VectorStore vectorStore, ConfigService config) {
        this.vectorStore = vectorStore;
        this.config = config;
    }

    // ① 发布新版本：打 version 标签写入，与旧数据共存
    public void publishVersion(String version, List<String> chunks) {
        List<Document> docs = chunks.stream()
                .map(c -> new Document(c, Map.of(
                        "version", version,
                        "doc_id", UUID.randomUUID().toString())))
                .toList();
        vectorStore.add(docs);
    }

    // ② 检索：只查当前激活版本（过滤切换 = 配置变更）
    public List<Document> search(String query, int topK) {
        var expr = new FilterExpressionBuilder()
                .eq("version", config.getActiveVersion()).build();
        return vectorStore.similaritySearch(SearchRequest.builder()
                .query(query).topK(topK).filterExpression(expr).build());
    }

    // ③ 回滚：切配置即可（config.setActiveVersion("v1")）

    // ④ 清理旧版本（灰度结束后）
    public void cleanupVersion(String version) {
        vectorStore.delete("version == '" + version + "'");
    }
}
✅ 性能进阶知识（面试加分） "过滤 + ANN 索引"存在先扫描后过滤的召回损耗：pgvector 官方建议对过滤列建标量索引或分区（PARTITION BY LIST(version)）；Milvus 用分区键（partition key）避免全库扫描；Qdrant 用 payload 索引。面试时能主动讲出这一点，说明你真的理解生产细节。

07进阶：embedding 模型变更的"三重版本耦合"陷阱

很多团队只给 chunk 内容 打版本，忽略另外两个会变的维度，导致"RAG 应用上线两周就失效"：

版本维度变更会怎样必须联合打标
Prompt 版本提示词改动改变答案格式，但检索结果不变config_version
Embedding 模型版本换 embedding 模型后向量空间不同，新旧向量不可比——最危险embedding_model 必须与 version 成对
Chunking 策略版本切分粒度变了，同一文档的 chunk 边界不同version（内容+切分联合）
⚠️ 铁律：embedding 模型变更 = 强制全量重嵌入 + 联合打标 换 embedding 模型后，新旧向量处于不同的向量空间，混在一起检索 = 用两套坐标系找最近邻，结果毫无意义。必须：全量重嵌入 → 新数据带 embedding_model=v3 + version=v2 联合标签 → 双跑验证（用同一新模型对两版内容跑）→ 再切换。这正是灰度发布流程存在的意义。

📝 术语表

灰度发布（Gray/Canary Release）新老版本并存、验证通过再切流量、随时可回滚的发布方式；类比微服务灰度，但"流量"是检索请求、"版本"是知识库快照。
chunk version 标签写入向量库时给每条切分记录打的版本号 metadata 字段，类比 MySQL 数据行加 version 列，用于隔离新旧数据。
双 namespace 并行新旧数据同时存在（单索引靠 version 字段隔离，或双索引物理隔离），互不干扰。
双跑验证同一批固定测试问题对 v1/v2 各检索一次并对比指标，类比新算法上线前的 A/B 对比。
索引别名（Index Alias）Elasticsearch 的"指向真实索引的逻辑名字"，切换时原子 remove+add，客户端无感——类比 Nginx upstream 平滑切换。
Filter Expression（过滤表达式）Spring AI 向量检索的 metadata 过滤 DSL（如 version=='v2'），对应 SQL WHERE 子句。
metadata（元数据）附着在文档/向量上的键值对标签，类比数据库行的附加列，用于过滤与版本管理。
分区键（Partition Key）Milvus 等向量库按字段哈希分区的机制，避免过滤时全库扫描，类比 MySQL 表分区。
三重版本耦合Prompt / Embedding 模型 / Chunking 三个维度版本叠加变化互相影响的陷阱，最危险的是换 embedding 模型后向量空间不可比。
召回率（Recall@k）top-k 结果中命中标准答案的比例，灰度双跑的核心判据之一。
